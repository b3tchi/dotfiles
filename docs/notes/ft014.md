# Feature [[cat001]] [[product]]

## providing

Visible, resumable Pi workers hosted as named windows inside an existing
linked tmux project group: a transport that starts an agent, carries typed
messages to it, and takes one typed result back.

Transport only. What a worker stage is ALLOWED to do — where it runs, what its
message may carry — is declared by the consumer in a stage registry, so this
Feature carries any consumer's vocabulary and interprets none of it. Under Pi
that consumer is [[ft013]]; nothing here depends on it.

## api_surface

`pi-worker` is a nushell CLI ([[adr0001]], [[adr0002]]) linked into
`~/.local/bin` by the plugin's installer alongside the `stage-registry.nu`
module it parses; output is JSON because every consumer is another program.
`wait` prints nothing when there is no mail, so it reads correctly in a shell
conditional. Nineteen verbs in four groups:

- initiator: `spawn`, `send`, `wait`, `ack`, `resume`, `accept`, `stop`,
  `rm`, `reclaim`, `respawn`
- worker: `result`, `settled`
- observation: `status`, `inspect`, `workers`, `ps`, `liveness`, `timeline`
- setup: `doctor`

The stage registry is the consumer's, read from `PI_WORKER_STAGES` or
`${XDG_CONFIG_HOME:-~/.config}/pi-workers/stages.json`. Each entry is
`{name, isolation, payload}` in vocabulary that describes MECHANISM rather
than meaning: `isolation` is `worktree` (its own throwaway tree and branch) or
`main` (the operator's shared tree); `payload` is `ticket` (a stage name and
one ticket id, nothing else) or `instructions` (prose plus artifact ids). An
absent registry is an error, never a permissive default — "no stages
configured, so allow anything" would drop every gate the consumer meant to
impose.

`spawn` places the worker per its stage, records the identity envelope, and
only then starts Pi in a window named `<role>-<subject>@<project>`, addressed
thereafter by tmux window id because a name is ambiguous the moment two runs
share a role and subject. Evidence precedes the process deliberately: a worker
that dies during startup still leaves a cwd and a resume command behind. The
window carries `remain-on-exit`, so a crashed worker's error stays on screen,
and `@pinned`, so this repo's own tmux housekeeping does not reap a detached
worker. An isolated worker owns branch `wk-<task-or-subject>.<N>`; a worker
sharing the operator's tree is given a commit guard instead. Identity reaches
the extension as window-scoped environment (`PI_WORKER_RUN`/`UID`/`ROLE`/
`BRANCH`/`SESSION`/`SKILL`/`WINDOW`), because the extension must know which
inbox is its own before any message can arrive.

`wait` is non-destructive and redelivers until `ack`. `--uid` scopes it to one
worker; `--after <sequence>` returns only what the caller has not read, which
is how an initiator that hands a reported-but-unacked worker more work learns
when the new round is done — a plain wait would hand back the old report,
since unacknowledged is what pending means. `--after` is not an ack and
requires `--uid`, because sequences are numbered per worker. `ack` is a
delivery receipt, never acceptance, and it releases the DISPLAY half: the
window and the process in it. The worktree, branch and identity envelope stay,
which is what makes an acked worker respawnable.

`resume` sends feedback to the ORIGINAL session as an addressed message and
records which result it answered; that result then stops being delivered by
`wait` and stops counting as unacknowledged mail, while the worker reads as
`running` even though its last envelope truthfully still says `complete`. A
second rejection returns `escalate: true` and parks the worker at
`waiting_human`.

`accept` is the only verb that reclaims work, and every refusal is collected
BEFORE anything is touched — a refusal costs nothing, so a declined
acceptance can be retried once its cause is fixed. It refuses a worker that is
not `complete`, one holding uncommitted or untracked work, the main worktree,
and a branch whose commits are reachable from no other ref, since deleting
that would end the only copy. It is idempotent, and a tree or branch already
gone is the finished state rather than an error. `stop` closes the window and
keeps both tree and branch, since a stopped worker may hold unmerged commits.
`rm` releases an address only once its worker is `stopped` or `accepted`.
`reclaim` sweeps trees and branches no live worker owns, locally or with
`--remote`; `respawn` brings a reclaimed worker back on its own Pi session
under a new uid carrying `respawned_from`, because `accepted` has no outgoing
edge and history stays literally true.

`result` and `settled` are the worker's own side of the bus, reached through a
typed result tool the Pi extension registers in worker mode; a Pi session that
ORCHESTRATES workers drives every verb above through one `pi_worker` tool.
Inbox delivery is conservative: a message reaches an `idle` agent as an
ordinary user turn, every other state defers, and at most one message is
delivered per poll with the agent state re-read for each. A delivery is what
starts a turn, so a batch judged against one reading loses everything after
the first, and a mid-turn steer cannot be confirmed and is therefore never
chosen.

A stage may report `complete` only with the verdict its own discipline
produces, read from the typed `validation` field and never from the summary;
`spec-refinement` must carry `SRE PASS` ([[adr0027]]). Every completion
envelope carries result, validation verdict, worker window, Pi session id and
the exact `pi --session <id>` resume command.

Tmux hosts and displays worker processes and nothing else — no `send-keys`,
`wait-for` or `display-message` as transport ([[adr0028]]). The one pane
option written is `@pinned`, which tells the display host not to reap a window
and carries no message, completion signal or coordination state.

## data_model

Transient bus data lives under
`$XDG_RUNTIME_DIR/pi-worker/<run-id>/<worker-uid>/` in `inbox/`, `outbox/`
and `identity/` boxes, as versioned, monotonically sequenced JSON envelopes.
Directories are created `0700` with `mkdir -m` (a mkdir-then-chmod window is
long enough for a concurrent writer to correctly refuse the tree) and envelope
files are `0600` before they are linked into place. Writes go to a scratch
name and are renamed, so a reader sees a whole envelope or no file; a sequence
slot is claimed with `link(2)`, which fails if taken, so racing writers cannot
both win. A slot is the lowest unused one, so an outbox is `1..n` with no
gaps and a worker's result count is also its newest sequence. Envelopes cap at
64 KiB and completion summaries at 4 KiB. Addressing is the directory path,
which makes cross-run isolation structural rather than a filter someone can
forget; an address already in use is refused rather than inherited.

Envelope kinds are `inbox`, `result`, `error` and `identity`. Persisted worker
states are `created`, `running`, `waiting_human`, `blocked`, `failed`,
`complete`, `protocol_error`, `accepted` and `stopped`, with `complete →
accepted` the only edge into `accepted`. States granted from outside the
worker are marker files beside its envelopes — `accepted`, `stopped`,
`waiting_human`, and `reopened`, which records WHICH result a rejection sent
back. Delivery and the frame both read that marker, so a superseded result is
neither handed over by `wait` nor counted as unacknowledged mail. Marker
precedence is accepted, stopped, waiting_human, reopened, then the newest
result. Delivery receipts are `<sequence>.ack` files in the outbox. `unknown`
is an observational verdict, never persisted, and never a licence to stop,
accept or delete ([[adr0017]]).

An agent that settles without calling the typed result tool produces a
`protocol_error` envelope, never a completion. Durable task evidence stays in
bd, source state in Git, AKM state behind `akm`, and conversation history in
Pi JSONL; bus state is reconstructable from its envelopes and contains no
copied bd task body.

## sample

```text
pi-worker spawn --role impl --subject timestamp-file --skill work
# {"run":"r7","uid":"impl-1","branch":"wk-timestamp-file.0","live":true,...}
pi-worker send impl-1 --run r7 --stage work --instructions 'Add ...'
pi-worker wait --run r7 --block --timeout 300
# {"sequence":1,"kind":"result","payload":{"status":"complete",
#  "validation":"tests/foo.nu: 12 passed","resume":"pi --session <uuid>"}}
pi-worker resume impl-1 --run r7 --feedback 'criterion 2 is unmet'
pi-worker wait --run r7 --uid impl-1 --after 1 --block --timeout 300
pi-worker ack --run r7 --uid impl-1 --sequence 2
pi-worker accept impl-1 --run r7 --repo ~/.dotfiles
```

mid-round instruction, ack, refused acceptance, retry, teardown — is

## known_limitations

The Pi-side bridge is no longer unproven — it has been run against a live Pi
repeatedly, and doing so is what found the delivery defects the surface above
now describes (`dotfiles-nhit`, `dotfiles-c4kh`). Automated coverage is 339
protocol cases plus 175 bridge cases, and neither can substitute for the live
run: a fake host that answers `idle` to every state query cannot expose a
message lost because delivering the previous one started a turn.

Three limits remain. A mid-turn steer stays unusable until Pi tells a caller
whether one was accepted, so an urgent message waits for the agent to settle
rather than interrupting it. `settled` writes its `protocol_error` only when
nothing has been reported yet, so a worker that goes quiet in a LATER round
leaves no evidence on the bus at all. And an initiator learns of a lost or
ignored message only by timing out, because the bus has no acknowledgement
from the agent — only from the transport.
