# Spec [[cat001]] [[cat002]] [[board]]

## problem
An operator running Pi workers has no way to see what they are doing without
walking the tmux windows one by one. [[ft014]] records everything needed —
nine persisted worker states, an addressed message bus, `status` / `inspect` /
`workers` / `ps` / `liveness` / `timeline` — and renders none of it as a view.
`timeline` is per-worker and reads the LEGACY `run/<uid>` inbox/outbox tree, so
peer-to-peer traffic between two workers appears in no verb at all. The
operator's actual question is two panes wide: which agents exist and what state
each is in, and what has been said to whom, in time order.

[[ft012]] is the same question already answered for the other runtime. It
counts running claude agents per project, buckets them `idle` / `working` /
`blocked` / `done` under [[adr0024]]'s two-axis rule, and says explicitly that
it observes only — "rendering belongs to its consumers". That renderer was
never built; [[us023]] is the draft story asking for it, and its acceptance
criteria bind this work: consumers must not re-implement the join, and a
consumer that polls must not pay the ~600 ms probe cost on every refresh
(fine on demand, wrong on a timer). So this is not a second census. It is the
missing renderer, plus the two data widenings that let it cover Pi.

Three strands, one deliverable:

**A. Widen [[ft014]] — presence and a whole-project message read.** Pi's
`ExtensionAPI` exposes no state getter (`dotfiles-zxzj`); the bridge derives
`idle` / `streaming` / `compacting` / `shutting_down` from lifecycle events and
keeps it in extension memory only, written nowhere. The worker must publish its
own state to its address directory on each transition — atomic rename, 0600,
the same write discipline the envelopes already use. This is [[adr0017]]-shaped
deliberately: a component's own evidence about itself. Stale presence renders
as `unknown`, which licenses nothing (ft014 already holds `unknown` as an
observational verdict, never persisted). Second: a new verb `pi-worker messages
--json` returning every envelope in the project bus as
`{at, id, from, to, kind, content}`. `content` stays opaque — the transport
interprets no flow ([[adr0028]]) — so no `subject` field is added to the
envelope; the reader derives display text (first line, or `status — summary`
for a result). This keeps the widening inside ft014's existing `providing`
paragraph rather than minting a fourth transport feature.

**B. Widen [[ft012]] — the census stops being claude-only.** A second probe
reads `pi-worker workers` plus the new presence, emitting the same row shape
with a `runtime: claude | pi` column. [[adr0024]]'s split maps cleanly: the
bus job state is the `state` axis, published presence is the `status` axis;
`waiting_human` / `blocked` / `protocol_error` bucket as `blocked`,
`complete` / `accepted` / `stopped` as `done`. [[im011]] is the migration
target — the shipped nushell action, already split into a probe layer and a
pure transform layer, which is what makes a second probe cheap to add and
testable from fixtures. The us023 ticker constraint lands here too: the census
must publish a cached sample that pollers read, so a 1-2 s refresh does not
re-run one `claude` call per account.

**C. Mint a new `ft###` — `agent-monitor`, the renderer.** A two-pane TUI:
roster (uid/name, runtime, role, state, presence, live, age) over the widened
census, and a message log (time, from, to, derived subject) over
`pi-worker messages`. It joins nothing and knows no bus file layout — it execs
the published interfaces on a ticker, so the three open read-side retirements
in the bus (`dotfiles-a34y`, `dotfiles-v1zt`, `dotfiles-hp6v`) can land without
touching it. Engine in Go, because a keyboard-driven render loop has no nushell
structural fit; user-facing entry point is a nushell wrapper per [[adr0003]]'s
mandatory-wrapper clause, so nothing invokes the binary directly.

**D. Mint a new `adr####` widening [[adr0003]].** As written, Go is authorised
only when all three conditions hold — long-running daemon holding network
listeners, websocket/stream proxying or hot-path latency, and no nushell
structural fit. A TUI satisfies the third alone: it holds no listener and
proxies nothing, yet [[adr0001]]'s default cannot express a keyboard event loop
with concurrent samplers. The decision to record is a fourth Go category
(interactive render loop), scoped as narrowly as adr0003 scoped the daemon
case — explicitly not a licence to rewrite existing nushell actions.

Categories [[cat001]] (workflow tooling) and [[cat002]] (display platform).
[[sp025]] is adjacent but separate: agent-inbox is an agent asking its operator
a question, not the operator watching agents. Nothing here depends on it.

Open questions for spec-writing: whether the cached census sample is a file or
a short-lived daemon; whether the monitor is read-only or grows actions
(resume / stop / accept) once the view exists; whether presence needs a written
heartbeat interval or only transition writes, given [[adr0017]]'s warning that
absence of a beat is indistinguishable from a missed one.

## solution

Three widenings and one new Feature, shipped together because the renderer is
useless without the data and the data has no other consumer yet. The new
Feature is [[ft016|agent-monitor-tui]] (`proposed`); the two widenings are
`## extends` on [[ft014]] and [[ft012]], not new cards — each stays inside its
host Feature's existing `## providing`.

**A. [[ft014]] publishes worker presence and reads the whole project bus.**
The Pi bridge already derives `idle` / `streaming` / `compacting` /
`shutting_down` from lifecycle events and keeps it in extension memory, where
nothing can see it (`dotfiles-zxzj`). The extension publishes that state on each
transition the way it already mutates the bus: by shelling out to nushell
through the `ExecFn` it holds (`queue-mark-read` goes out exactly this way).
It imports `existsSync` / `readdirSync` / `readFileSync` and no writer at all,
and that boundary is worth keeping — nushell owns the bus layout ([[adr0001]]),
so the presence write is a module function doing the scratch-name-then-rename,
0600 discipline the envelopes already use, not a second writer in a second
language. The cost to measure during execution is one `nu -c` per transition,
several times a turn; debouncing, or dropping the write for states no consumer
renders, is a refinement decision and not a change of approach. It is the worker's own
evidence about itself, which is what [[adr0017]] requires of any reading a
consumer will act on; a reading past its freshness bound renders `unknown`,
and `unknown` licenses nothing. Second, a new verb `pi-worker messages --json`
returns every envelope in the project bus as `{at, id, from, to, kind,
content}`. No `subject` field is added: the transport interprets no flow
([[adr0028]]), so the subject is derived by the reader.

**B. [[ft012]] gains a second probe and stops being claude-only.** It reads
`pi-worker workers` plus the presence written in A, through the CLI and only
the CLI — [[adr0025]] binds the census to a supported surface, and the bus
tree is no more readable-by-outsiders than claude's `jobs/` tree is. Rows gain
`runtime: claude | pi`. [[adr0024]]'s two axes map without strain: the bus job
state is `state`, published presence is `status`; `waiting_human` / `blocked` /
`protocol_error` bucket as `blocked`, `complete` / `accepted` / `stopped` as
`done`, and an unrecognised state surfaces as `other` rather than vanishing
from the totals. [[im011]] is the migration target and the reason this is
cheap: its probe layer and its pure transform layer are already separate, so a
second probe is a new probe function plus fixtures, not a redesign.

**C. [[ft016]] renders, and joins nothing.** A Go TUI over the published
output of A and B: roster pane from `agent-census --json --detail`, message
pane from `pi-worker messages --json`, subject derived first-line-or-verdict.
It holds no bus paths, so the three open read-side retirements in the bus
(`dotfiles-a34y`, `dotfiles-v1zt`, `dotfiles-hp6v`) can land without touching
it. Both sampling loops carry [[adr0014]]'s three guards, since both read a
runtime directory that vanishes at logout.

The cost of the roster probe is the one real constraint: ~600 ms dominated by
one `claude` call per account, which [[us023]] names as fine on demand and
wrong on a timer. The solution is two clocks inside the one process — messages
sampled fast because they are local file reads, roster sampled slowly and on
an explicit `r`, rendering from the last good sample in between — and
deliberately **not** [[adr0012]]'s single-writer daemon publishing a shared
state file. That daemon is the right answer for [[us023]]'s bar and picker,
which poll continuously and are many; it is overbuilt for one interactive
process that can cache its own samples, and building it here would commit a
lifecycle, a start guard and a state-file contract to serve consumers that do
not exist yet. [[us023]] keeps it.

**D. A standalone `adr####` admits Go for [[ft016]].** [[adr0003]] authorises a
compiled helper only when all three of its conditions hold, and a TUI holds no
listener and proxies no stream; it satisfies the third alone. [[adr0021]] has
already ruled on exactly this temptation — it took Go for `hotkeyd` on stated
merits and refused to invoke adr0003's gate, because "borrowing that clause
anyway would make it unciteable the next time a proposal needs to pass it
honestly". This ADR follows that shape and [[adr0008]]'s: Go is admitted for
an interactive terminal UI on its own merits — raw-mode input, alternate
screen, resize handling and concurrent samplers are outside nushell's process
model, and [[adr0001]]'s default cannot express them at all — under conditions
stated in the ADR, without reopening adr0003's general test and without
licensing any rewrite of existing nushell actions. It carries the same wrapper
carve-out adr0021 took: adr0003 mandates a `nushell/actions/` front-end
because the binary is an engine and not an interface, and here the binary *is*
the interface, so a wrapper would forward argv and add a shell start-up to an
interactive launch. The binary links straight to `~/.local/bin`.

Scope held out deliberately: the monitor is read-only. `resume`, `stop` and
`accept` destroy worktrees, branches and addresses and stay with whoever
allocated them ([[ft014]]); putting them one keystroke from a roster row is a
separate decision, not a free addition.
