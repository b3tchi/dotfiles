# Spec [[cat001]] [[cat002]] [[board]]

## extends
[[ft016]]

## problem
[[ft016]]'s message pane is one flat list of envelopes, newest-first since
[[sp033]]. On a bus where three agents and an operator talk past each other,
that list interleaves every conversation: reading one exchange means picking
its rows out of everyone else's, and a reply two minutes old sits four rows
away from the message it answers. The pane shows the bus honestly and shows a
CONVERSATION nowhere.

Widen the pane with a THREADED view — a feature refresh of the accepted
[[ft016]], not a new capability and not a new story. Nothing here changes
[[ft012]] or [[ft014]]: the grouping is a reader-side derivation over the
envelopes [[ft014]]'s `messages` verb already publishes, exactly the altitude
[[adr0031]] puts a consumer's own display at, and no `thread_id` field is
added to an envelope ([[adr0028]] — the transport interprets nothing it
carries).

Decided at brainstorm, carried into spec-writing:

- **Thread key** is the sorted composite of the envelope's own ADDRESSES —
  `join(sort([from_address] + to_addresses), "|")` — never the rendered
  labels. [[adr0034]] is the whole reason: a label two parties share is
  exactly what resolution refuses to answer, so keying on labels would
  collapse two different conversations into one row and call it a thread.
  A message with two or more recipients keys on all of them, so a 3-party
  exchange is its own thread rather than being folded into either 2-party
  one. An envelope from an older `pi-worker` that predates the address fields
  ([[sp033]] T1) keys on what it has, forming its own degenerate thread
  rather than being dropped from the view.
- **Mode, not replacement.** `t` flips threaded <-> flat; a session opens
  THREADED. The flat chronological read stays reachable, which is what a busy
  bus is actually read with when you want time order rather than topic.
- **Nested inline, many open at once.** An expanded thread renders its
  messages indented directly beneath its own row; any number of threads may
  be open. One cursor walks thread rows and child rows alike — one rendered
  row list, one `SetMessagesLen`, so [[sp032]]'s first-class scroll and
  [[sp033]]'s newest-first liveness derivation (`cursor == 0 && scroll ==
  top`) carry over UNCHANGED rather than gaining a second authority.
- **A child row omits TO.** Thread rows carry `TIME`, participants, the
  message count and the newest message's SUBJECT; child rows carry `TIME`,
  `FROM` and SUBJECT only — the recipient is implicit in the thread's own
  participant pair, and repeating it on every child spends the pane's
  scarcest resource (width) on a constant.
- **Threads sort by their newest message, newest-first**, so an arrival
  re-sorts and a waking conversation jumps to the head. The head of the pane
  keeps meaning "most recent activity", which is what [[sp033]]'s inversion
  made it mean.
- **SUBJECT stays underived.** A thread row shows the newest message's
  subject through the same `subject.go` derivation, neutralisation and
  cell-aware truncation as today; grouping does not license parsing content
  ([[adr0031]]).
- **For-you is unchanged arithmetic.** [[sp033]]'s `*` marks a thread row
  when any message in it is addressed to the operator's resolved address, and
  `N for you` keeps counting MESSAGES, not threads — a count that silently
  changed units between modes would be worse than no count.
- **Filter semantics do NOT change.** `/` keeps matching `From` or any entry
  of `To`, never content. Because a thread's messages share participants, a
  matching thread matches wholly and children need no per-message logic at
  all. Widening `/` to match the derived SUBJECT was considered and declined
  for this refresh; it is separable and can carry its own `sp###`.
- **Keys.** `->` / `l` expand, `<-` / `h` collapse (on a child row, `<-`
  jumps to its thread row), `space` toggles, `t` flips mode. None shadows a
  documented binding: `KeyLeft`/`KeyRight` are decoded today and handled
  nowhere, and `space`, `l`, `h`, `t` are unbound. `enter` / `o` keep meaning
  detail-zoom. Every one of them ships with a test driving a real
  `tea.KeyMsg` through the translation layer ([[adr0036]]).

Constraints the spec must respect:

- `tui.Model` is a COMPARABLE struct by contract — fixtures assert `*m !=
  want` — so the expansion set cannot become a map or slice field on it.
  The `shell.opened` latch in `cmd/` is the standing precedent for
  per-session state that `Model` cannot hold; which shape wins is a
  spec-refinement call, not a brainstorm one.
- `--once` renders FLAT and byte-identical to today. A pipe has no cursor and
  nothing to expand, and [[sp030]] T9's byte-plain contract is cheap to keep
  — the same reasoning that keeps the detail pane out of `--once`.
- Go, per [[adr0030]]; no nushell wrapper, and nothing here opens a bus path
  directly.

Categories [[cat001]] and [[cat002]], matching [[ft016]]'s own. No `us###`
and no `im###`: [[sp030]] through [[sp033]] all landed on [[ft016]] as
feature work, and this continues that lineage — at [[ft016]] `status:
accepted`, so the finale is a feature-refresh archive, not a status flip.

## solution
Refresh [[ft016]] in place. No new `ft###` is minted and no `us###` / `im###`
lineage is invented: [[sp030]] through [[sp033]] all landed on [[ft016]] as
feature work and it is already `status: accepted`, so this is the
feature-refresh shape — the spec declares `## extends [[ft016]]`, `work-merge`
archives it without a status flip, and `spec-retro` rewrites [[ft016]]'s
`## api_surface` and `## data_model` to match what shipped.

**Threading is a pure derivation, in its own file.** A new unit under
`internal/render/` (or `internal/thread/`, a spec-refinement call) exposes one
function from `[]source.Message` to the pane's RENDERED ROW LIST: thread rows
in newest-first order, each followed by its child rows when the thread is
expanded. It holds no state, reads no bus path, and consumes only what
[[ft014]]'s `messages` verb already publishes through `source.Message` — the
altitude [[adr0031]] puts a consumer's own display at. No `thread_id` is
written onto an envelope ([[adr0028]]), and SUBJECT keeps coming from
`subject.go`'s existing derivation, neutralisation and cell-aware truncation:
grouping licenses no parsing of `content` it did not already license.

Keying is on the envelope's ADDRESSES per [[adr0034]] — `join(sort(
[from_address] + to_addresses), "|")` — so two parties sharing a label never
merge, a multi-recipient envelope forms its own thread, and an envelope
predating [[sp033]] T1's address fields keys on what it has rather than
vanishing.

**One list, one cursor.** The derived row list is what `SetMessagesLen`, the
scroll derivation and the detail-pane selection all see, so [[sp032]]'s
first-class scroll and [[sp033]]'s newest-first liveness
(`cursor == 0 && scroll == top`) keep working unchanged rather than gaining a
second authority. A thread row's selection resolves to its newest envelope for
the detail pane, reusing [[sp031]]'s VALUE-identity selection key — an index
key is exactly what re-derivation breaks.

**State without breaking the comparable `Model`.** `tui.Model` is asserted with
`*m != want` in existing fixtures, so it may gain the mode as a plain
`bool` field but must not gain the expansion SET. The set lives in `cmd/`, the
standing precedent being the `shell.opened` latch, and `HandleKey` reports
expand / collapse / toggle through its existing `Outcome` return — the same
caller-acts-on-a-signal shape [[sp033]] T8 used for `Send` — rather than
mutating state it cannot hold. Keys: `t` mode, `->` / `l` expand, `<-` / `h`
collapse, `space` toggle; none shadows a documented binding, and each ships
with a test driving a real `tea.KeyMsg` through the translation layer
([[adr0036]]).

**What deliberately does not change.** `/` keeps matching `From` or any entry
of `To` and never content, so a thread matches wholly and children need no
per-message filter logic. [[sp033]]'s `*` marks a thread row when any member is
for the operator, and `N for you` keeps counting messages. `--once` renders
FLAT and byte-identical, keeping [[sp030]] T9's byte-plain pipe contract — the
same reasoning that keeps the detail pane out of a pipe. Go per [[adr0030]],
no wrapper, and the source-scanning test that keeps this binary off bus paths
stays green. Categories [[cat001]] and [[cat002]] are unchanged; no ADR under
either is overturned, so this refresh mints none.

**Confidence.** Nothing here is unproven: the derivation is a pure function over
a shape this binary already parses, the signal-through-`Outcome` pattern shipped
in [[sp033]] T8, and `KeyLeft` / `KeyRight` are already decoded by
`translateKey` and handled nowhere. No PoC is warranted.
