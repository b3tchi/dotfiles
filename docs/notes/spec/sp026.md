# Spec [[cat001]] [[cat002]] [[board]]

## problem

There is no way to ask how many claude agents are running per project and
in which state. `claude agents --all --json` answers *what agents exist*
but is blind to projects: it is scoped to one `CLAUDE_CONFIG_DIR`
(7 rows under `~/.claude-personal`, 6 under `~/.claude-work` — one
invocation never sees both), and it labels each agent only by `cwd`.
Attribution therefore has to be reconstructed, and today it is
reconstructed by eye, per session, every time.

The missing capability is a **census**: a CLI that joins the agent list
with the tmux pane→project assignment and returns per-project counts
bucketed by state. It is a horizontal capability — the census emits
structured data and does not render it; the rendering consumers come
later and are several.

Two attribution paths exist and both are needed:

- Interactive agents carry a live `pid` whose process parent is the tmux
  `pane_pid`; the pane's `session_group` **is** the project name
  (`dotfiles_0..3` → group `dotfiles`). Verified: agent 788567 → pane
  788390, agent 3290937 → pane 3290465. This path is authoritative.
- Background agents have no pane. Their `cwd` as reported by
  `claude agents --all --json` is already the *origin* project root, not
  the isolation worktree (job `462e7625` runs in
  `.claude/worktrees/zettel-write-skill` yet reports
  `cwd: /home/jan/.dotfiles`), so a `cwd` match against the [[ft001]]
  registry is sound — with one hazard below.

The hazard: [[ft001]]'s `~/.config/project/projects.yaml` does not hold
unique paths. `auctions` and `iac` both point at
`/home/jan/repos/b3tchi/auctions`; `mindtime` and `mindtime-python` both
point at the mindtime solution dir. A `cwd`-only join silently
mis-credits those agents. The tmux path disambiguates them for free
whenever a pane exists; where it does not, the census must refuse to
guess and surface the agents under an `unknown` row carrying the raw
`cwd`, so undercounting is visible rather than invented.

Consumers, none of which should own this join themselves: a quickshell
bar widget ([[cat002]]), the project switcher and `project list` in
[[ft001]] / [[im001]], the tmux status line, and `claude/statusline.sh`.
Each wants the same numbers rendered differently, which is what makes
this a [[ft001]]-consuming feature rather than an extension of it —
[[ft001]] registers and navigates projects, it does not observe what is
running inside them.

Scope decided during brainstorming:

- Source is the supported CLI surface only — `claude agents --all --json`
  run once per account and tagged. The richer
  `~/.claude-*/jobs/*/state.json` and `~/.claude-*/sessions/*.json`
  files were surveyed and rejected: undocumented on-disk format, and the
  sessions registry is 23/26 stale dead pids.
- States normalize to four buckets: `busy`/`working` → working,
  `idle`/`shell` → idle, `waiting`/`blocked`/`failed` → blocked,
  `done` → done. Any state the upstream adds later lands in `other`
  rather than being dropped.
- Surface: `agent-census [--json] [--project <name>] [--detail]`,
  emitting one row per project with the four counts, a total, and an
  account breakdown, plus the `unknown` row.

Binding decisions: [[adr0001]] makes this nushell — structured pipeline
in the workflow-tooling layer that completes and exits; [[adr0002]]
supplies no bash trigger; [[adr0003]] is not met (no listener, no
streaming hot path), so no Go helper.

Deliberately out of scope: no cache, no daemon, no bar widget. Measured
cost is ~600 ms per account, ~600 ms wall when the two account calls run
in parallel, against 4 ms for `tmux list-panes` and 10 ms for `ps`. That
is fine on demand and wrong for a polling bar, so a TTL cache or an
[[adr0012]]-style read-only broadcast (with [[adr0014]] reader-loop
discipline) is a follow-up spec to be written when a real bar consumer
exists — not now.

A new `ft###` is minted at spec-writing time; no existing feature covers
agent observation. Surveyed for duplication: [[ft001]] (registry and
navigation — consumed, not extended), [[ft004]], [[ft005]], [[ft010]]
(daemons with their own state surfaces — none census agents).

## solution

Mint the census as its own capability — [[ft012]] `agent-census` — and
ship it as a single nushell action on `PATH`
(`nushell/actions/agent-census` → `~/.local/bin/agent-census`, the shim
pattern already used by `wm-ipc.nu` and `project-picker`). One exec,
structured output, no rendering: the bar widget, the project picker,
the tmux status line and `claude/statusline.sh` each consume the same
rows and shape them themselves. That is what makes this a feature
rather than an extension of [[ft001]] — the registry answers *which
projects exist*, the census answers *what is running in them*.

Language is settled by decision, not preference. [[adr0001]] puts any
structured-data pipeline in the workflow-tooling layer ([[cat001]]) in
nushell; [[adr0002]] supplies no bash trigger (this is neither
pre-nushell bootstrap, nor the tmux outer shell, nor a sub-50 ms
one-liner); [[adr0003]] is not met, since there is no listener, no
stream proxying and no hot path — the work is a pipeline that completes
and exits. So: nushell action, no Go helper, no daemon.

The join runs in three steps. Both accounts are fetched concurrently
with `par-each` over the two `CLAUDE_CONFIG_DIR` values, each row
tagged with the account it came from — ~600 ms wall instead of ~1.2 s
serial, and correct where a serial single-account call is simply blind.
A pane index is then built once from `tmux list-panes -a -F
"#{pane_pid} #{session_group}"` plus `ps -eo pid=,ppid=` (4 ms and
10 ms — free next to the agent fetch). Finally each agent resolves:
live `pid` → ancestor walk to a `pane_pid` → the pane's
`session_group` is the project; otherwise longest-prefix `cwd` match
against the [[ft001]] registry; tie or miss → the `unknown` row with
the raw `cwd` kept.

The trade-off taken is refusing to guess. [[ft001]]'s registry does not
hold unique paths (`auctions`/`iac`, `mindtime`/`mindtime-python`), so
a `cwd`-only join would silently mis-credit agents while looking
complete. Routing those to `unknown` makes the gap visible and
fixable — a slightly uglier table beats confidently wrong counts, and
the tmux path already resolves the collision whenever a pane exists.
The second trade-off is source discipline: only the supported
`claude agents --all --json` surface is read. The richer
`~/.claude-*/jobs/*/state.json` and `sessions/*.json` were surveyed and
rejected — undocumented on-disk format, and the sessions registry is
23/26 stale dead pids. Reported `cwd` already carries origin-not-
worktree semantics, which was the only thing those files were needed
for.

Deliberately not built here: no cache, no daemon, no bar widget. The
~600 ms cost is fine on demand and wrong for a polling bar, so when a
real bar consumer lands it gets its own spec — a TTL cache, or an
[[adr0012]]-style read-only broadcast under [[adr0014]] reader-loop
discipline ([[cat002]]). Building either now would be speculative.

Attribution and bucketing are covered by tests against captured
fixtures of the three inputs, so the joins are verifiable without live
agents in a given state.
