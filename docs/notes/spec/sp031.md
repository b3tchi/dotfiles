# Spec [[cat001]] [[cat002]] [[board]]

## extends [[ft016]]

## problem
Two gaps showed up the first time [[ft016]] was driven against live agents,
both in what the panes SHOW rather than in what they read. Neither needs a new
data source: the monitor already fetches everything below and discards it at
render time.

**The message log is unreadable for the messages that matter most.** Every row
is one derived line — first line of `content`, or `status — summary` for a
result — truncated to the column width. That is right for a log, and [[sp030]]
T9's tests pin it deliberately so nobody "fixes" the JSON-blob case by parsing
it. But it means a result envelope renders as a single `{` and an instruction
renders as its first eight words, with no way to read the rest. The operator
watching two workers talk can see THAT they talked and not WHAT they said.
`Message.Content` is already carried in full as `json.RawMessage`, so the bytes
are there.

**The roster cannot say which project a row belongs to.** `agent-census`
already returns `project` on every row for both runtimes — the claude rows on
this machine span `asahi`, `copacks`, `dotfiles` and more — and the renderer
drops it. [[sp030]] T8 also parsed a `--project` flag and deliberately
discarded it (`_ = project`) as scaffold for a later task. So a monitor on a
machine running several workspaces blends them together with no way to tell
rows apart or narrow to one.

Both are widenings of the accepted [[ft016]] surface, so this is a feature
refresh rather than a story-backed change: [[sp030]] was a feature-add and
minted no `us###` or `im###`, and nothing here reverses the Feature's
`## providing`. It stays inside [[cat001]] and [[cat002]].

**Delta 1 — a detail pane under the message log.** The message pane gains a
cursor, and a third region shows the selected row in full: a header
(`from → to`, time, kind) plus the body. Selection is new state — today
`Model` carries focus, filter and scroll offsets but no notion of a current
row — so both panes get a cursor and scroll derives from it, keeping `j`/`k`
meaning one thing rather than "move selection" in one pane and "scroll" in the
other. `buildFrame`'s height budget (added post-ship with `dotfiles-m0km`)
becomes three-way so the roster still cannot be pushed off screen.

The body is pretty-printed when the content parses as JSON and rendered raw
when it does not, always neutralised (C0, C1 and DEL, per `dotfiles-r9ty` and
T9's `neutralize`) and wrapped on display cells, never mid-escape. **That is a
bounded exception, and it is worth stating precisely where its boundary is.**
[[ft014]]'s opacity rule binds the TRANSPORT — "it carries any consumer's
vocabulary and gates on none of it" — and `agent-monitor` is a consumer, so
formatting what it displays does not touch that contract. What it does narrow
is [[sp030]]'s own plan anti-pattern, which forbade parsing content to prettify
the SUBJECT COLUMN. That rule stands unchanged: the log column stays
raw-first-line and underived, tested as it is today. Only the detail pane
formats, and a parse failure falls back to raw rather than erroring. No
`subject` field is invented on an envelope, and no [[adr0028]] clause moves.

**Delta 2 — a `PROJECT` column and a live `--project`.** The column joins the
roster in the drop-priority order T8 established, so it sheds on a narrow
terminal like any other. `--project <name>` stops being scaffold and filters on
it.

One ambiguity to record rather than smooth over: for claude rows `project` is
the tmux-pane-to-registry attribution ([[ft012]], [[adr0024]]), while for pi
rows it comes from `parse-pi-window`, which reads the tmux session group
hosting the window. Those are not the same thing. Demonstrated live: two peers
spawned with `pi-worker spawn --project amdemo` displayed as `amdemo` while
messaging on the `dotfiles` bus, because the bus slug follows the repository
and the tmux group follows the display host — exactly the split [[adr0028]]
insists on, surfacing in a column. The column is honest about the display host;
a bus-scope column would be a separate ask and is not in scope here.

Out of scope, deliberately: no `pi-worker` verb changes, no [[ft014]] widening
(`content` already arrives in full), no [[ft012]] widening (`project` already
arrives on every row), and no new `adr####` — nothing here overturns
[[adr0014]], [[adr0017]], [[adr0028]] or [[adr0030]].

Open questions for spec-writing: whether the detail pane is always present or
toggled (a permanent region costs rows on a short terminal); how many rows it
gets from the height budget and whether that is fixed or proportional; whether
the roster's cursor should also drive anything beyond selection, given the
monitor is read-only by [[sp030]]'s decision and `dotfiles-1xfo` already tracks
widening the message filter beyond `From`.

## solution

A render-layer change to [[ft016]] alone. No new `ft###` is minted — this is a
feature refresh declared by `## extends`, so [[ft016]]'s card is rewritten to
match what ships rather than a second Feature being created beside it. Nothing
here reads a new source: `content` already arrives in full from
`pi-worker messages` ([[ft014]]) and `project` already arrives on every census
row ([[ft012]]), so no verb, probe or bus layout moves. Categories [[cat001]]
and [[cat002]] are unchanged.

**Half of delta 2 is not an extension at all.** [[ft016]]'s `## api_surface`
already documents `agent-monitor --project <name>` — "restrict to one project"
— and [[sp030]] T8 parsed that flag and discarded it (`_ = project`) as
scaffold. The card has promised unimplemented behaviour since it was accepted.
Making the flag real closes a card-vs-code gap rather than widening a surface;
the `PROJECT` column beside it is the genuinely new part. Both land together
because a filter with no visible column to filter on is untestable by eye.

**Selection replaces independent scrolling.** Today `Model` carries focus,
filter and two scroll offsets, and `j`/`k` move a viewport. A detail pane needs
a current row, so both panes gain a cursor and the viewport follows it. That
is deliberately a change to [[ft016]]'s documented keys — the card says
"arrows / `jk` scroll the focused pane" and will say the selection moves and
the view follows — declared here so `spec-retro` rewrites the card knowingly
instead of discovering the drift later. Both panes get the cursor rather than
only the message pane: one meaning for one keystroke is worth more than saving
a field, and a roster cursor is the seam any future action would hang from.
The monitor stays read-only per [[sp030]]'s decision, so the roster's cursor
drives selection and nothing else.

**The detail pane is budget-aware, present by default, and toggleable.** It
renders the selected message as a header (`from → to`, time, kind) over a body.
`fitPanes` becomes three-way with a capped share — roughly a third of the
height or eight rows, whichever is smaller — and below a minimum height the
pane hides itself rather than squeezing the other two into uselessness; a key
reclaims the space on demand. The cap exists because `dotfiles-m0km` already
cost one round of this: before the post-ship fix, `buildFrame` had no height
budget at all and a tall frame scrolled the roster off the top while the pane
offsets were applied correctly and invisibly. A third region makes that failure
mode cheaper to reintroduce, so the budget is part of the solution rather than
an implementation detail.

**The body formats JSON, and the boundary is stated rather than assumed.**
[[ft014]]'s opacity rule — "it carries any consumer's vocabulary and gates on
none of it, including the shape of what it carries" — binds the TRANSPORT.
`agent-monitor` is a consumer, and [[adr0028]] governs what tmux may carry, not
what a reader may draw; neither moves here. What this does narrow is
[[sp030]]'s own plan anti-pattern, written for the SUBJECT COLUMN: that column
stays raw-first-line, underived, with T9's tests unchanged, and only the detail
pane pretty-prints. A body that does not parse as JSON renders raw. Both paths
run through the same neutraliser the log already uses (C0, C1 and DEL, per
`dotfiles-r9ty`) and the same display-cell wrapping, never cutting mid-escape —
a detail pane shows strictly more foreign bytes than a truncated column, so
those rules matter more here, not less.

**`--project` filters the roster only.** Messages carry no project field: the
bus is scoped by repository, so every message already in view is in scope.
Stating that asymmetry here stops a later reader filing it as a bug. The column
itself reports what each runtime actually attributes — tmux-pane-to-registry
for claude rows ([[ft012]], [[adr0024]]), and for pi rows the tmux session
group parsed out of the window name, which is the display host and not the bus
slug. That distinction is [[adr0028]]'s split surfacing in a column, and the
card will say so.

Unchanged and explicitly out of scope: [[adr0014]]'s three loop guards (no new
sampler is added — the detail pane reads the sample the message pane already
holds), [[adr0017]]'s observational `unknown`, [[adr0030]]'s wrapper carve-out,
and the read-only stance. `dotfiles-1xfo` (widening the message filter beyond
`From`) stays a separate decision and is not folded in here.

## plan

### file tree

```text
agent-monitor/
  cmd/agent-monitor/main.go        # three-way frame, detail budget, --project wiring
  cmd/agent-monitor/main_test.go
  internal/tui/keys.go             # cursor state, viewport-follow, toggle key
  internal/tui/keys_test.go
  internal/render/roster.go        # PROJECT column
  internal/render/roster_test.go
  internal/render/detail.go        # NEW — the detail pane renderer
  internal/render/detail_test.go   # NEW
docs/notes/ft016.md                # card refresh, written last from shipped reality
```

### conventions

- **The render packages stay pure.** `render.Render`, `RenderLog` and the new
  `RenderDetail` take data plus a width (and, for detail, a height) and return
  `[]string`. They read no clock but the one passed in, touch no terminal, and
  shell out to nothing. Everything that knows about terminals lives in `cmd/`.
- **`cmd/` owns composition, `render/` owns bytes.** [[sp030]] T10 established
  this when it applied scroll by slicing the sample before calling the render
  functions rather than teaching them about scroll. The detail pane follows it:
  `cmd/` picks the selected message, `render.RenderDetail` draws it.
- **Every foreign byte goes through the existing neutraliser.** `neutralize`
  (`internal/render/subject.go:92`) and `truncateCells` (:109) are the shipped,
  mutation-tested implementations for C0/C1/DEL stripping and display-cell
  truncation. The detail pane reuses them; it does not grow its own.
- **Columns are declared, never ad-hoc.** A new roster column is an entry in
  `columnOrder` plus a width in `columnWidth`; `fitColumns` and
  `effectiveWidths` then handle narrow terminals without further thought.
- **Tests prove their own bite.** Every test introduced here that guards a
  behaviour must be shown to fail against the pre-change implementation, the
  way [[sp030]]'s reviewers established — assert the failure, then fix.

### anti-patterns

- **No parsing in the subject column.** The log column stays raw-first-line;
  T9's tests on it are not to be relaxed. JSON formatting is confined to the
  detail body, and a parse failure there renders raw rather than erroring.
- **No new sampler, ticker or goroutine.** The detail pane reads the sample the
  message pane already holds. [[adr0014]]'s three guards are satisfied by not
  adding a fourth loop to guard.
- **No unbounded pane.** Every region takes a row budget; a frame must never
  exceed the terminal height. `dotfiles-m0km` is what that rule costs when it
  is missing — the roster scrolled off and the pane offsets were applied
  correctly and invisibly.
- **No `subject` field invented on an envelope**, and no write of any kind to
  the bus. This spec is read-and-draw only ([[ft014]], [[adr0028]]).
- **No cursor that can point outside its list.** A filter that shrinks a list
  must clamp the cursor in the same pass, not on the next keystroke.
- **No mutating verb.** The monitor stays read-only per [[sp030]]; a roster
  cursor is selection, not a target for `stop`/`accept`.

### known limitations

- `project` for pi rows is the tmux session group parsed from the window name —
  the display host, not the bus slug. A worker spawned with `--project amdemo`
  from a `dotfiles` repo shows `amdemo` while messaging on the `dotfiles` bus.
  The column reports attribution honestly; a bus-scope column is a separate ask.
- The message filter still matches `From` only (`dotfiles-1xfo`), so filtering
  by a recipient hides its messages. Out of scope here.
- The detail pane shows one message. No history navigation beyond moving the
  cursor, and no search within a body.
- Pretty-printing is best-effort: a body that parses as JSON is indented, one
  that does not is shown raw. There is no YAML/TOML/other-format handling.

## tasks

### Task 1: cursor in the model, viewport follows

#### type
feature

#### effort
6h

#### depends
none

#### files_touched
- `agent-monitor/internal/tui/keys.go`
- `agent-monitor/internal/tui/keys_test.go`

#### success_criteria
- `Model` gains a cursor per pane. `j`/`k` and the arrow keys move the cursor
  within the focused pane; the pane's scroll offset is DERIVED so the cursor
  stays visible, rather than being moved directly by those keys.
- The caller reports each pane's visible height per frame (e.g.
  `SetRosterViewport(n)` / `SetMessagesViewport(n)`); scroll is computed from
  cursor plus viewport, so a resized terminal cannot leave the cursor off-screen.
- The cursor is clamped in the same pass that changes a list's length — a
  filter that shrinks the roster leaves the cursor inside the new bounds
  immediately, not after the next keystroke.
- `SetRosterLen` / `SetMessagesLen` keep their existing contract for callers
  that do not care about the cursor; nothing outside `tui` needs to change to
  compile.
- Every existing key test in `keys_test.go` still passes unmodified, including
  the editing-mode gate (`q` while typing a filter is text, not quit).

#### edge_cases
- Empty list: the cursor is a valid no-op, rendering selects nothing, and
  `j`/`k` do not panic or produce a negative index.
- List shorter than the viewport: no scrolling is possible and the cursor may
  still move freely within the rows that exist.
- Viewport of zero or one row (a pathologically short terminal or a collapsed
  pane): scroll math must not divide by, or index past, zero.
- Cursor at either end: `k` at the top and `j` at the bottom are no-ops, never
  a wrap-around and never an out-of-range index.

#### test_plan
- Drive the key table against a model with a known list length and viewport;
  assert cursor position and derived scroll after each keystroke, including the
  two boundary no-ops.
- Shrink the list via a filter with the cursor near the old end; assert the
  cursor is inside the new bounds BEFORE any further keystroke.
- Resize: set a smaller viewport with the cursor low in the list; assert the
  derived scroll brings it back into view.
- Zero-length and zero-viewport cases assert no panic and a sane cursor.
- Run the existing suite unmodified to prove the refactor preserved behaviour.

#### sre
1 granularity 6h, one package. 2 implementability the existing `scroll`,
`SetRosterLen` and `HandleKey` are the functions to change, named above. 3
success criteria five, each mechanically checkable. 4 dependencies none; blocks
Tasks 3 and 5. 5 safety clamp-in-the-same-pass is a stated criterion, and the
anti-pattern list forbids a cursor pointing outside its list. 6 edge cases empty
list, short list, zero viewport, both ends. 7 red flags none. 8 test
meaningfulness the shrink-then-check-before-keystroke case fails against the
obvious implementation that clamps lazily, which is exactly the bug this task
would otherwise ship.

### Task 4: the detail renderer

#### type
feature

#### effort
6h

#### depends
none

#### files_touched
- `agent-monitor/internal/render/detail.go` (new)
- `agent-monitor/internal/render/detail_test.go` (new)

#### success_criteria
- `RenderDetail(msg *source.Message, width, height int) []string` returns a
  header line (`from → to`, time, kind) followed by the body, bounded to
  `height` lines and `width` cells, and is pure — no clock, no terminal, no
  exec.
- A body that parses as JSON is indented for reading; one that does not is
  rendered raw. Parse failure is a fallback, never an error or an empty pane.
- Every line goes through the existing `neutralize` and cell-aware wrapping, so
  no control character, C1 byte or partial escape sequence can reach the
  terminal — the same guarantee [[sp030]] T9 proved for the subject column,
  applied to a pane that shows strictly more foreign bytes.
- A body longer than `height` is truncated with a visible indication that more
  exists, never silently cut.
- Multi-recipient `to` renders as a list, matching the log's existing rule.

#### edge_cases
- A body that is a single 64 KiB line (the envelope cap): bounded by height and
  width without attempting to render it all.
- Content that is valid JSON but deeply nested: indentation must still respect
  the width budget rather than running off the right edge.
- An 8-bit C1 introducer (U+009D) inside a JSON string value: neutralised
  before or after formatting, but certainly before render.
- A nil message (nothing selected, or an empty log): a placeholder line, not a
  panic and not a blank region with no header.

#### test_plan
- Table over the four envelope kinds (`inbox`, `result`, `error`, `identity`)
  asserting header shape and body path for each.
- A JSON body asserts indentation; a non-JSON body asserts raw passthrough; a
  malformed-JSON body asserts the raw fallback rather than an error.
- An ANSI-bearing and a C1-bearing body each assert neutralisation, proven to
  fail against a no-op neutraliser first.
- A CJK body asserts cell-boundary wrapping and that no line exceeds width.
- An over-long body asserts the truncation indicator is present.
- A nil message asserts the placeholder, not a panic.

#### sre
1 granularity 6h, one new file plus its tests. 2 implementability `neutralize`
and `truncateCells` are named with their file and line; the four envelope kinds
come from [[ft014]]'s data model as corrected by `dotfiles-9oa4`. 3 success
criteria five, each asserted. 4 dependencies none; blocks Task 5. 5 safety this
is the task where foreign bytes reach the terminal in bulk; neutralisation is a
success criterion and a test, not a convention. 6 edge cases 64 KiB line, deep
nesting, C1 inside JSON, nil. 7 red flags none. 8 test meaningfulness the
neutralisation cases are proven against a no-op first, and the malformed-JSON
case fails against an implementation that errors instead of falling back.
