# Spec [[cat002]] [[board]]

## problem

The Nothing Phone's cameras only work through libcamera's `simple`
pipeline (software ISP); there is no V4L2 node Qt Multimedia's own
`Camera` could open, and plasma-camera (which links libcamera itself)
drags in Kirigami/KF6. Today the phone's photo flow
(`camera/phone-cam`, Alt+f, hotkeyd's `camera` layer) runs a
`gst-launch-1.0 libcamerasrc ! waylandsink` window: it has to be tiled
around by a kwi3 rule, cannot be styled, and is not reachable from QML
at all. The ask is a **camera backend any QML can use**: streamed
straight into a quickshell overlay, and equally inside a standard
standalone QML app.

Capability boundary (v1, agreed): list cameras, pick one (default: first
back camera), live frames into a QML `VideoOutput`, the sensor's
rotation exposed, full-resolution still capture to a JPEG path, and the
last capture onto the clipboard as image/png. No exposure/AE/resolution
controls, no video recording (later, separate scope).

Approach (chosen over a Go daemon / Rust options after review): a C++
Qt6 QML module, `import LibCamera`, talking to libcamera directly and
pushing frames into a `QVideoSink` (Qt Multimedia used for display
only; `qt6-qtmultimedia-dev` is already on the phone, `libcamera-dev`
is the one new package). Its own private repo (like radio / kwi3),
cloned and built on the phone by the `camera` dot into
`~/.local/lib/qml`; the repo also ships a minimal standalone app
(`qml6 app/main.qml`, preview + shutter).

Consumers:
- the phone's quickshell `CameraOverlay.qml` (layer-shell panel between
  the top and the bar's hint strip), opened/snapped/closed over
  quickshell IPC by hotkeyd's `camera` layer — the global hotkey layer
  [[ft011]], whose hint strip is the mode bar [[ft009]];
- the standalone QML app in the module's repo;
- captures land in the shared clipboard history [[ft007]] (Alt+v keeps
  only image/png).

Dedup: no existing feature covers a camera; the file-preview daemon
[[ft005]] renders video *files*, a different capability. No `im###`
records the current phone-cam flow, so there is no migration card;
the migration is the code itself: delete `camera/phone-cam`, the kwi3
`gst-launch-1.0` rule and the dot's gstreamer packages, and point the
camera layer's actions at the overlay's IPC. Keep the layer, the hint
strip and the ownership-count fix.

Constraints: category [[cat002]] (display-platform). hotkeyd's external
control stays compile-time declared [[adr0022]]; the `camera` layer's
divergence from the python golden dump is already declared in code
[[adr0023]]; any respawning reader loop (overlay ↔ module) fails fast
and is rate-bounded [[adr0014]]. Risks: libcamera's rotation=90 vs the
counter-clockwise flip found on the device (module exposes rotation,
QML applies it); mapping the simple pipeline's output format into a
`QVideoFrame`.

Intent: mint a new `ft###` (libcamera QML camera source) at
spec-writing.

## solution

Feature-add: the deliverable is [[ft019]] (libcamera QML camera source),
category [[cat002]]. A C++ Qt6 QML module, `import LibCamera`, opens the
camera through libcamera directly (so the `simple` pipeline's GPU/soft
ISP runs inside libcamera, as `cam` and `libcamerasrc` already prove on
this phone) and maps each completed request's buffer into a
`QVideoFrame` pushed to a `QVideoSink`; Qt Multimedia is used for
display only (`VideoOutput`), never its camera backend. Still capture
saves the newest preview frame (stream size, narrowed at refinement) as JPEG; the clipboard copy is
image/png so the shared clipboard history [[ft007]] keeps it. Built as
a shared QML plugin from its own private repo by the `camera` dot into
`~/.local/lib/qml` (one new package, `libcamera-dev`), with a minimal
standalone `qml6` app in the same repo as the second consumer.

On the phone, quickshell's `CameraOverlay.qml` hosts the `CameraSource`
in a layer-shell panel between the top and the mode bar's hint strip
[[ft009]]; hotkeyd's `camera` layer [[ft011]] drives it over quickshell
IPC (open / snap / close) instead of spawning `phone-cam`. The layer
itself, its hint strip and its post-python declaration [[adr0023]] stay
as built; no new external-control layer is added, so [[adr0022]] is
untouched. The overlay never restarts the module in a loop: a failed
open surfaces `error` and stops [[adr0014]]. Removed: `camera/phone-cam`,
the kwi3 `gst-launch-1.0` window rule and the dot's gstreamer packages.

Trade-offs taken: C++ over Go/Rust (no maintained Go libcamera binding;
Rust's cxx-qt cannot yet ship a plugin quickshell can load without C++
glue) in exchange for zero-copy-ish, low-latency preview; a module, not
an app, so UI stays per consumer. Unproven: libcamera's buffer format
from the simple pipeline mapping cleanly into a `QVideoFrame`, and the
plugin loading inside quickshell — the confidence gate below.

Confidence gate: **validated** by [[poc025]] (2026-11-22). A ~120-line
plugin streamed the back camera at ~31 fps in qml6 and ~32 fps inside
quickshell, real colours, upright at `VideoOutput.orientation: 270`.
Carry forward: build with `QT_NO_KEYWORDS` (libcamera's headers clash
with Qt's `signals`/`emit`); libcamera's ABGR8888 is Qt
`Format_RGBA8888` with no conversion; expose the display rotation as
`(360 - sensorRotation) % 360`.

### conventions
- Module installs to `~/.local/lib/qml/LibCamera` (qmldir, plugin .so,
  .qmltypes); consumers find it through `QML_IMPORT_PATH`.
- Build with `QT_NO_KEYWORDS` (libcamera's `signals`/`emit` clash, [[poc025]]):
  use `Q_SIGNALS` / `Q_EMIT` only.
- libcamera callbacks run on libcamera's thread: copy the frame there,
  touch QObjects only on the GUI thread (queued `invokeMethod`).
- `rotation` is the DISPLAY rotation, `(360 - sensorRotation) % 360`
  (sensor 90 -> 270, measured in [[poc025]]); consumers set
  `VideoOutput.orientation: cam.rotation`.
- Captures: `~/Pictures/camera/YYYYmmdd-HHMMSS.jpg`, JPEG quality 92.
- Clipboard: `wl-copy --type image/png` when `WAYLAND_DISPLAY` is set
  (an overlay has no keyboard focus, so `QClipboard` cannot own the
  selection on Wayland); `QClipboard` otherwise.

### anti-patterns
- No QObject access or signal emission from `requestCompleted` directly.
- No retry loop opening the camera: a failed open sets `error`, stops,
  and the overlay shows it ([[adr0014]]).
- No external `set-layer` for `camera`: it stays a chord layer, so
  [[adr0022]]'s compile-time external set is untouched; the overlay only
  ever sends `set-layer default`.
- No `unwrap`-style ignoring of libcamera return codes: every
  `configure/allocate/start/queueRequest` result is checked and mapped
  to `error`.
- No gstreamer anywhere in the new path.

### known limitations
- Capture saves the newest preview frame at stream size (1280x720), not
  a separate full-sensor still (needs a StillCapture stream; later).
- No colour tuning for s5kjn1 (libcamera uses `uncalibrated.yaml`).
- One CPU copy per frame (dmabuf zero-copy is an optimisation).
- Module tests that need the sensor run on the phone only (smoke.qml).

### Task 1: CameraSource streaming core
#### type
feature
#### effort
6h
#### depends
none
#### files_touched
libcamera-qml: CMakeLists.txt, src/camerasource.h, src/camerasource.cpp,
src/frameutil.h, src/frameutil.cpp, tests/tst_frameutil.cpp, README.md
(new private GitHub repo `b3tchi/libcamera-qml`, created with `gh repo
create --private`)
#### success_criteria
- `import LibCamera 1.0` exposes `CameraSource` with `cameras`,
  `cameraId`, `active`, `videoSink`, `size`, `rotation`, `error` exactly as
  [[ft019]] `## api_surface`.
- `cameras` lists both phone cameras with `facing` back/front and
  sensor rotation; `cameraId: ""` picks the first back camera (`camera@2d`).
- `active: true` streams 1280x720 RGBA frames into the sink; `active:
  false` stops and releases the camera (a second `active: true` works).
- `rotation` reads 270 for the back camera.
- `ctest` passes `tst_frameutil` with no camera present.
#### edge_cases
- No cameras (CameraManager empty) -> `error: "no camera"`, `active`
  stays settable, no crash.
- Unknown `cameraId` -> `error`, nothing opened.
- Camera busy (another process holds it, e.g. `cam` running) ->
  `acquire` fails -> `error: "camera busy"`.
- `videoSink` null or changed while streaming -> frames dropped, no crash.
- Object destroyed while streaming -> destructor stops and releases.
- Stride != width*4 -> rows copied by stride (copyRows).
#### test_plan
tst_frameutil: `pickCamera` (empty list -> none; "" -> first back;
explicit id; unknown id -> none), `displayRotation` (0->0, 90->270,
180->180, 270->90), `toVideoFormat` (ABGR8888 -> Format_RGBA8888,
unsupported -> Invalid), `copyRows` (padded stride copies only width*4
per row, verified byte-for-byte on a synthetic buffer).
