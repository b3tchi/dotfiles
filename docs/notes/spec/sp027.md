# Spec [[cat001]] [[board]]

## problem

Infinifu's lifecycle skills should run unchanged in both Claude Code and Pi.
Today the knowledge and task layers are already runtime-neutral: `akm` owns
AKM reads and writes, `bd` owns task state and dependencies, and Git owns
source branches and worktrees. The execution layer is not neutral because
orchestration skills directly assume Claude-native agent tools, messaging,
completion notifications, and resume semantics.

This capability will make one canonical set of Infinifu skills select a thin
runtime adapter while preserving existing Claude Code behavior. Under Pi, the
same idea, spec, refinement, ready, supervised work, audit, merge, and retro
stages must continue to use `akm` and `bd`; they must not fork the lifecycle or
duplicate zettels. The primary consumers are the `idea-*`, `spec-*`,
`plan-supervised`, `work-do`, `work-audit`, `work-merge`, and `spec-retro`
skill chains.

No existing Feature duplicates lifecycle runtime portability. [[ft004]]
provides AKM graph visualization, while [[ft012]] provides a Claude-specific
agent census. Their consumers [[im004]] and [[im011]] confirm that those
capabilities solve different problems rather than providing an agent-runtime
adapter. [[adr0024]] and [[adr0025]] deliberately define running-agent and
census semantics around Claude's supported CLI; this work must preserve those
boundaries instead of silently treating them as portable abstractions.

The deliverable is intended to mint a new Feature for runtime-neutral
Infinifu lifecycle execution in [[cat001]]. Runtime detection must be explicit:
Pi selects the Pi adapter, availability of Claude's native agent surface
selects the Claude adapter, and unsupported runtimes fail clearly rather than
falling through. This is phase one and must be useful independently of
multi-agent Pi orchestration.

## solution

Provide [[ft013]] as the single runtime-neutral contract for Infinifu's
lifecycle skills in [[cat001]]. The canonical skills keep their current names
and continue to use `akm`, `bd`, and Git as the only durable AKM, task, and
source interfaces. Context delivery is stage-specific. Idea, spec, and other
AKM stages receive direct instructions and resolve referenced AKM documents
through `akm`. A `work-*` subagent receives only its bd ticket ID as
direct work content and resolves the contract with `bd show <id>`. Direct
messaging remains the primary control channel in both cases.
Runtime-dependent behavior moves behind explicit branches:
`AI_AGENT=pi` selects Pi behavior, availability of Claude's native agent
surface selects Claude behavior, and an unknown runtime fails closed. Claude's
existing native path remains unchanged; Pi gains the sequential lifecycle in
this spec and delegates visible multi-worker orchestration to [[sp028]].

[[ft004]] and [[ft012]] remain surveyed non-duplicates rather than
dependencies: graph visualization and agent census are separate capabilities.
The adapter does not generalize the Claude-specific running-agent semantics in
[[adr0024]] or supported-surface boundary in [[adr0025]]. This keeps one
lifecycle source instead of a Pi-specific skill fork, at the cost of small,
explicit runtime branches in the affected skills.
