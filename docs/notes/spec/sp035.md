# Spec [[cat001]] [[cat002]] [[board]]

## extends
[[ft016]]

## problem
[[sp034]] shipped the threaded message pane and got one thing visibly wrong the
moment a thread is UNFOLDED: the newest message renders twice — once as the
thread row's own summary (`TIME` + `SUBJECT` come from the newest member) and
again as the first child, because children are the thread's full membership in
newest-first order. Collapsed is correct; only the expanded state repeats
itself. Nothing caught it, because the two halves were specified in different
tasks — [[sp034]] `### Task 3` gave the thread row the newest member's subject,
`### Task 2` gave the fold every member, and neither task's criteria mention
the other's rows.

Operator's call on the shape: the thread row KEEPS its summary and the fold
starts at the SECOND-newest. The count column keeps reporting the thread's
total message count, so an expanded thread of `N` shows `N-1` children — the
count stays a property of the conversation rather than of the rows currently
on screen.

That inverts one shipped assertion on purpose:
`TestThreadRows_OneMessageThreadExpandedIsNotNoOp` ([[sp034]] Task 2) pinned a
single-message thread expanding to exactly one child. Under this change such a
thread has nothing beneath it at all, so it becomes NOT EXPANDABLE: a thread
with `Count == 1` renders a blank glyph cell and ignores expand/collapse/toggle.
The chevron then means "there is something under here", which is the only
honest reading once the newest member lives on the thread row. The inverted
test is rewritten to assert the new contract, not deleted.

Second, unrelated in mechanism and related in symptom: two threads whose
participants wear the SAME labels are indistinguishable on screen. On the live
bus today, `claude-main <> jan` appears twice —
`a01M2TB0H5X9…|a01M2TB0H7FW…` and `a01M2TEEMKNC…|a01M2XG66ZAC…` — four distinct
addresses, because every `pi-worker register` mints a fresh, never-reused one
([[adr0034]]), so a re-registered session is a new party wearing an old label.
`jan <> rev-1` likewise appears twice for two different reviewer sessions. The
GROUPING is right and must not change: keying on labels is exactly what
[[adr0034]] refuses, and it would merge those two genuinely separate `rev-1`
sessions into one thread.

The fix belongs in the DETAIL pane, not the log — decided explicitly, because
the message pane's scarcest resource is width and a per-row disambiguator
spends it on every row to serve the rare collision. `detail.go`'s header
(`detail.go:67`) renders LABELS only —
`fmt.Sprintf("%s → %s   %s   %s", orDash(msg.From), toCell(msg.To), …)` — so
selecting either `claude-main <> jan` thread yields an identical detail header
too, and a resolved party's ADDRESS is currently rendered nowhere in the
product. The detail pane gains `FromAddress` / `ToAddresses` alongside the
labels, which is also the view an operator copies an address from.

That last point corrects a false claim in [[ft016]] itself: `shortAddress`'s
doc comment says "The full address is in the detail pane (detail.go), which is
the view an operator copies from." It holds only when the registry FAILED to
resolve, because then `From`/`To` literally carry the address. For a resolved
party it is simply untrue today. [[sp034]]'s own retro did not catch it.

Constraints:

- Feature-refresh on the accepted [[ft016]], exactly as [[sp034]] was: no
  `us###`, no `im###`, no new `ft###`. The finale archives the spec without
  flipping [[ft016]]'s status.
- The thread KEY, the address-based grouping and the participant labels in the
  log are untouched ([[adr0034]]).
- Reader-side only: no envelope field is added ([[adr0028]]) and no `content`
  is parsed that is not parsed today ([[adr0031]]).
- `--once` stays FLAT and byte-identical; [[sp030]] T9's pipe contract and the
  suite's `0x1b` check both still bind.
- `tui.Model` stays comparable; the expansion set stays in `cmd/`.
- Any binding whose behaviour changes (expand/collapse/toggle now no-op on a
  one-message thread) needs a real `tea.KeyMsg` test ([[adr0036]]).

Not in scope, tracked separately and deliberately not folded in here:
`dotfiles-i1sw` (`render.Threads` re-sorts by the `At` string while
`orderedMessages` orders by id — a second reorder observable under clock skew)
and `dotfiles-br55` (`FROM`/`TO`/`PARTICIPANTS` label cells bypass the
neutraliser `content` passes through). Both are defects in shipped code with
their own bd issues; this spec is a display-shape change and mixing them would
blur what its tests are proving.

## solution
A second feature-refresh of [[ft016]], the same shape [[sp034]] took: the spec
declares `## extends [[ft016]]`, `work-merge` archives it without flipping the
Feature's `accepted` status, and `spec-retro` rewrites [[ft016]]'s body to the
shipped surface. No `ft###` is minted, no `us###` or `im###` is invented, and
neither [[ft012]] nor [[ft014]] is touched — this changes what the reader
DISPLAYS and nothing about what the bus carries ([[adr0028]], [[adr0031]]).

**The fold starts at the second-newest, and one predicate decides
expandability.** `ThreadRows` emits children from the thread's membership
MINUS its newest member, which the thread row already shows. The count column
keeps reporting the conversation's total, so an expanded thread of `N` renders
one summary row and `N-1` children — the number stays a property of the
conversation rather than of the rows currently on screen, which is what makes
it stable across expanding and collapsing.

A thread of one therefore has nothing beneath it and becomes NOT EXPANDABLE.
That is a rule two different layers would otherwise each decide for
themselves — the renderer choosing whether to draw a chevron, and the shell
choosing whether to mutate the expansion set — and [[sp034]] already paid for
exactly that mistake once: its Task 6 audit found `renderFrame` and
`currentThreadsAndRows` reading `Threaded` independently and disagreeing at
height 0, one cursor over two lists. So expandability is derived ONCE, in
`ThreadRows`, and carried on `LogRow`; the glyph cell renders from it and the
shell consults it before touching the set. One authority, by construction
rather than by discipline.

**The detail pane gains the addresses.** `detail.go`'s header renders labels
only, so today two threads whose participants share labels are
indistinguishable there as well as in the log — and a RESOLVED party's address
is rendered nowhere in the product. The pane gains the envelope's own
`FromAddress` and `ToAddresses` ([[sp033]] T1's fields, never re-resolved from
a label per [[adr0034]]) alongside the labels it already shows, wrapped by the
same cell-aware helper the body uses and passing the same neutraliser. This is
the view an operator copies an address from, which is precisely what
`shortAddress`'s doc comment in [[ft016]] already claims and which is true
only for an UNRESOLVED address today; `spec-retro` corrects that sentence.

The message pane's `PARTICIPANTS` column is deliberately NOT touched. A
per-row disambiguator spends the pane's scarcest resource — width — on every
row to serve the rare collision, and the collision is legible the moment the
operator opens the row they are already looking at.

**What must not move.** Thread keys, the address-based grouping and the
participant labels in the log are unchanged ([[adr0034]]); collapsed rendering
is byte-identical to what [[sp034]] shipped; `--once` stays FLAT and
byte-identical, keeping [[sp030]] T9's pipe contract and the suite's `0x1b`
check; `tui.Model` stays comparable with the expansion set in `cmd/`; and the
expand/collapse/toggle bindings, whose behaviour now changes on a one-message
thread, each keep a real `tea.KeyMsg` test ([[adr0036]]).

One shipped assertion inverts on purpose.
`TestThreadRows_OneMessageThreadExpandedIsNotNoOp` ([[sp034]] Task 2) pinned
the behaviour this spec removes. It is REWRITTEN to assert the new contract —
a one-message thread reports itself non-expandable and the set is never
mutated for it — never deleted. A deleted test is how an inversion becomes an
accident nobody can date later.

Categories [[cat001]] and [[cat002]], unchanged from [[ft016]]. No ADR is
overturned and none is minted: nothing strategic shifts, and both changes sit
inside decisions [[adr0034]], [[adr0028]], [[adr0031]] and [[adr0036]] already
govern.

**Confidence.** Nothing here is unproven. Both changes are local edits to code
that shipped and is under test: the children slice is one expression in a pure
function [[sp034]] Task 2 already covers, the `Expandable` flag follows the
single-predicate pattern that spec's Task 6 landed under audit, and the detail
header is an additional line in a renderer that already wraps and neutralises.
No PoC is warranted.

## plan

### file tree

```text
agent-monitor/
  internal/render/
    thread.go        LogRow gains Expandable; ThreadRows emits children from Messages[1:]
    thread_test.go   the inverted sp034 test REWRITTEN, not deleted
    log.go           glyph cell reads Expandable
    log_test.go
    detail.go        header gains from_address / to_addresses
    detail_test.go
  cmd/agent-monitor/
    main.go          applyThreadOutcome refuses a non-expandable thread
    main_test.go
tests/agent-monitor/run-tests.nu   suite entry point, unchanged
```

### conventions

- **Expandability is derived ONCE**, in `ThreadRows`, and carried on `LogRow`
  beside `Count` and `Expanded` — on the thread row and on every child row of
  that thread, exactly as `Count` already is. The renderer reads it for the
  glyph; `cmd/`'s `applyThreadOutcome` reads it before touching the expansion
  set. Neither recomputes `Count > 1` for itself.
- **`Count` stays the CONVERSATION's total**, never the number of rows on
  screen. An expanded thread of 3 renders one summary row, two children, and a
  count cell reading `3`.
- The thread row keeps rendering the newest member's `TIME` and `SUBJECT`;
  only the CHILD list changes.
- Detail addresses render through the same `neutralize` + cell-aware wrapping
  the body already uses, and come from the envelope's own `FromAddress` /
  `ToAddresses` — never re-resolved from a label ([[adr0034]]).

### anti-patterns

- **Do not let the renderer and the shell each decide expandability.**
  [[sp034]] Task 6's audit found `renderFrame` and `currentThreadsAndRows`
  reading `Threaded` independently and disagreeing at height 0 — one cursor
  over two lists. `Count > 1` must not be spelled twice.
- **Do not delete `TestThreadRows_OneMessageThreadExpandedIsNotNoOp`.** Rewrite
  it to the new contract. A deleted test is how an inversion becomes an
  accident nobody can date later.
- **Do not make `Count` mean "children".** Two numbers that agree today and
  diverge under expansion is the bug this spec exists to remove, not to move.
- **Do not touch the thread KEY, the grouping, or the log's `PARTICIPANTS`
  cell.** Disambiguation is the detail pane's job here, by decision.
- **Do not elide the detail pane's addresses.** `shortAddress` exists for the
  LOG's width budget; the detail pane is the view an operator COPIES from, so
  it carries the full 27-character address.
- **Do not add a field to an envelope or parse `content`** ([[adr0028]],
  [[adr0031]]).

### known limitations

- Collapsed rendering is byte-identical to what [[sp034]] shipped **with one
  deliberate exception**: a one-message thread's glyph cell is now blank where
  it previously carried `>`. The column still occupies its cell, so the grid
  does not shift. This is the visible half of "not expandable" and is asserted
  rather than discovered.
- The detail pane grows by one line for every message. On the smallest budget
  the pane already truncates its body with a visible indicator; an address
  line consumes one row of that budget.
- Two threads whose participants share labels remain indistinguishable IN THE
  LOG. That is the accepted trade — the operator disambiguates by selecting
  the row, which is where the addresses now are.

## tasks

### Task 1: Fold from the second-newest, and derive expandability once

#### type
feature

#### effort
4h

#### depends
none

#### files_touched
- `agent-monitor/internal/render/thread.go`
- `agent-monitor/internal/render/thread_test.go`

#### success_criteria
- `ThreadRows` emits, for an expanded thread, one `KindThread` row followed by
  one `KindMessage` row per member EXCEPT the newest (`Messages[1:]`), in the
  thread's existing newest-first order. A thread of `N` yields `N-1` children.
- `LogRow` gains `Expandable bool`, set from `Count > 1` and carried on the
  thread row AND every child row of that thread, exactly as `Count` is. It is
  computed in this one function and nowhere else.
- `expanded(key)` returning true for a `Count == 1` thread produces NO child
  rows — the predicate cannot override expandability.
- Collapsed output is otherwise unchanged: same thread rows, same `Count`,
  same order, same `Message` (the newest) on each thread row.

#### edge_cases
- A one-message thread: one row, `Expandable` false, zero children whether or
  not its key is in the expansion set.
- A two-message thread expanded: exactly one child, and it is the OLDER
  message — not the newest repeated.
- A thread whose `Messages` is empty cannot occur from `Threads()`, but the
  existing length guard stays so `ThreadRows` cannot panic on a hand-built
  `Thread{}`.
- `Count` on child rows still reads the thread total, not `len(children)`.
- Determinism unchanged: same `(threads, expanded)` yields a byte-identical
  slice.

#### test_plan
- `TestThreadRows_ExpandedOmitsTheNewestMember` — three-message thread
  expanded; asserts the exact row sequence and that the newest message's id
  appears exactly ONCE across all rendered rows. The "exactly once" assertion
  is the one that fails on today's code.
- `TestThreadRows_OneMessageThreadIsNotExpandable` — the REWRITE of
  `TestThreadRows_OneMessageThreadExpandedIsNotNoOp`. Same name-adjacent
  scenario, inverted contract: `Expandable` false and zero children even with
  the key expanded. A comment cites [[sp035]] as the inversion's origin.
- `TestThreadRows_ExpandableIsCarriedOnChildRows` — asserts every child row
  carries `Expandable` true, so the shell can read it off whichever row the
  cursor sits on.
- `TestThreadRows_CountStaysTheConversationTotal` — expanded `N=3`, asserts
  `Count == 3` on all three rows while only 2 children exist.
- `TestThreadRows_CollapsedUnchanged` — collapsed output for a mixed fixture
  asserted against the pre-change expectation.

### Task 2: Honour expandability in the glyph and in the shell

#### type
feature

#### effort
5h

#### depends
Task 1

#### files_touched
- `agent-monitor/internal/render/log.go`
- `agent-monitor/internal/render/log_test.go`
- `agent-monitor/cmd/agent-monitor/main.go`
- `agent-monitor/cmd/agent-monitor/main_test.go`

#### success_criteria
- `threadGlyphCell` renders a BLANK cell (not `>`, not `v`) on a thread row
  whose `Expandable` is false, and is otherwise unchanged: `v` expanded, `>`
  collapsed, blank on child rows. The cell keeps its width, so the grid does
  not shift.
- `applyThreadOutcome` returns without mutating the expansion set when the row
  under the cursor has `Expandable` false — for expand, collapse AND toggle.
- Both read `LogRow.Expandable`; neither computes `Count > 1` itself. A grep
  for `Count > 1` (or `Count >= 2`) outside `ThreadRows` finds nothing.
- Every other binding and the cursor-restore behaviour are unchanged: a
  collapse from a child row still resolves to that child's thread and leaves
  the cursor on the thread row ([[sp034]] Task 6's carried-forward gate).

#### edge_cases
- Expand pressed on a one-message thread: no set mutation, no cursor move, no
  frame change — a true no-op, asserted as such rather than assumed.
- A stale key for a now-one-message thread already in the set stays inert:
  `ThreadRows` emits no children for it regardless.
- The glyph column is never dropped at any width, so the blank cell is visible
  at every terminal size ([[sp034]] Task 3's rule).
- A thread that grows from one message to two becomes expandable on the next
  sample with no keystroke.
- `--once` renders flat, so no glyph is emitted at all.

#### test_plan
- `TestRenderThreadRow_OneMessageThreadHasNoGlyph` — asserts a blank cell at
  the glyph index AND that the `SUBJECT` column still starts at the same
  computed index as on an expandable row (grid did not shift).
- `TestShell_ExpandOnOneMessageThreadIsANoOp` — real `tea.KeyMsg`; asserts the
  expansion map is unchanged, the cursor is unchanged, and the rendered frame
  is byte-identical before and after.
- `TestShell_ToggleOnOneMessageThreadIsANoOp` — the toggle path specifically,
  since `s.expansion[key] = !s.expansion[key]` would otherwise CREATE the key.
- `TestShell_CollapseFromChildRowStillTargetsItsThread` — the [[sp034]]
  carried-forward gate re-asserted against the new row shape.
- `TestNoSecondExpandabilityDerivation` — scans the non-test sources for a
  `Count > 1` style comparison outside `thread.go`; fails if a second
  derivation appears. This is the `## plan` anti-pattern made executable.

### Task 3: Detail pane carries the participants' addresses

#### type
feature

#### effort
4h

#### depends
none

#### files_touched
- `agent-monitor/internal/render/detail.go`
- `agent-monitor/internal/render/detail_test.go`

#### success_criteria
- The detail pane renders the selected envelope's `FromAddress` and every entry
  of `ToAddresses`, in full (27 characters, never elided by `shortAddress`),
  alongside the labels the header already shows.
- The addresses come from the envelope's own fields and are never re-derived
  from a label ([[adr0034]]); an envelope carrying empty address fields (a
  pre-[[sp033]]-T1 payload) renders the existing header with no address line
  rather than an empty one or a dash-filled placeholder.
- Address text passes through the same `neutralize` and cell-aware wrapping the
  body uses; no line exceeds the pane width at any width.
- Two envelopes whose labels are identical but whose addresses differ produce
  DIFFERENT detail output — the property this task exists for.

#### edge_cases
- A multi-recipient envelope renders every recipient address, never only the
  first.
- A narrow pane wraps an address across lines by display cells rather than
  truncating it into something un-copyable — or truncates with the existing
  visible indicator; whichever, the choice is asserted, not incidental.
- An envelope with `FromAddress` set and `ToAddresses` empty renders the
  from-address alone.
- The detail pane's height budget already truncates; the address line is
  subject to the same budget and must not push the body out silently.
- A hostile address-shaped string carrying C0 bytes is neutralised like any
  other cell.

#### test_plan
- `TestRenderDetail_ShowsFullAddresses` — asserts both the from-address and
  every to-address appear in full; a fixture whose addresses share their first
  eleven characters (same-millisecond ULIDs), so a head-truncating
  implementation fails.
- `TestRenderDetail_SameLabelsDifferentAddressesDiffer` — two envelopes,
  identical `From`/`To` labels, different addresses; asserts the rendered
  output differs. This is the live `claude-main <> jan` case.
- `TestRenderDetail_AddresslessEnvelopeRendersNoAddressLine` — pre-T1 payload;
  asserts the header is intact and no empty or dash-filled line appears.
- `TestRenderDetail_AddressLineNeutralisedAndWidthBounded` — C0 bytes in an
  address field; asserts no `0x1b` and no line over width at 20/40/80 cells.
- `TestRenderDetail_MultiRecipientShowsEveryAddress`.
