# Spec [[cat001]] [[board]]

## problem

Pi needs visible multi-agent execution for the Infinifu pipeline without
replacing Claude Code's native agent orchestration. The current
`plan-scrum-master` assumes Claude-native spawn, message, list, stop,
completion, and transcript-resume operations. Pi intentionally does not
provide built-in subagents, so merely loading the skill cannot execute the
full implementer-to-reviewer-to-merge pipeline.

The capability will provide a Pi runtime adapter that launches named Pi workers
as windows in the existing linked tmux project group. A worker window is shown
as `<worker-name>@<project>`, for example
`impl-dotfiles-7opn.1@dotfiles`; it is not a separate tmux session. Each worker
uses an isolated `bd-<id>.<N>` worktree, a stable Pi session ID, and a stable
worker-bus identity. `bd` remains authoritative for status and evidence, `akm`
remains
authoritative for lifecycle artifacts, Git remains authoritative for source,
and Pi JSONL remains authoritative for conversation history.

[[im002]] is the existing tmux dispatch shape to reuse rather than bypass,
while [[ft001]] supplies existing project identity conventions. [[ft012]] and
its consumer [[im011]] remain Claude-specific census behavior. In particular,
[[adr0024]] and [[adr0025]] prevent this adapter from pretending that Claude
agent records describe Pi workers; Pi worker liveness comes from process
state, `bd`, and bus-owned envelopes.

The deliverable is intended to mint a separate Feature for visible Pi worker
orchestration in [[cat001]]. Worker windows remain visible through completion
so the user can inspect detail. Rejection resumes the stored Pi transcript.
Explicit acceptance, including successful task merge, closes the owned windows
and cleans the worktree while retaining the Pi session ID and evidence.
Completion returns through the CLI message bus; `agent-inbox` remains the
channel for human decisions rather than hidden orchestration state. Claude Code
continues using its native agent path without behavioral regression.

## solution

Provide [[ft014]] as the Pi worker-orchestration adapter layered on the shared
lifecycle contract in [[ft013]] and categorized under [[cat001]]. The Pi branch
of `plan-scrum-master` invokes a worker CLI to create named windows in the
existing linked tmux project group and launch stable Pi sessions in isolated
`bd-<id>.<N>` worktrees. Addressed communication uses an `infinifu-worker` CLI
message bus. A Pi extension watches each worker inbox, injects messages through
`pi.sendUserMessage()`, and exposes a typed result tool that atomically writes
a compact outbox envelope. Tmux remains only the display and process
host; it never carries prompts, completion messages, or coordination state.

For `work-do`, `work-audit`, and `work-merge`, direct work content is only the
bd ticket ID. The worker reads its contract via `bd show <id>` and inspects
dependencies and linked specs; the orchestrator does not copy or summarize the
task body. Role, skill, session, and worktree are trusted transport
configuration injected by the extension. Non-work stages receive direct stage
instructions and artifact IDs, then resolve AKM documents through `akm`.
Completed windows remain visible for optional inspection. Explicit acceptance
or successful merge cleanup closes them while retaining the Pi transcript and
exact resume command.

The adapter reuses the linked-project tmux shape recorded by [[im002]] and
project conventions from [[ft001]], while Claude Code continues using native
agents. It does not fold Pi workers into the Claude-only census capability
[[ft012]] or its consumer [[im011]], preserving [[adr0024]] and [[adr0025]].
[[poc022]] validates linked-window visibility, stable Pi resume, and scoped
cleanup on Pi 0.84.4. Its tmux signalling experiment is feasibility evidence
only; the production message path is the CLI bus defined here.

### Conventions

- Worker UID is `<role>-<task-or-artifact>-<run-id-short>`; tmux displays
  `<role>-<task-or-artifact>@<project>`.
- The CLI bus owns versioned, sequenced JSON inbox and outbox envelopes under
  `$XDG_RUNTIME_DIR/infinifu-worker/<run-id>/<worker-uid>/`.
- The Pi extension watches the inbox and calls `pi.sendUserMessage()` with
  `steer` or `followUp` delivery according to current agent state.
- Role and skill are trusted extension configuration. For `work-*`, the user
  message body remains exactly the bd task ID; non-work stages receive direct
  stage instructions plus artifact IDs.
- Workers finish through a typed result tool. The initiator receives the compact
  envelope from `infinifu-worker wait`, while detail stays in tmux and
  Pi JSONL.
- Tmux owns only window/process visibility and termination. It is not a
  message, signal, status, or durable-state channel.

### State and safety

- Bus directories use mode `0700`; envelopes use `0600` and atomic rename.
  Envelopes are limited to 64 KiB and completion summaries to 4 KiB.
- Every envelope includes protocol version, sequence, run ID, worker UID, kind,
  creation time, and payload. Duplicate sequence numbers are idempotent only
  when byte-identical; conflicts fail closed.
- Persisted states are `created`, `running`, `waiting_human`, `blocked`,
  `failed`, `complete`, `protocol_error`, `accepted`, and `stopped`. Only
  `complete` may become `accepted`; resumable outcomes may return to `running`.
  `unknown` is an observational verdict and never licenses mutation.
- `agent_settled` without a typed result call records `protocol_error`, never
  `complete`. `wait` redelivers until `ack`; acknowledgement does not accept
  the work.
- Completed windows remain visible until explicit acceptance. Work-stage
  windows may be accepted automatically only after successful merge evidence.
- [[adr0017]] applies: missing process, bus, or transcript evidence yields
  `unknown`; it never licenses cleanup.

### Anti-patterns

- No tmux `send-keys`, `wait-for`, pane-option mailbox, or display message for
  agent communication.
- No copied bd task body in a work-stage message.
- No completion inferred from an idle prompt, exited pane, or assistant prose.
- No cleanup of complete, waiting-human, failed, blocked, rejected,
  protocol-error, unknown, or dirty workers before acceptance permits it.
- No Claude `Agent`, `SendMessage`, `ListAgents`, or `TaskStop` in Pi mode.
- No Pi worker census through [[ft012]] or [[im011]].
- No compiled helper; [[adr0001]] and [[adr0002]] select nushell for the CLI,
  while TypeScript is required for the Pi extension hook.

### Known limitations

- The adapter requires tmux, Pi extension loading, and an existing linked
  project group.
- The runtime mailbox is transient; durable results must be committed to Git,
  recorded in bd for work stages, or written through `akm` for AKM stages.
- A killed extension cannot consume new inbox messages until the same Pi
  session is resumed.
- Interactive visibility requires a live tmux integration test in addition to
  fake process tests.

### Binding sanity

- [[ft014]] binds `spawn`, `send`, `wait`, `ack`, `status`, `inspect`,
  `resume`, `accept`, and `stop`, plus the typed Pi bridge and result envelope.
- [[ft013]] binds stage-specific context and requires validation before a
  delegated stage reports success.
- [[ft001]] and [[im002]] contribute naming and linked-window display only.
- [[adr0001]] and [[adr0002]] require nushell for structured workflow data.
- [[adr0017]] forbids destructive conclusions from missing evidence.
- [[adr0024]] and [[adr0025]] keep Pi workers outside Claude census semantics.
