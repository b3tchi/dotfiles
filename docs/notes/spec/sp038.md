# Spec [[cat001]] [[cat002]] [[board]]

## problem

Restoring a session (`nushell/actions/wm-state restore`) must produce
processes that are indistinguishable from ones started by hand: same
parent/owner, same session (setsid), no inherited fds, the same scrubbed
environment, the same tmux wiring. Jan, 2026-10-06: "from process
perspective there should be no difference in apps and processes between a
restored or an interactively spawned session" - for terminals AND for GUI
apps.

Today the launch paths differ per host and per caller:

- i3 and kwi3-X11: `$mod+Return` is a [[ft011|global-hotkey-layer]] Run
  action (or an i3 `exec` in `i3/config.common`) that calls
  `wm-launch-terminal`; the DETACH is done by the caller (hotkeyd's
  `internal/proc/spawn.go`: setsid, close-on-exec sweep, reaped; the daemon
  itself started with `env -u I3SOCK -u TMUX -u TMUX_PANE`).
  `wm-launch-terminal` runs the terminal in the foreground and picks the
  tmux target from the FOCUSED workspace only (`wm-current-workspace`,
  [[ft001|project registry]], [[im002|tmux-to-workstation dispatch]]).
- kwi3 (KWin, phone): launching is a systemd user unit,
  `i3spawn@.service` in `app.slice` (kwi3 repo `i3kwin/phone/`) - owner is
  the systemd --user manager.
- Windows host: no setsid/fork; nushell runs, detaching is `Start-Process`.
- kwi3 sp007 T6 restore uses kwi3 RPC `exec`, which the kwi3 X11 host
  refuses by design (its `spawn()` is a stub: kwi3 does not own
  processes) - kwi3 bug `kwi3-a1j.12`, blocking kwi3 sp007 T7.

hotkeyd ([[ft011]]) was considered as the spawner (a `spawn` verb on its
control socket beside sp023's `set_layer`) and REJECTED by Jan: hotkeyd only
receives keyboard events and handles modes; it does not become a process
launcher.

Capability (approved design, 2026-10-06):

1. Two entry points over one detach core: `wm-launch-terminal <term>
   [--workspace W] [--session S] [--class C]` and a new `wm-launch-gui
   <cmd...> [--class C]`, both ending in one shared `wm-launch-detach`.
   No-flag `wm-launch-terminal` keeps today's behaviour (focused workspace,
   `$mod+Return`); the flags let restore name the session and slot class
   instead of taking whatever is focused.
2. Per-host backends inside `wm-launch-detach`, chosen by PROBING (not
   config): X11 - i3 AND kwi3-X11 - setsid + double fork with the env
   scrubbed exactly like hotkeyd's start (TMUX, TMUX_PANE, I3SOCK);
   KWin/systemd - `systemd-run --user --slice=app.slice` (the `i3spawn@`
   owner); Windows - `Start-Process`. Interactive and restored launches then
   share one code path, so they are identical by construction on every
   host.
3. Callers: i3 `exec` binds and hotkeyd `$mod+Return` keep calling
   `wm-launch-terminal` (on i3 it must keep working exactly as today - a
   detach after the caller's own setsid is harmless); `wm-state restore` on
   kwi3 swaps RPC `exec` for `wm-launch-terminal --session S --class
   wm-slot-...` and `wm-launch-gui` for GUI placeholders; kwi3 sp008
   (spawn below/beside) consumes the same entry points later.
4. kwi3 side: X11 `spawn()` stays a stub; `kwi3-a1j.12` closes as
   superseded by this spec, and kwi3 sp007 T7 depends on it instead.

Rejected alternatives: kwi3 `spawn()` shelling out to the launcher (kwi3
would depend on a dotfiles script); systemd-run on every host including
X11 (needs a systemd user session inside every xrdp session).

Constraints: launchers stay nushell per [[adr0003]] (no long-running
daemon, no stream proxying - nothing here justifies a compiled helper);
a missing backend precondition fails fast and named, never retried
([[adr0014]]'s shape). Testing headless only (sandboxed HOME, stub
tmux/systemd-run, never :10, live i3 or live xrdp).

Intent: mint a new `ft###` (session-launcher) at spec-writing time;
[[ft011]] is a consumer-adjacent caller, not extended.

## solution

Deliver [[ft017|session-launch-entrypoints]] ([[cat001]], [[cat002]]): nushell
launchers per [[adr0001]] / [[adr0003]] (no daemon, no stream - nothing
earns a compiled helper; bash only where [[adr0002]] names it).
`wm-launch-terminal` and a new `wm-launch-gui` both end in
`wm-launch-detach`, which probes the host once and picks a backend:

- X11 (i3 and kwi3-X11): `setsid -f` (util-linux) - new session, the
  intermediate exits at once, so the child is re-parented to the
  session's reaper whoever called the launcher.
- KWin / systemd: `systemd-run --user --slice=app.slice`, the owner
  `i3spawn@.service` already gives on the phone.
- Windows host: `Start-Process`.
- No usable backend: refused by name, never retried ([[adr0014]]).

The child's environment is the SESSION's canonical environment, never the
caller's (Jan, 2026-10-06): on X11 a snapshot written by the session start
script (xinitrc / kwi3's `kwi3-session-env.sh` shape), on KWin the systemd
user manager's, on Windows the user environment; cwd is `$HOME`. That is
what makes a restore run from inside a tmux pane (carrying TMUX, PWD,
NU_*) produce the same process as `$mod+Return` from hotkeyd - a denylist
of names would drift.

`wm-launch-terminal` gains `--workspace`, `--session`, `--class`; with no
flags it keeps exactly today's behaviour on i3 (i3 `exec` binds,
`$mod+Return`). Callers: [[ft011|global-hotkey-layer]] (hotkeyd) is an
unchanged caller and stays keyboard-only; [[ft001|project registry]] and
[[im002|tmux-to-workstation dispatch]] keep resolving the tmux target;
`wm-state restore` on kwi3 swaps kwi3 RPC `exec` for these launchers
(kwi3 bug `kwi3-a1j.12` superseded; kwi3 X11 `spawn()` stays a stub), and
kwi3 sp008's spawn-below/beside consumes them later.

Proof: a headless test launches the same terminal both ways (the hotkeyd
`proc.Run` path and the restore path, from a caller env that deliberately
differs) and diffs `/proc/<pid>`: parent, session id, open fds, environ,
cwd - all equal. Per-host backends are exercised against stubs
(`systemd-run`, `Start-Process` shim) plus the real X11 path on Xvfb.

Trade-offs taken: the X11 env snapshot is a new session-start duty (a
session without one is refused, not silently given the caller's env);
Windows and KWin backends are proven against stubs here and on the real
host only at deploy.

Evidence: [[poc023]] (validated) - env from the session snapshot via
`env -i`, cwd = snapshot HOME, and `setsid -f /bin/sh -c` with an explicit
close-every-fd->2 loop give identical children from a hotkeyd-shaped and a
tmux-pane-shaped caller; a bare `setsid -f` leaks every non-CLOEXEC caller
fd and nushell's own CURRENT_FILE/FILE_PWD/LAST_EXIT_CODE.

one-line fd-closer inside `setsid -f`, a POSIX exec shim [[adr0002]] case 4

### conventions

- Snapshot: `$XDG_RUNTIME_DIR/wm-session-env-<display>` where `<display>`
  is `$DISPLAY` with `:` and `.` replaced by `_` (`:10` -> `_10`), NUL
  separated (`env -0`), written atomically (tmp + `mv`), mode 0600. Dropped
  at write time, never in the session: `TMUX`, `TMUX_PANE`, `I3SOCK`,
  `HOTKEYD_I3SOCK`, `OLDPWD`, `PWD`, `SHLVL`, `_`, and nushell's
  `CURRENT_FILE`, `FILE_PWD`, `LAST_EXIT_CODE`, `NU_VERSION`, `CMD_DURATION_MS`.
  The list lives once, in `wm-session-env-snapshot`.
- `wm-launch-detach [--display D] [--set K=V]... [--dry-run] -- <argv...>`:
  the caller's environment is NEVER passed through; the ONLY caller inputs
  are the display selector (`--display`, default the caller's `$DISPLAY`)
  and explicit `--set` pairs (e.g. `TMUX_TARGET`). cwd = snapshot `HOME`.
- Backend probe, in this order, first match wins:
  1. `$nu.os-info.name == "windows"` -> `Start-Process` (via `powershell
     -NoProfile -Command`), env = user env + `--set` pairs.
  2. snapshot for the display exists -> X11: `env -i <snapshot> <--set>
     setsid -f /bin/sh -c '<close fds > 2>; exec "$@"' sh <argv>` ([[poc023]]).
  3. `systemctl --user show-environment` succeeds -> `systemd-run --user
     --slice=app.slice --collect --quiet <--setenv K=V> -- <argv>` (env =
     systemd user manager's, the `i3spawn@` owner).
  4. else exit 78: `wm-launch-detach: no launch backend for display <D>
     (no snapshot at <path>, no systemd user manager)`.
- `--dry-run` prints the exact backend name and argv on stdout, one line,
  and starts nothing: that is how the Windows and systemd backends are
  tested on this box.
- Exit 0 once the child is started; detach never waits for it.
- Terminal class flag mapping (`st -c`, `foot --app-id`, `kitty/alacritty
  --class`, `xterm -class`) MOVES from `wm-state`'s `term-class-flag` into
  `wm-launch-terminal`; `wm-state` keeps a call-through so its i3 path is
  untouched.

### anti-patterns

- Passing caller env through, or unsetting a denylist at LAUNCH time (it
  drifts - [[poc023]] showed nushell itself adds vars).
- `setsid -f` without the fd-closer (leaks every non-CLOEXEC caller fd).
- Falling back to the caller's env when the snapshot is missing.
- `sleep` to wait for a child; `pkill -f` patterns in tests (kill by pid).
- Tests that touch `:10`, a live i3, Jan's tmux server, or a real
  `systemd-run --user` unit (stub it).
- hotkeyd changes of any kind ([[ft011]] stays keyboard-only, Jan).

### known limitations

- kwi3's LOCAL-display session (`kwi3-xsession`, kwi3 repo) and lightdm i3
  sessions get their snapshot only from the i3 `exec` line / a kwi3 repo
  follow-up; a kwi3 local session without one is refused (exit 78), not
  degraded. Follow-up filed in the kwi3 bd at spec-ready.
- Windows and systemd backends are proven by `--dry-run` argv here and on a
  real host only at deploy.
- The sp007 i3 dry-run golden changes on purpose in Task 6 (Jan approved
  2026-10-06), on `exec` lines only.

#### success_criteria
- [[poc023]] reproduced as a test with a probe child: launched once from a
  hotkeyd-shaped caller (`env -i <session env> setsid sh -c ...`) and once
  from a tmux-pane-shaped caller (TMUX, TMUX_PANE, PWD, NU_*, cwd /tmp,
  non-CLOEXEC fds 7 and 9 open): `/proc` ppid equal, sid == pgid == pid
  for both, fd sets equal to a bare probe's, environ `diff` empty, cwd ==
  snapshot HOME.
- Control: the same tmux-pane caller with the fd-closer removed (test-only
  env knob `WM_LAUNCH_TEST_NO_FDCLOSE=1`, refused unless
  `WM_LAUNCH_TEST=1`) shows fds 7/9 - proves the assertion has teeth.
- `--set TMUX_TARGET=dev` appears in the child's environ and nothing else
  from the caller does.
- `--dry-run` prints exactly `x11 <argv>` / `systemd <argv>` / `windows
  <argv>` for each backend (systemd forced by a stub `systemctl` on PATH
  and no snapshot; windows by `WM_LAUNCH_TEST_OS=windows`), starts nothing
  (process count unchanged).
- No backend -> exit 78 with the message in ## plan, nothing started.

#### edge_cases
- Argv with spaces, quotes, `$`, unicode reaches the child verbatim (no
  shell re-joining; `"$@"` only).
- Snapshot present but unreadable / corrupt (no `HOME=`) -> exit 78 naming
  the path, never the caller env.
- `--display` naming a display with no snapshot while another has one ->
  refused, not cross-used.
- Command not found -> non-zero exit with the command named (checked
  before detaching via `which`), not a silent detached failure.
