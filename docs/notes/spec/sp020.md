# Spec [[cat002]] [[board]]

## solves
[[us019|programmable-global-keybinds]] via [[im009]]

## problem

**The keyboard event layer is i3's bind table, and it has run out of
expressiveness.** Global binds live as 159 `bindsym`/`bindcode` lines spread
across five files — 142 in [i3/config.common](../../../i3/config.common), 6 in
[i3/config](../../../i3/config), 5 in
[i3/config-xrdp](../../../i3/config-xrdp), 4 in
[i3/config.d/native.conf](../../../i3/config.d/native.conf), 2 in
[i3/config.d/wsl.conf](../../../i3/config.d/wsl.conf) — plus a Python XI2
listener ([quickshell/qs-keymon.py](../../../quickshell/qs-keymon.py)) that
exists *only* because i3 cannot express what one feature needed. [[ft003]]
solved the file-layering problem cleanly; it did not and cannot solve the
expressiveness one.

**Evidence that the ceiling is real, not theoretical.** The `$mod+o` nav mode
(dotfiles-5u6m) is one self-contained three-layer mode, and it took 14 commits
to get to its current shape — the majority of them working around i3 rather
than building features:

- i3 cannot report **held modifier state**. The bar needs it to paint
  "nav MOVE" / "nav RESIZE", so `config.common` binds the raw Ctrl and Alt
  keycodes (37/105, 64/108) to `nop nav-move-on` / `nop nav-resize-on` marker
  binds whose entire purpose is to make an executed-binding event fire, which
  [quickshell/config/Bar.qml](../../../quickshell/config/Bar.qml) then
  string-matches (`noteBinding`, `cmd.indexOf("nop nav-move-on")`). The layer
  name is reconstructed from bind side effects: `navLayer` composes synthetic
  mode names i3 never enters, and a 120 ms `navUnstick` timer guesses when a
  release was missed (6dc7751 shrank it; 64321d7 debounced the pill; b017cc3
  had to filter mode-switch bindings back out of the same stream).
- Before the marker binds it was worse: a twin mode `nav-move` that duplicated
  every movement bind (03ff052 removed it), because publishing "Ctrl is held"
  as a *mode name* was the only channel i3 offered.
- `bindsym Control_L` silently drops — i3's parser eats the leading `Control`
  as a modifier and fails on the `_L`, with no error from `i3 -C`. Hence
  `bindcode` against hardcoded keycodes, i.e. the bind table already contains
  keymap-specific magic numbers.
- i3 has `--release` (this config uses it: `$mod+Print --release`,
  `$mod+Shift+d --release`, and nav's `bindcode --release` markers), but it
  cannot carry **state between a press and a release**. The alt-tab switcher
  needs exactly that — cycle on repeated Tab while Super stays down, confirm on
  Super release — so it could not be a bind: `config.common` grabs `$mod+Tab`
  with `nop` purely to stop the key leaking, and the real logic reads raw XI2
  events in `qs-keymon.py`. Two event mechanisms, one feature.

**What i3 structurally cannot do**, and therefore what stays unbuildable while
the bind table lives there: held-modifier layers without marker-bind
side channels, key sequences, repeat counts (`3j`), per-window conditional
binds, and bind timeouts. Every one of those is ordinary in a program that owns
its own grabs.

**Cost of staying.** Each new interaction pays the same tax the nav mode paid:
express the intent in i3's vocabulary, discover a gap, work around it via `nop`
signals or a second event listener, then teach the bar to reverse-engineer
state from bind side effects. The bar is now coupled to the *shape of the bind
table* rather than to a state contract — b017cc3 and 64321d7 are both bugs of
that coupling, not of the feature.

**Constraints the solution inherits.** X11 only: native `:0` and the xrdp `:10`
session. Sway is out (no active sway session). App-internal keys — nvim, tmux,
quickshell pickers — are out by nature: they are not global binds and no global
layer can own them. xrdp synthesises Shift around every character it sends
(dotfiles-5u6m), so a held Shift is unobservable *in that session*, not in i3
specifically — any replacement sees the same churn and must keep Ctrl/Alt as
its modifier layers plus the release fall-back guard.

**Non-negotiable safety properties**, from the failure modes this layer can
create: (1) a chord must be owned by exactly one grabber — bound in both i3 and
a new layer, it double-fires; (2) whatever owns the binds must not be able to
lock the session out of input if it hangs; (3) if it dies, there must remain a
way to restart it, since a session whose every bind died with a process is
unusable.

The target capability is recorded as [[ft011]] (`global-hotkey-layer`,
`status: proposed`) and the execution epic exists in beads as `dotfiles-hwds`;
this spec is where the solution and the migration order get decided. [[ft009]]
(mode-bar control) is the consumer whose binding-event parsing the change is
meant to retire, and [[ft003]] keeps owning what remains in the i3 files.

## solution

**Build [[ft011]] as a per-display Python daemon that owns its own grabs, and
migrate the bind table into it one group at a time.** The daemon lives in a new
top-level `hotkeyd/` dot — `hotkeyd.py` (grab + dispatch), `binds.py`
(declarative table), `layers.py` (layer engine + state publisher), `dot.yaml`
(links + `python-xlib`), `hotkeyd.sh` (thin launcher), `test-hotkeyd.sh`.
[[cat002]] is the bucket: this is display-platform machinery, X11-only, native
`:0` and the xrdp `:10` session.

**Mechanism: a per-chord passive grab on the root window, never an exclusive
grab.** That is the same thing i3 and sxhkd do, and the choice is a failure-mode
decision rather than a taste one: an exclusive keyboard grab held by a hung
daemon locks every key in the session, whereas per-key grabs degrade to "that
one chord stopped working" and leave the rest of the session — including the
panic bind — reachable. Each chord is grabbed with its lock-bit variants
(`Mod2`/`Lock`), because those bits ride in the event state and a bare-mask
grab silently misses whenever NumLock is on. Dispatch goes over one persistent
i3 IPC socket held open for the process lifetime; no `i3-msg` spawn per
keystroke. (Shipped through T5 as core `XGrabKey`; moving to XI2
`XIGrabKeycode` for source-device identity — see the mechanism amendment
below. Per-chord, never `XGrabKeyboard` / `XIGrabDevice`, holds either way.)

**Language: Python, per [[adr0015]]** — condition 1, an X-ecosystem binding
with working prior art in this repo (`python-xlib` in
[quickshell/qs-keymon.py](../../../quickshell/qs-keymon.py), already an
installed dependency, so this adds no new runtime). [[adr0003]] does not apply:
there is no listener to proxy and no per-request hot path, only one keystroke
per human action. Front-end is a thin shell launcher in the `qs-bar.sh` /
`qs-notif.sh` shape, not a `nushell/actions/` wrapper — [[adr0015]] explicitly
declines the wrapper mandate for Python entry points, and a nushell hop in
front of a keystroke daemon would add startup cost to the exact path this
spec exists to keep short.

**Bind table is a Python module, not YAML.** Binds need composition —
workspace `1..8` loops, per-layer tables, shared command builders — and a
module gives that plus comments without anyone writing a parser. The loader
validates what i3's parser used to catch for free: duplicate chord within a
layer, reference to a layer that does not exist, empty command. `--check`
loads, validates, reports, and exits without grabbing — the `i3 -C`
replacement once binds leave i3, and the thing that makes the migration
auditable.

**State channel: a unix socket per display**
(`$XDG_RUNTIME_DIR/hotkeyd-<display>.sock`), one JSON line per layer or
held-modifier change, with current state replayed on connect so a
late-starting bar is never blank. This is the [[adr0012]] shape applied to
input state — the daemon owns the state, bars are read-only consumers — and it
is what retires [[ft009]]'s reverse-engineering of layer state from
`nop nav-move-on` marker binds and its synthetic mode names. The bar's reader
obeys [[adr0014]] (fail fast on unrecoverable setup, sleep floor, respawn via
a timer outside the loop), same as every other reader loop here.

**Migration: cutover per group, never duplication, and the group is sized by
grab ownership.** A chord bound in both i3 and the daemon double-fires, so
binds leave [[ft003]]'s files in the same commit they appear in `binds.py`.

*The original plan said `nav` goes first, "self-contained, three layers". That
was wrong, and the T6 cutover was reverted for it (`fd9e9f2`).* nav is not
self-contained. On `:10` the xrdp session merges `i3wm.mod: Mod1`, so nav's own
sublayer chords **are** i3 globals on that display:

| nav chord | on `:10` resolves to | i3 global owner |
|---|---|---|
| `Mod1+{h,j,k,l}` resize | `$mod+{h,j,k,l}` | `focus left/down/up/right` |
| `Mod1+{Left,Down,Up,Right}` resize | `$mod+{arrows}` | `focus` |
| `Mod1+q` exit | `$mod+q` | `split toggle` |

The first two rows are the eight chords that took `BadAccess` (`fd9e9f2`). The
`Mod1+q` row is a *behavioural* overlap rather than a grab collision — exit
keys are grabbed bare (`layer_chords`), so the daemon never requests `Mod1+q`
and it routes via the active Alt grab instead. Eight `BadAccess`, not nine; the
Task 13 fixture names the eight.

On `:0` (`$mod` = `Mod4`) none of those collide, which is exactly why the
cutover passed every suite and broke on the only display in daily use.

**The structural fact behind it:** two X clients cannot hold a passive grab on
one chord. An i3 binding *mode* has no such constraint — inside `mode "nav"`
i3 re-binds its own keys against itself. A grab-based daemon therefore **can
never shadow an i3 global the way an i3 mode can**; it takes `BadAccess` and
the key falls through to i3. So a migration group is not a conceptual grouping
(a "mode", a "feature") — it is the **transitive closure of chords that would
otherwise be owned twice**, resolved per display. One grabber owns a chord and
gives it several meanings by state; that is what an i3 mode was doing all
along.

Concretely, the first real group is the **directional group**: i3's global
`$mod+{h,j,k,l}` / `$mod+{arrows}` focus binds, `$mod+Shift+*` move binds,
`$mod+q`, `$mod+o`, and the whole `mode "nav"` block — migrated in one commit,
after which the daemon owns `$mod+h` and resolves it by state (`focus left` in
the default layer, `resize shrink width` in nav's resize sublayer). The
ownership map that defines the closure is machine-generated, not hand-written;
see the `--ownership` convention in `## plan`.

[[ft003]] keeps the panic bind, permanently un-migrated — see `## recovery`.

**Mechanism amendment: grab via XI2, not core `XGrabKey`, so every event
carries its source device.** Core `KeyPress` carries no device identity, so the
daemon as built through T5 structurally cannot tell a real keystroke from an
injected one, or one keyboard from another. `XIGrabKeycode` delivers
`XIDeviceEvent` with a `sourceid`. The installed `python-xlib` 0.33 supports
this directly — `Xlib.ext.xinput` exposes `grab_keycode` /
`XIPassiveGrabDevice` and registers a parsed `DeviceEventData` struct carrying
`deviceid`, `sourceid`, `detail` and `mods` for `KeyPress`/`KeyRelease`. No
hand-unpacking is needed on this path; the manual struct decoding in
[quickshell/qs-keymon.py](../../../quickshell/qs-keymon.py) is required only
for XI2 **raw** events, which have no registered parser, and grabbed-keycode
delivery is not raw. Measured device inventory:

    :0    id=12  AT Translated Set 2 keyboard      id=5  XTEST (injection)
          id=13  BlueZ 5.86 (MCS)
          id=14  Acer WMI hotkeys
    :10   id=7   xrdpKeyboard                      id=5  XTEST (injection)

This adds a `device=` predicate to `Bind` and lets the daemon drop
XTEST-sourced events.

**CORRECTION (measured during Task 11, `dotfiles-hwds.13`).** This paragraph
previously claimed an XI2 passive grab "contends with i3's core passive grab
identically", so the port was orthogonal to the collision problem. That is
false. The X server keeps core and XI2 passive grabs in **separate conflict
domains** — reproduced independently on a throwaway display:

| grab order | result |
|---|---|
| core → core | `BadAccess` |
| XI2 → XI2 | refused (non-empty `modifiers` reply) |
| core → XI2 | **no conflict** |
| XI2 → core | **no conflict** |

Two consequences, both load-bearing for the rest of this spec:

1. **`BadAccess` is no longer a detector of i3-vs-daemon double ownership.** It
   now only sees a second hotkeyd. Every "zero `BadAccess`, asserted" criterion
   below was designed as the T6 safety net; against an XI2 daemon it is a guard
   that cannot fire for the case it exists for. `check --ownership` (Task 13)
   stops being belt-and-braces and becomes the *only* collision detector — so it
   must land before Task 14, not merely before Task 16.
2. **A contested chord now transfers instead of no-opping, and which way it
   lands depends on grab order.** Pre-port, i3 grabbed at config load and the
   daemon took `BadAccess`, so `$mod+o` — owned by both `binds.py` and
   `config.common:408` — stayed with i3. Post-port the **later grabber wins,
   symmetrically** (measured both ways: core→XI2 gives the XI2 client 3/3,
   XI2→core gives the core client 3/3). Observed end to end on a real i3 plus
   the real daemon:

   | phase | i3 binding state | daemon layer |
   |---|---|---|
   | fresh session | default | **nav** |
   | after `i3-msg reload` | **nav** | default |
   | after daemon `SIGHUP` | **nav** | default |

   So the daemon holds the chord from session start, and the first i3 reload
   takes it back *permanently*: `exec_always hotkeyd.sh start` exits
   `already running` and spawns nothing, and `GrabManager.sync_binds` re-grabs
   only chords whose `(code, mask)` changed, so `SIGHUP` does not re-register an
   unchanged one either. Only a daemon restart flips it back.

   Not a lockout — either owner serves a working nav, and the panic chord is
   unaffected in both states. But the migration rule ("a chord lives in EITHER
   i3 or the daemon") was previously enforced by the X server, and now nothing
   enforces it: double ownership is silent, and which side answers depends on
   who reloaded last.

Filed as `dotfiles-f224`. It must be decided before the directional cutover.

**Per-display handling belongs to the event layer, keyed on screen id.** One
daemon per display already exists, but both load the same `binds.py`. Since the
daemon knows which screen it owns, per-screen resolution happens there rather
than by branching the table into two files — AC3 forbids a duplicate table, not
a table that knows its screen.

**What actually diverges is narrower than it first appears.** Both in-scope
displays run the *same* i3 entry point: `xrdp/xinitrc` ends in `exec i3`, which
loads `~/.i3/config` — i.e. [i3/config](../../../i3/config) — so `:0` and `:10`
get identical commands from it. [i3/config-xrdp](../../../i3/config-xrdp) is
**not** the `:10` config; its only consumer is
`scripts/termux/start-xorg-rdp-proot.sh`, i.e. proot-over-Xvnc, which this
spec scopes out. So the five chords that differ between those two files
(`$mod+Return`, `$mod+d`, `$mod+p`, `$mod+Shift+c`, `$mod+Shift+d`) are a
desktop-vs-proot divergence, not a `:0`-vs-`:10` one, and migrating them is not
this spec's problem.

The divergence that *is* real is the modifier: `$mod` is `Mod4` on `:0` and
`Mod1` on `:10`, via the `i3wm.mod` X resource. That is what the daemon must
resolve per screen, and the staging constraint on it is hard: while i3 still
owns binds in a group, the daemon's `$mod` must equal i3's, so both read the
same source (`set_from_resource $mod i3wm.mod Mod4`, with `xrdp/xinitrc`
supplying `Mod1`). Agreement by construction, not by hand. After a group is
fully migrated the daemon is its sole grabber and simply defines the value.

**xrdp constraints carried forward. MEASURED on a live RDP client
(2026-07-28) — the ~120 ms release fall-back guard is PERMANENT, not
conditional.** An earlier draft made the guard conditional on source
filtering: if xrdp's synthetic Shift arrived as XTEST `id=5` while real keys
arrived as `xrdpKeyboard` `id=7`, the daemon could filter and drop the guard.
A passive XI2 raw-event probe on the live `:10` session, with a human typing
at a real RDP client, settles it: **every event — real keystrokes and the
synthetic Shift alike — carries `sourceid 7 (xrdpKeyboard)`. No XTEST is
involved.** xrdp injects at the device level, so there is no source to filter
on, and no amount of device scoping can separate the two. This could not have
been settled by injection, because XTEST is what a harness injects with.

The same trace shows *why* the guard is needed, and narrows the claim. Typing
`A` with Shift genuinely held produced:

    3905.1  press    Shift_L      <- physical press
    5012.4  release  a            <- spurious leading release
    5012.5  press    a
    5012.5  release  a
    5012.6  release  Shift_L      <- xrdp DROPS Shift to deliver the character
    5910.4  release  Shift_L      <- physical release, ~900 ms later

One press, two releases: a tracker believes Shift is up at 5012.6 while it is
still physically down for another 900 ms. That is precisely the state the
fall-back recovers from.

**Narrower than previously stated:** a *bare* held Shift is NOT unobservable
here. Two bare holds in the same run (246 ms and 623 ms) produced balanced
press/release pairs. The corruption is specific to a character being delivered
mid-hold. So "a held Shift is unobservable on `:10`" is too strong; the
accurate statement is that a held Shift is corrupted by any character sent
during the hold. Modifier layers stay on Ctrl/Alt regardless.

Scope of the measurement, so it is not over-read: it characterises **this** RDP
client on `:10`. A different client may synthesise differently, and `:0` — with
three real keyboards — has not been probed and would need its own run at the
console.

The session also resets its keymap on every connect, so the daemon resolves
chords keysym-first and re-grabs on `MappingNotify`; that is strictly better
than today's hardcoded `bindcode 37/105/64/108`.

**Trade-offs accepted.** (1) A third sanctioned language and a new daemon in
the session's input path — bounded by the per-key grab degradation above and
the panic bind. (2) The daemon reimplements validation i3 gave for free;
`--check` plus the loader tests are the price. (3) Sway is out of scope (no
active sway session), so a future sway host would need its own grab backend —
accepted rather than designed for. (4) App-internal keys (nvim, tmux,
quickshell pickers) stay where they are; no global layer can own them. (5) XI2
grabbing is a second X-extension dependency, and an XI2 protocol change is a
silent-decode risk in a way a core grab is not. Accepted because it is the only
way to obtain the source device, and cheap because `python-xlib` already parses
these events. (6) Migration
groups sized by grab-ownership closure are larger than the conceptual groups
they replace, so there are fewer, bigger cutovers than originally planned —
this is the cost of the T6 lesson, not a regression.

**Confidence gate.** The mechanism is not yet measured here, so the first task
is the throwaway spike already filed as `dotfiles-4q3n`: one grabbed chord,
persistent IPC dispatch, press→action latency against i3's own binding-event
baseline, on **both** displays, plus grab survival across an xrdp reconnect and
behaviour when the daemon is SIGKILLed mid-hold. Its verdict lands as a
`poc###` zettel informing this spec before any bind moves.

**Gate outcome: validated by [[poc013]]** (2026-07-27). Daemon dispatch p95 is
+0.17 ms vs i3 on the live xrdp `:10` session and +0.11 ms on a clean display,
with the daemon's *median* actually faster on `:10`; SIGKILL mid-hold leaves no
latched modifier and no leaked grab; a keymap reset is survivable. Three
findings tighten the tasks rather than change the shape: the lock-bit variants
are load-bearing (a bare-mask grab fires 0/3 with NumLock on — measured, not
theorised), `Super_L` is keycode 133 on `:0` but 115 on `:10` so chords must
resolve keysym-first, and `MappingNotify` must be compare-then-regrab because
spurious events arrive at every startup. Live `:0` numbers stayed unmeasurable:
that display had a stuck client-held keyboard grab which blackholed i3's own
binds too, so real-`:0` measurement remains Task 8's.

## recovery

**One i3-owned chord resets the whole layer back to i3.** Added after the T6
cutover was reverted (`fd9e9f2`): the original escape hatch only ran
`hotkeyd.sh restart`, which helps when the daemon is DEAD and not at all when it
is alive and wrong — misgrabbing, stuck in a layer, or serving a table whose
chords collide with i3's. Recovery has to mean "give the keyboard back to i3",
not "try the daemon again".

    i3 keeps exactly one bind:  $mod+Shift+F12 -> hotkeyd-panic.sh

`hotkeyd-panic.sh panic`:

1. `hotkeyd.sh stop` on this display — the daemon exits and its grabs die with
   it, because X drops a client's grabs when the client goes.
2. Link `i3/config.d/zz-fallback-binds.conf` into `~/.i3/config.d/`.
3. `i3-msg reload` — i3 parses the fallback table and takes passive grabs on
   every chord it names.

`hotkeyd-panic.sh resume` reverses it: remove the fallback link, reload, start
the daemon.

**Why the ordering has no contested-chord window.** Grabs die with the process
and i3 re-establishes its own on reload, so at no point do two clients hold the
same chord. This is the same reasoning that made the T6 revert clean: stopping
the daemon and reloading i3 was enough to restore every key, with no ungrab
bookkeeping.

**What makes it trustworthy rather than decorative:**

- `zz-fallback-binds.conf` is the REAL bind table, kept in the repo and checked
  by `i3 -C` in the suite. A stub that rots is worse than nothing, because it
  is discovered during the outage it exists for.

  **Its content is the i3 equivalent of whatever `binds.py` currently owns —
  not "the set i3 owns today".** Those are opposites, and the first draft said
  the latter: i3 still owns its own binds, so a fallback restating them would
  duplicate every one, and i3 treats duplicate keybindings as a config error
  (nagbar) rather than last-wins — the same trap `i3/config.d/native.conf:103`
  already documents. So the file is empty until Task 14, then names the
  directional group. The freshness test diffs it against `binds.py`'s chord
  set, not against i3's.
- For the same reason there is no override story: `zz-` keeps the file last in
  the `config.d/*.conf` glob, which settles ordering, but the fallback must not
  duplicate a live bind at all. `i3 -C` on the composed tree is the check.
- The panic chord is RESERVED: `binds.py`'s validator refuses any table that
  binds it, under every modifier spelling and not merely the `$mod` token, so a
  future edit cannot quietly take the one key that recovers the session. That
  is a validator rule, not a comment.
- Asserted on real effects: start the daemon, confirm it owns a chord, panic,
  then confirm i3 owns that chord again — read from `i3-msg -t get_config`
  (bindings; `get_tree` returns the window tree), not from the script's exit
  code.
- **Panic is machine-wide, not per-display, and the spec should stop implying
  otherwise.** `~/.i3/config.d/` is shared: both `:0` and `:10` include the same
  glob, so panicking on one display links a file the other display's i3 will
  parse on its *next* reload, while that display's daemon still holds its grabs
  — reintroducing exactly the contested state the ordering argument rules out.
  Either scope the fallback per display or state plainly that panic is a
  machine-wide fallback and `resume` must precede any reload on the other
  display. Task 10 owns this decision.

  **DECIDED (Task 10): machine-wide, and enforced rather than documented.**
  Per-display scoping is not available: `i3/config` is a single shared entry
  point whose `include ~/.i3/config.d/*.conf` both sessions run, and i3's
  `include` takes no conditionals — a per-display fallback would mean a second
  entry point, which is the hand-synced duplication [[ft003]] exists to have
  deleted. Writing down "resume before reloading the other display" would leave
  the hazard live and merely noted, triggerable by a `$mod+Shift+c` nobody
  connects to hotkeyd. So `panic` stops the daemon on EVERY display before it
  links, and `hotkeyd.sh start` refuses while the link exists (exit 4). After a
  panic no hotkeyd grabs exist anywhere, so a reload on any display is safe,
  and no autostart or reconnect can rearm one display behind the fallback.
  Panic is sticky until `resume` — the property that survives a reboot, since
  the link is on disk and the daemon's absence is not.

**Why this changes the risk calculus for the full migration.** The objection to
one process owning every hotkey is blast radius: if it breaks, the keyboard is
gone. With panic, the worst case is one chord away from the setup that works
today — recoverable without a terminal, without ssh, and without knowing why the
daemon failed. That is what makes migrating the remaining ~159 binds a decision
about scope rather than about safety.

**Conventions** (each is load-bearing):

- **Per-key grabs, never `XGrabKeyboard` / `XIGrabDevice`.** An exclusive grab
  held by a hung daemon locks every key in the session including the panic
  chord. This is the [[ft011]] mechanism decision and is not revisitable inside
  a task. Applies to the XI2 port identically: `XIGrabKeycode` per chord, never
  a device grab.

- **A migration group is a grab-ownership closure, not a concept.** Never scope
  a cutover by "this is one mode" or "this is one feature". Resolve `$mod` for
  every display (`Mod4` on `:0`, `Mod1` on `:10`), expand every chord the group
  would grab, and pull in every i3 bind that collides on *any* display — then
  repeat until closed. This is the T6 lesson (`fd9e9f2`) and the single most
  expensive thing to get wrong, because a partial group passes on `:0` and
  fails only on the display in daily use.

- **`hotkeyd.sh check --ownership` is the gate on every cutover commit.** It
  emits, per display, chord → resolved modifier → owner (`i3` / `daemon` /
  `neither` / `BOTH`), machine-generated by parsing i3's live bind table and
  `binds.py`, and exits non-zero on any `BOTH` row. Hand-auditing a bind table
  across two `$mod` values is what failed at T6; this is the replacement.

- **Zero `BadAccess` is an assertion, not a log line.** Any cutover test must
  assert the daemon obtained *every* grab it asked for, on an `:0`-shaped and
  a `:10`-shaped display. A `BadAccess` means another client already owns that
  chord — the exact silent failure that let T6 merge green.

- **The daemon defers to i3 modes.** i3 modes hold their own passive grabs, so
  a daemon layer entered while an i3 mode is up produces two owners and
  divergent published state (`dotfiles-hwds.10`, reproduced). The daemon
  subscribes to i3's `mode` event on its existing IPC connection: it refuses
  layer entry while i3 reports a non-default mode, and exits any active layer
  (publishing `default`) when i3 enters one. Never two active owners.
- **Grab every lock-bit variant of each chord** (`0`, `LockMask`, `Mod2Mask`,
  both). Those bits ride in the event `state`, so a bare-mask grab silently
  stops matching the moment NumLock or CapsLock is on — a bug that looks like
  "the daemon randomly stops working".
- **Chords resolve keysym-first, re-grabbed on `MappingNotify`.** The xrdp
  session resets its keymap on every connect; hardcoded keycodes (today's
  `bindcode 37/105/64/108`) are stale after that.

- **Events carry their source device; XTEST-sourced events are dropped.** XI2
  `XIDeviceEvent.sourceid` is the only channel that distinguishes a real
  keystroke from an injected one, and the two live on the same display so no
  per-display mechanism can substitute. Use `Xlib.ext.xinput.grab_keycode` and
  the library's parsed `DeviceEventData` — do **not** hand-unpack. The manual
  decoding in [quickshell/qs-keymon.py](../../../quickshell/qs-keymon.py)
  exists because XI2 *raw* events have no registered parser; grabbed-keycode
  events do.

- **The event layer owns per-screen handling, keyed on screen id.** The daemon
  knows which display it owns, so *all* per-display resolution happens there:
  the modifier `$mod` binds to, the `qsenv` prefix, the terminal command, and
  any bind that should exist on one screen and not the other. Screen-awareness
  inside the table is legitimate — AC3 forbids a duplicate *table*, not a table
  that knows which screen it is running on. What it rules out is two files, or
  a second copy kept in sync by hand.

  **Where the screen-specific value comes from is staged, and the stage is a
  correctness constraint, not a style one.** While i3 still co-owns binds, the
  daemon's `$mod` must equal i3's `$mod` or the two grab different chords and
  the T6 collision returns — so during partial migration the daemon reads the
  same X resource i3 reads (`set_from_resource $mod i3wm.mod Mod4` in
  [i3/config](../../../i3/config), overridden to `Mod1` by `xrdp/xinitrc`,
  alongside ~16 colour vars in `config.common`). Same source, agreement by
  construction. Once a group is fully migrated, the daemon is the sole grabber
  for it and `$mod` is simply whatever the event layer says — i3 has no opinion
  left to disagree with. Do not take that shortcut before the group's cutover
  completes.

- **The panic chord is reserved in the validator, under every spelling.**
  `binds.py`'s validator refuses any table that binds the panic chord. The
  validator is display-agnostic while `$mod` is not, so reserving the literal
  `$mod` token alone leaves a hole: `Mod1+Shift+F12` spelled out steals the
  chord on `:10`, `Mod4+Shift+F12` on `:0`, and neither matches a token check.
  The reserved set is `Shift+F12` under **both** modifier resolutions plus the
  `$mod` token, normalised. A rule with a fixture per spelling, not a comment.
- **One persistent i3 IPC connection** for the process lifetime. No `i3-msg`
  spawn per keystroke — a ~30 ms process launch on the path this spec exists
  to keep short.
- **Per-display scoping via `quickshell/qs-session.sh` helpers** (`QS_SID`,
  `qs_same_session()`), plus `flock` on
  `$XDG_RUNTIME_DIR/hotkeyd-<display>.lock` exactly as
  `quickshell/qs-focus-border.py` does. Never `pkill` unscoped — that is
  dotfiles-8xt.
- **Python under [[adr0015]] condition 1**, `python-xlib` only (no new deps),
  with the front-end a thin shell launcher per that ADR — not a
  `nushell/actions/` wrapper, which would add nushell startup to the restart
  path.
- **State socket is write-only from the daemon, read-only for bars**
  ([[adr0012]] shape). Bar-side readers obey [[adr0014]]: fail fast on
  unrecoverable setup, sleep floor per iteration, respawn on a timer outside
  the loop.
- **Ctrl/Alt for modifier layers, plus the ~120 ms release fall-back**, because
  xrdp synthesises Shift around every character it sends. That is a property
  of the session, not of i3, so the daemon inherits it.

**Anti-patterns** (auto-reject in review):

- A chord present in both `i3/config.common` and `binds.py` at any commit
  boundary. It double-fires; migration is cutover, not duplication.
- `XGrabKeyboard`, `xinput --disable`, or any exclusive-input trick.
- A `subprocess.run(["i3-msg", ...])` dispatch path, even "temporarily".
- Hardcoded keycodes in `binds.py`. Keysyms only — keycodes are a keymap
  artifact (see the `MappingNotify` convention).
- Migrating the panic bind out of i3, or letting `binds.py` bind that chord.
  It exists precisely for the case where the daemon is dead *or wrong*.
- Scoping a cutover group by concept ("it's one mode") instead of by
  grab-ownership closure across both `$mod` values. This is the T6 defect
  verbatim.
- A cutover commit whose tests do not assert zero `BadAccess` on an
  `:10`-shaped display. Green on `:0` proves nothing about the display in use.
- A second bind table, or a per-display copy kept in sync by hand. One table
  that resolves per screen is the design; two files is the anti-pattern.
- A daemon `$mod` that disagrees with i3's `$mod` while i3 still owns binds in
  the same group. They must read the same source until the group is closed.
- A daemon layer entered while i3 is in a non-default mode. Two owners.
- A daemon that keeps running after losing its X connection, or that retries a
  failed grab in a tight loop ([[adr0014]]).
- Test assertions on log lines or "the process is running" in place of the
  actual WM effect. `i3/test-nav-mode.sh` asserts focus/geometry today and must
  keep doing so.

**Known limitations** (accepted, not defects):

- X11 only. Sway has no `XGrabKey`; a sway host would need its own backend, and
  nothing regresses today because sway binds nothing here.
- App-internal keys (nvim, tmux, quickshell pickers) stay where they are.
- The daemon reimplements i3's duplicate-bind detection; `--check` plus loader
  tests are the entire safety net for the bind table.
- Grabs die with the process, so any crash is a partial keyboard outage until
  the panic chord is pressed. Bounded, never zero.
- Native `:0` verification requires the desktop machine; from a WSL session
  there is no `:0` to test against (the [[sp012]] Task 8 situation).
- Migration groups are grab-ownership closures, so they are coarser than the
  conceptual groups originally planned. Expect fewer, larger cutovers, each
  gated by `check --ownership`.
- Source-device filtering cannot be verified by injection: XTEST is what a
  harness injects *with*, so proving that real client keys differ from
  xrdp's synthetic Shift needs a human at an RDP client. Until then the
  ~120 ms release fall-back guard stays.
- XI2 event decoding is a silent-decode risk rather than an import error if the
  protocol shifts. `python-xlib` parses device events, but XI2 *raw* events
  still have no registered parser — anything that selects raw events (today
  only `qs-keymon.py`) unpacks by hand.
- The kernel input layer is out of reach and stays out: `/dev/input/*` is
  `root:input` (the user is not in `input`), `/dev/uinput` is root-only, and
  `:10` has no evdev node at all — `xrdpKeyboard` is an xorgxrdp X input
  driver, not a kernel device. An evdev-based design would be blind on the
  display in daily use.

### native `:0` — BLOCKED, and not by anything in this spec

Every `:0` row is unverified. The display has a **stuck exclusive keyboard
grab** (`XGrabKeyboard` → `AlreadyGrabbed`; `:10` → `Success`), which bypasses
every passive grab on that display. i3's own binds are equally dead there —
injecting `$mod+r` leaves the binding state at `default`. XTEST injection does
reach the server (an XI2 raw monitor sees the presses), because raw events
bypass grabs; the grabbed chords simply never match.

This is the same condition `poc013` hit and recorded as an environmental
oddity. It is reproducible and it is what blocks these rows. Ruled out by
experiment: **hotkeyd is not the cause** (grab persists with the daemon stopped
entirely), and neither is the quickshell overlay (grab persists across a
restart). The holder remains unidentified — X offers no API to name it. Filed
as `dotfiles-hwds.30`.

**Anyone re-running the `:0` matrix must probe `XGrabKeyboard` first and abort
on `AlreadyGrabbed`.** Otherwise every row fails and is misattributed to the
daemon, which is what happened to poc013 and nearly happened again here.

### What the matrix caught that no suite did

hotkeyd on `:0` logs `1 chords grabbed on :0 via XI2` and `status` reports
`running` rc 0 — while being completely inert, every chord blackholed. A
component that reports healthy when it cannot do its job is the recurring theme
of this spec's defects (`dotfiles-hwds.19`, `.21`, `.29`, `.30`), and a startup
probe of `XGrabKeyboard` would have turned an afternoon of misattribution into
one log line.
