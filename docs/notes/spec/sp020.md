# Spec [[cat002]] [[board]]

## problem

**The keyboard event layer is i3's bind table, and it has run out of
expressiveness.** Global binds live as 158 `bindsym`/`bindcode` lines spread
across five files — 141 in [i3/config.common](../../../i3/config.common), 6 in
[i3/config](../../../i3/config), 5 in
[i3/config-xrdp](../../../i3/config-xrdp), 4 in
[i3/config.d/native.conf](../../../i3/config.d/native.conf), 2 in
[i3/config.d/wsl.conf](../../../i3/config.d/wsl.conf) — plus a Python XI2
listener ([quickshell/qs-keymon.py](../../../quickshell/qs-keymon.py)) that
exists *only* because i3 cannot express what one feature needed. [[ft003]]
solved the file-layering problem cleanly; it did not and cannot solve the
expressiveness one.

**Evidence that the ceiling is real, not theoretical.** The `$mod+o` nav mode
(dotfiles-5u6m) is one self-contained three-layer mode, and it took 14 commits
to get to its current shape — the majority of them working around i3 rather
than building features:

- i3 cannot report **held modifier state**. The bar needs it to paint
  "nav MOVE" / "nav RESIZE", so `config.common` binds the raw Ctrl and Alt
  keycodes (37/105, 64/108) to `nop nav-move-on` / `nop nav-resize-on` marker
  binds whose entire purpose is to make an executed-binding event fire, which
  [quickshell/config/Bar.qml](../../../quickshell/config/Bar.qml) then
  string-matches (`noteBinding`, `cmd.indexOf("nop nav-move-on")`). The layer
  name is reconstructed from bind side effects: `navLayer` composes synthetic
  mode names i3 never enters, and a 120 ms `navUnstick` timer guesses when a
  release was missed (6dc7751 shrank it; 64321d7 debounced the pill; b017cc3
  had to filter mode-switch bindings back out of the same stream).
- Before the marker binds it was worse: a twin mode `nav-move` that duplicated
  every movement bind (03ff052 removed it), because publishing "Ctrl is held"
  as a *mode name* was the only channel i3 offered.
- `bindsym Control_L` silently drops — i3's parser eats the leading `Control`
  as a modifier and fails on the `_L`, with no error from `i3 -C`. Hence
  `bindcode` against hardcoded keycodes, i.e. the bind table already contains
  keymap-specific magic numbers.
- i3 binds fire on **press only**, so the alt-tab switcher (which must confirm
  on Super *release*) could not be a bind at all: `config.common` grabs
  `$mod+Tab` with `nop` purely to stop the key leaking, and the real logic
  reads raw XI2 events in `qs-keymon.py`. Two event mechanisms, one feature.

**What i3 structurally cannot do**, and therefore what stays unbuildable while
the bind table lives there: held-modifier layers without marker-bind
side channels, key sequences, repeat counts (`3j`), per-window conditional
binds, and bind timeouts. Every one of those is ordinary in a program that owns
its own grabs.

**Cost of staying.** Each new interaction pays the same tax the nav mode paid:
express the intent in i3's vocabulary, discover a gap, work around it via `nop`
signals or a second event listener, then teach the bar to reverse-engineer
state from bind side effects. The bar is now coupled to the *shape of the bind
table* rather than to a state contract — b017cc3 and 64321d7 are both bugs of
that coupling, not of the feature.

**Constraints the solution inherits.** X11 only: native `:0` and the xrdp `:10`
session. Sway is out (no active sway session). App-internal keys — nvim, tmux,
quickshell pickers — are out by nature: they are not global binds and no global
layer can own them. xrdp synthesises Shift around every character it sends
(dotfiles-5u6m), so a held Shift is unobservable *in that session*, not in i3
specifically — any replacement sees the same churn and must keep Ctrl/Alt as
its modifier layers plus the release fall-back guard.

**Non-negotiable safety properties**, from the failure modes this layer can
create: (1) a chord must be owned by exactly one grabber — bound in both i3 and
a new layer, it double-fires; (2) whatever owns the binds must not be able to
lock the session out of input if it hangs; (3) if it dies, there must remain a
way to restart it, since a session whose every bind died with a process is
unusable.

The target capability is recorded as [[ft011]] (`global-hotkey-layer`,
`status: proposed`) and the execution epic exists in beads as `dotfiles-hwds`;
this spec is where the solution and the migration order get decided. [[ft009]]
(mode-bar control) is the consumer whose binding-event parsing the change is
meant to retire, and [[ft003]] keeps owning what remains in the i3 files.

## solution

**Build [[ft011]] as a per-display Python daemon that owns its own grabs, and
migrate the bind table into it one group at a time.** The daemon lives in a new
top-level `hotkeyd/` dot — `hotkeyd.py` (grab + dispatch), `binds.py`
(declarative table), `layers.py` (layer engine + state publisher), `dot.yaml`
(links + `python-xlib`), `hotkeyd.sh` (thin launcher), `test-hotkeyd.sh`.
[[cat002]] is the bucket: this is display-platform machinery, X11-only, native
`:0` and the xrdp `:10` session.

**Mechanism: per-bind `XGrabKey` on the root window, never `XGrabKeyboard`.**
That is the same thing i3 and sxhkd do, and the choice is a failure-mode
decision rather than a taste one: an exclusive keyboard grab held by a hung
daemon locks every key in the session, whereas per-key grabs degrade to "that
one chord stopped working" and leave the rest of the session — including the
escape hatch — reachable. Each chord is grabbed with its lock-bit variants
(`Mod2`/`Lock`), because those bits ride in the event state and a bare-mask
grab silently misses whenever NumLock is on. Dispatch goes over one persistent
i3 IPC socket held open for the process lifetime; no `i3-msg` spawn per
keystroke.

**Language: Python, per [[adr0015]]** — condition 1, an X-ecosystem binding
with working prior art in this repo (`python-xlib` in
[quickshell/qs-keymon.py](../../../quickshell/qs-keymon.py), already an
installed dependency, so this adds no new runtime). [[adr0003]] does not apply:
there is no listener to proxy and no per-request hot path, only one keystroke
per human action. Front-end is a thin shell launcher in the `qs-bar.sh` /
`qs-notif.sh` shape, not a `nushell/actions/` wrapper — [[adr0015]] explicitly
declines the wrapper mandate for Python entry points, and a nushell hop in
front of a keystroke daemon would add startup cost to the exact path this
spec exists to keep short.

**Bind table is a Python module, not YAML.** Binds need composition —
workspace `1..8` loops, per-layer tables, shared command builders — and a
module gives that plus comments without anyone writing a parser. The loader
validates what i3's parser used to catch for free: duplicate chord within a
layer, reference to a layer that does not exist, empty command. `--check`
loads, validates, reports, and exits without grabbing — the `i3 -C`
replacement once binds leave i3, and the thing that makes the migration
auditable.

**State channel: a unix socket per display**
(`$XDG_RUNTIME_DIR/hotkeyd-<display>.sock`), one JSON line per layer or
held-modifier change, with current state replayed on connect so a
late-starting bar is never blank. This is the [[adr0012]] shape applied to
input state — the daemon owns the state, bars are read-only consumers — and it
is what retires [[ft009]]'s reverse-engineering of layer state from
`nop nav-move-on` marker binds and its synthetic mode names. The bar's reader
obeys [[adr0014]] (fail fast on unrecoverable setup, sleep floor, respawn via
a timer outside the loop), same as every other reader loop here.

**Migration: cutover per group, never duplication.** A chord bound in both i3
and the daemon double-fires, so binds leave [[ft003]]'s files in the same
commit they appear in `binds.py`. `nav` goes first — self-contained, three
layers, and it already has a runtime suite
([i3/test-nav-mode.sh](../../../i3/test-nav-mode.sh)) that can be re-pointed
at the daemon while still asserting real focus/move/resize effects rather than
which mechanism produced them. [[ft003]] keeps a hardcoded escape-hatch bind
that restarts the daemon, permanently un-migrated: grabs die with the process,
so a session whose every bind died with a crashed daemon must still have one
key that brings it back.

**xrdp constraints carried forward.** The `:10` session synthesises Shift
around every character it sends, so a held Shift is unobservable there — a
property of the session, not of i3 — which means modifier layers stay on
Ctrl/Alt and the ~120 ms release fall-back guard stays. The session also
resets its keymap on every connect, so the daemon resolves chords keysym-first
and re-grabs on `MappingNotify`; that is strictly better than today's
hardcoded `bindcode 37/105/64/108`.

**Trade-offs accepted.** (1) A third sanctioned language and a new daemon in
the session's input path — bounded by the per-key grab degradation above and
the escape hatch. (2) The daemon reimplements validation i3 gave for free;
`--check` plus the loader tests are the price. (3) Sway is out of scope (no
active sway session), so a future sway host would need its own grab backend —
accepted rather than designed for. (4) App-internal keys (nvim, tmux,
quickshell pickers) stay where they are; no global layer can own them.

**Confidence gate.** The mechanism is not yet measured here, so the first task
is the throwaway spike already filed as `dotfiles-4q3n`: one grabbed chord,
persistent IPC dispatch, press→action latency against i3's own binding-event
baseline, on **both** displays, plus grab survival across an xrdp reconnect and
behaviour when the daemon is SIGKILLed mid-hold. Its verdict lands as a
`poc###` zettel informing this spec before any bind moves.
