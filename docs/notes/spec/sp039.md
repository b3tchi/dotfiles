# Spec [[cat001]] [[cat002]] [[board]]

## problem

**One clipboard across every host, carried by a transport we own.** Today
each hop between hosts rides a different, unowned channel, and the worst of
them fails silently.

**Incident that prompted this (2026-10-30).** On the WSL box's kwi3 xrdp
session (`:40`, up since 10-24), copy from the RDP client PC stopped
reaching X after the 08:31 mstsc reconnect. `xrdp-chansrv`'s log shows no
clipboard traffic after the reconnect while sound/smartcard renegotiated
fine — the channel looked attached and carried nothing (upstream xrdp
#2596, the same failure `i3/config.d/wsl.conf` records "after 6 days").
Restarting chansrv alone did not help; only a full mstsc restart did. A day
earlier a stalled `image/bmp` transfer over the same channel hung Claude
Code's paste probe (`xclip -o`, no timeout) for 1h40m, blocking text paste
in that pane too. Separately, the kwi3 session launcher did not start
`clip-win-bridge.sh` at all (patched in the kwi3 repo, uncommitted), and
that bridge only reaches the *local* WSL host's Windows clipboard — never
the RDP client PC the user actually sits at.

**Current channels, per hop:**

- X display ↔ X display on one host: [[ft007]] store loops + `clip-set.sh`
  (works; per-host only).
- PRIMARY ↔ CLIPBOARD: `i3/scripts/clip-sync.sh` (per display).
- WSL X ↔ local Windows: `i3/scripts/clip-win-bridge.sh` over
  `powershell.exe` interop (one per user, one display).
- RDP client PC ↔ X: `xrdp-chansrv` cliprdr — untrustworthy, text-only in
  0.10.x, no health signal.
- Termux / proot / other Linux boxes / additional Windows PCs: nothing.

**More hosts are coming** (user, 2026-10-30), so the shape must be N agents
over M host types, not a Windows-to-`:40` point fix.

**Proposed capability (one `ft###` to mint at spec-writing):
networked-clipboard-hub.** A single `clipd` daemon owns the current
clipboard state and fans it out; every host runs a thin agent that pushes
local copies and applies remote ones. Bidirectional on every edge.

- **Local surface:** a unix socket `$XDG_RUNTIME_DIR/clipd.sock`, mode 0600.
  JSON-lines protocol — `{op:"set", origin, id, mime, b64}` and
  `{op:"sub"}` → stream of `{op:"event", seq, origin, mime, b64}`.
- **Network surface: SSH only — no TCP listener anywhere.** A remote agent
  spawns `ssh <hub> socat - UNIX-CONNECT:<sock>` and speaks the protocol
  over stdio. Auth and encryption are the existing per-host SSH keys
  (`gwt user register`, `~/.ssh/config.d/`). Windows may alternatively use
  AF_UNIX (Win10 1803+, pwsh 7 `UnixDomainSocketEndPoint`) + `ssh -L` —
  whether Win32-OpenSSH forwards to a client-side unix path is unverified;
  probe before choosing.
- **Echo suppression:** hub never returns an event to its `origin`; each
  agent remembers the hash of what it last applied and does not re-push it;
  ordering is last-writer-wins by hub `seq`.
- **Agents (consumers of the hub API, implementations not features):**
  X (`clipnotify` + `xclip`, every `xclip` under `timeout`), Windows (pwsh,
  `AddClipboardFormatListener`, logon scheduled task), Termux
  (`termux-clipboard-get/set`), and the Quickshell picker as a plain
  subscriber via `Quickshell.Io` `Socket`.

**Constraints (bind the solution):**

- **Every clipboard entry is a secret** (user, 2026-10-30). No
  classification step decides what is sensitive — [[sp015]] already showed
  that detection fails silently (gopass never emits the password-manager
  hint atom). The hint gate from [[ft007]] / `clip-win-bridge.sh` stays as
  an extra *drop* rule, but the baseline handling applies to all content:
  - **End-to-end encrypted between agents.** The hub routes and orders
    ciphertext only; it cannot read payloads (key held by agents, never
    by the hub process). SSH protects the link; E2E protects against the
    hub host itself.
  - **Never persisted, anywhere.** Hub and agents keep payloads in memory
    or under `$XDG_RUNTIME_DIR` only ([[ft007]]'s tmpfs property, extended
    fleet-wide). No payload in logs, traces, error messages or crash
    output — metadata (seq, origin, mime, size) only.
  - **Expiry.** Entries carry a TTL; the hub drops them and agents may
    clear the local clipboard when it lapses if it still holds the
    synced value (gopass `cliptimeout` behaviour, made universal).
  - **No leakage into host clipboard history/cloud.** The Windows agent
    writes with the clipboard formats that exclude Win+V history and cloud
    sync (`ExcludeClipboardContentFromMonitorProcessing`,
    `CanIncludeInClipboardHistory=0`, `CanUploadToCloudClipboard=0`); other
    agents must be checked for equivalent leaks (e.g. Android clipboard).
  - **Least exposure.** An agent only receives events while subscribed;
    nothing is replayed to a newly connecting agent beyond the current
    (unexpired) entry.
  - **Why the KeePassXC hint is still a never-send rule.** "All secret"
    governs *how* an entry travels (E2E, memory-only, TTL) — it is still
    *delivered*, and at the receiving host it is plaintext on that host's
    clipboard, readable by any app there and captured by [[ft007]]'s store.
    `application/x-kde-passwordManagerHint` is the one positive signal that
    a copy is a *known* credential, not merely possibly sensitive; for those
    the right number of other hosts is zero — a password is copied to be
    pasted where it was copied. So hinted copies never leave the origin
    agent, in either direction. Limit: gopass emits no hint ([[sp015]]), so
    gopass copies sync under the baseline protections only.
- **Payload:** text and `image/png` only, explicit size cap, chunking for
  large images; agents never open or execute what arrives.
- **Hang-proof:** every selection read is bounded — the 10-29 hang is the
  failure to design out.
- **Copies, never pastes** — [[adr0010]] carries over to remote agents.

**Tension with existing decisions:** [[adr0011]] chose "bespoke clipnotify
file store, **no daemon**" for [[ft007]]. `clipd` is a daemon. Either the
hub stays strictly a sync transport beside the [[ft007]] store (adr0011
untouched), or the store migrates onto the hub and adr0011 is superseded.
Spec-writing must pick and record it. [[adr0012]] (user-bus singleton
daemon, read-only bar consumers) is the closest precedent for the hub shape.

**Dedup:** [[ft007]] is the nearest feature — it is *history + cross-display
sync on one host*; this is *cross-host sync transport*. Not an extension of
ft007's surface, so a new `ft###`. [[ft006]] (region-capture) puts PNGs on
the clipboard and is an image-sync consumer. [[ft008]] / [[im006]] (combo
picker) is the QML consumer.

**Migration targets:** `clip-win-bridge.sh` (retired), `xrdp-chansrv`
clipboard (left as harmless fallback or disabled via `xrdp.ini` `cliprdr`),
`clip-sync.sh` and `clip-store.sh` (fold into the X agent or stay —
decided with the adr0011 question), the kwi3 launcher's bridge start.

**Scope: LAN only** (user, 2026-10-30). Every agent reaches the hub host
by plain SSH on the local network. Cross-network reach (NAT, mobile data,
home ↔ work) is out of scope for now; the design must not preclude adding
it later via a mesh VPN or `ProxyJump` — E2E payload encryption already
makes a less-trusted hub host acceptable.

**Open questions for spec-writing:**

1. Hub placement with more hosts: which host is always on (the WSL box is
   not), or one hub per site, or agent-to-agent? Single hub is the default.
2. History: hub-side, or stays per-host in [[ft007]]?
3. Agent reconnect/backoff and a visible health signal (the chansrv failure
   was invisible — the replacement must not be).
4. Windows transport: stdio-over-ssh vs AF_UNIX + `ssh -L` (probe).

Categories: [[cat001]] (workflow tooling), [[cat002]] (display platform).

## solution

**Revised 2026-11-03** — replaces the 2026-10-30 hub + SSH-pipe design
(that version is in git history at `d64c1873`). Reasons: a hub needs an
always-on host, which fits "more hosts" badly; a Syncthing folder is
peer-to-peer and already solves discovery, device auth and Windows. The
user accepted ciphertext-at-rest (age-encrypted per entry) in exchange.

Deliver [[ft018]] (clipd-clipboard-sync): **one Go binary, `clipd`** —
Go per [[adr0003]] / [[adr0021]] / [[adr0030]], with `filippo.io/age`
natively; cross-compiled for Windows and Termux from one source.

- **The native clipboard is the source of truth.** Copy writes the native
  clipboard as always; the local `clipd agent` observes the change and
  *additionally* writes an age-encrypted entry into the sync folder. Paste
  reads the native clipboard only — **clipd is never in the paste path**,
  so a sync failure cannot block or hang a paste (the 10-29 incident).
- **Remote entries are pick-on-demand, never auto-applied.** An entry
  arriving from another host stays encrypted in the folder and never
  overwrites the local clipboard. The `$mod+v` picker (already
  `qs-clip.sh toggle`, [[ft007]] / [[ft008]] / [[im006]]) lists remote
  entries beside local history; picking one decrypts it in memory and
  publishes it to the native clipboard — copies, never pastes
  ([[adr0010]]). Plaintext of a remote entry exists only on a host where
  the user chose it.
- **Encryption: age, per entry, per device.** Each device has its own X25519
  identity (local file, 0600, never synced); every entry is encrypted to
  all devices' recipients. Recipients are **pinned in each device's local
  config**, never read from the shared folder (a writer to the folder must
  not be able to add itself). Losing a device = drop its recipient. Entry
  filename is a random id; origin, time, mime and TTL live inside the
  ciphertext.
- **Transport: Syncthing, LAN only.** Dedicated folder, global discovery /
  relays / NAT traversal off, versioning off, conflict copies ignored,
  `fsWatcherDelayS` ≈ 1 (expect ~1-2 s latency). On Linux the folder lives
  on tmpfs (`$XDG_RUNTIME_DIR`), so not even ciphertext touches disk; on
  Windows it is on disk (ciphertext only).
- **Every entry secret:** short TTL; the origin agent deletes its own
  entries at expiry (deletion syncs) and any agent drops expired ones. No
  payload in logs. Password-manager-marked copies are never written to the
  folder: X `application/x-kde-passwordManagerHint`, Windows
  `ExcludeClipboardContentFromMonitorProcessing` (KeePass/KeePassXC,
  Bitwarden, 1Password, …). gopass sets no marker ([[sp015]]) and syncs
  under the baseline protections only. Text + `image/png` only, size cap;
  [[ft006]] screenshots sync as PNG. Nothing received is opened or run.
- **Health:** each agent writes an encrypted heartbeat into the folder;
  `clipd status` shows per-peer last-seen plus Syncthing's REST connection
  state — a dead link is visible, per [[adr0017]]. Restart loops are
  backoff-bounded per [[adr0014]].
- **History stays in [[ft007]]** and stays local; [[adr0011]] (no daemon
  for history) is unchanged — `clipd agent` is a sync daemon, not a
  history store. The picker merges ft007's local store with the folder's
  remote entries.
- **Retires** `clip-win-bridge.sh` and its kwi3-launcher start; the RDP
  client PC becomes a peer with its own agent, so `xrdp-chansrv`'s
  clipboard is no longer relied on and can be disabled once proven.

Categories: [[cat001]], [[cat002]].

**Windows peers are outbound-only** (user, 2026-11-03: managed Windows
devices may forbid inbound firewall rules — the PoC's first listen raised a
Defender prompt). A Windows peer's Syncthing has no listen address and dials
out to a listening Linux/Android peer on the LAN; no inbound rule, no prompt.
Consequence: Windows devices sync *through* a listening non-Windows peer, never
directly with each other. Outbound-only connectivity is unverified — first
check in refinement.

**Evidence:** [[poc024]] validated both open risks — Go Win32 listener
with password-manager-marker detection and history/cloud-excluded publish,
and Syncthing + age transport at ~2.0-2.3 s create/delete latency between
tmpfs and NTFS folders (recommendations carried into refinement).

**Open for refinement:** the Windows-side picker (no QML on Windows — tray
or hotkey `clipd pick`); where device identities live (plain 0600 file vs
KeePassXC/gopass).


## plan

Deliverable: [[ft018]] (feature-add spec — no `us###` / `im###` lineage).
Categories [[cat001]], [[cat002]]. Evidence: [[poc024]].

**Scope decisions (refinement, 2026-11-03, user-approved):**

- Agents in scope: **X** and **Windows**. Termux is deferred to a follow-up
  spec (the entry format and folder protocol below are host-neutral, so it
  adds an agent and nothing else).
- **Windows is CLI-only** in this spec: `clipd.exe list`, `pick <id>`,
  `pick --latest`. The picker UI on Windows will be the *same* Quickshell
  picker, delivered by kwi3 (its win32 host) — out of scope here, and the
  CLI is the surface it will call.
- Device identity: plain age identity file, mode 0600 —
  `~/.config/clipd/identity.txt` (Linux), `%APPDATA%\clipd\identity.txt`
  (Windows). Password-manager-backed storage is a later extension.
- The Go binary is authorised by a **new ADR (Task 1)**: [[adr0003]]'s
  conditions (network listener + stream proxy / hot path) do not hold —
  Syncthing does the networking — so Go needs its own record, the
  [[adr0021]] precedent. That ADR also discharges [[adr0003]]'s
  nushell-wrapper rule: `nushell/actions/clipd.nu` on Linux; on Windows the
  logon scheduled task + CLI.

**File tree:**

    clipd/
      dot.yaml                 rotz: guarded go build (hotkeyd pattern),
                               syncthing install, links; windows: section
      go.mod                   module clipd; deps: filippo.io/age only
      cmd/clipd/main.go        subcommand dispatch
      internal/entry/          plaintext model, encode/decode, size/mime rules
      internal/crypt/          identity load/keygen, pinned recipients, age
      internal/store/          folder IO: write-tmp-rename, list, sweep, hb
      internal/xsel/           clipnotify/xclip driver, all calls timeout'd
      internal/winclip/        Win32 listener + publish (//go:build windows)
      internal/agent/          shared loop: dedupe, echo guard, hint gate
      internal/status/         heartbeat read + Syncthing REST link state
      test-clipd-x.sh          Xvfb end-to-end (repo test-*.sh convention)
    nushell/actions/clipd.nu   setup | peer add | peer rm | status | start | stop
    quickshell/qs-clip.sh      list merges `clipd list` (r: rows); set routes r:
    docs/notes/adr00NN.md      Task 1
    docs/notes/ft007.md        api_surface widened (r: rows) — in this commit

Runtime paths: folder `$XDG_RUNTIME_DIR/clipd/folder` (tmpfs, Linux) /
`%LOCALAPPDATA%\clipd\folder` (Windows); agent state
`$XDG_RUNTIME_DIR/clipd/state/` (last-written + last-picked hashes);
config `~/.config/clipd/{identity.txt,recipients.txt,config.toml}`.

**Entry format** (one file `<16-hex-random>.age`, age-encrypted to every
pinned recipient): plaintext is one JSON object
`{"v":1,"origin":"<device-name>","created":<unix-ms>,"ttl_s":<int>,
"mime":"text/plain;charset=utf-8"|"image/png","data":"<base64>"}`.
Heartbeat: `hb-<device-name>.age`, same envelope with
`mime:"application/x-clipd-heartbeat"`, empty data. Default TTL 300 s,
size cap 8 MiB (configurable, decrypted size).

**Conventions:**

- Every external process (`xclip`, `clipnotify`, `syncthing` REST) is run
  under a `context.WithTimeout`; default 1 s for selection reads.
- Writes are always `.<id>.tmp` then `rename` — Syncthing must never ship a
  partial file ([[poc024]]).
- Password-manager markers are checked **before** any payload read: X
  `application/x-kde-passwordManagerHint` in TARGETS; Windows
  `ExcludeClipboardContentFromMonitorProcessing` present. Marked copies are
  never read, never written.
- Recipients come **only** from local `recipients.txt`; nothing in the
  shared folder can change who an entry is encrypted to.
- Remote entries are never applied automatically; only `clipd pick`
  writes the native clipboard ([[adr0010]]: copies, never pastes).
- Logs carry metadata only (id, origin, mime, size, timings) — never
  payload bytes, never decoded previews.
- Restart / reconnect loops are backoff-bounded and fail fast
  ([[adr0014]]); status claims rest on the component's own evidence
  ([[adr0017]]).

**Anti-patterns (auto-reject in review):**

- Reading the selection before the marker check, or logging/printing a
  payload in an error path.
- Any write of plaintext to disk (including "debug dumps", temp files for
  xclip input — pipe stdin instead).
- Bare `xclip -o` / blocking Win32 `OpenClipboard` loops without a bound.
- Taking recipients from a folder file, or auto-adding peers.
- `panic` on malformed / undecryptable entries — skip and log metadata.
- Applying remote entries to the native clipboard from the agent loop.

**Known limitations:**

- ~2 s sync latency floor (Syncthing watcher) — acceptable for
  pick-on-demand ([[poc024]]).
- Windows peers dial out only (no inbound rule needed on managed devices);
  two Windows peers sync only via a listening Linux peer.
- age has no forward secrecy: a stolen identity decrypts any entry still in
  a folder — bounded by TTL; Windows folder is on disk (ciphertext).
- gopass copies carry no marker ([[sp015]]) and sync under baseline rules.
- [[adr0011]] untouched: history stays in [[ft007]]; `clipd` keeps none.
- Win+V exclusion honoured per Microsoft docs, not machine-verified.

#### success_criteria
- `clipd keygen` writes `identity.txt` mode 0600, refuses to overwrite

- Unknown `v` or mime → rejected on decode.

#### success_criteria
- Display is required (arg or `CLIPD_DISPLAY`); inherited `$DISPLAY` is
  never used (same contract as `clip-sync.sh`); missing → exit 78.
- On each CLIPBOARD change (`clipnotify -s clipboard`): read TARGETS (1 s
  bound); if the password-manager hint is present → skip without reading
  payload; else read `image/png` if advertised, otherwise `UTF8_STRING`;
  write one entry. A hung owner costs ≤1 s and the loop continues.
- Dedupe: same content hash as last written → no new entry; content whose
  hash matches the last `clipd pick` (state file) → not re-sent (echo
  guard). Heartbeat written every 30 s.

#### edge_cases
- Image-only owner advertising `image/bmp` only → skipped (text/png only),
  no laundering into text (see `xclip-serves-any-target`).
- Owner that never answers → timeout, entry skipped, metadata log line.
- Burst of 20 copies in 1 s → each distinct content written once, none
  lost after clipnotify re-arm.
- Folder missing → agent logs and retries with bounded backoff
  ([[adr0014]]), does not exit hot-looping.
