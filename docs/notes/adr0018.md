# ADR [[cat001]] [[product]]

## title
Go for the X-session keystroke daemon

## context
[[ft011]]'s global keybinding daemon (`hotkeyd.py`) is Python + `python-xlib`,
sanctioned under [[adr0015]] condition 1 (an X11-ecosystem binding with
working prior art here). [[sp021]] proposes rewriting it in Go with binds
compiled into the source, dwm `config.h` style. Two feasibility unknowns
blocked that move and are now settled: [[poc014]] proved XI2 passive grabs
work from Go, and [[poc015]] proved a **zero-dependency** stdlib-only client
(no vendored fork) reads the real `:0` and `:10` sessions correctly — static
3.8 MiB binary, `CGO_ENABLED=0`, cross-compiling clean to arm64/arm. What
remained unresolved was not feasibility but authority: no existing ADR
covers "compiled helper for an X11 keystroke daemon" on its own merits.

[[adr0003]] is the repo's standing rule for when a compiled Go helper is
required over nushell/bash, but its gate is a strict three-condition AND:
long-running daemon, **"Websocket/stream proxying or hot-path latency"**,
and no nushell structural fit. hotkeyd satisfies condition 1 and 3 but not
condition 2 — it holds no listener, proxies no stream, and its "hot path" is
one XI2 event per human keystroke, nowhere near a rate where GIL-style
interpreter serialisation would dominate measured latency. Reading condition
2 loosely enough to wave hotkeyd through would make the gate uncitable for
the next daemon that actually needs it. [[adr0008]] set the precedent for
this shape of problem: it admits Rust in place of Go for a *specific
binding-level reason* (wry/tao exists only in Rust) without touching
[[adr0003]]'s gate, layering a narrow, stated-conditions carve-out beside it
instead of stretching the original test.

A second, independent conflict sits underneath the language question. Every
[[adr0003]]-authorised compiled helper is mandated to expose a
`nushell/actions/` wrapper as its user-facing front end — "the binary is an
engine, not an interface." [[adr0015]] already refused exactly that for
X-session keystroke daemons: "Adding a nushell hop in front of a keystroke
daemon would add startup cost on the very path this ADR exists to keep
short," and names the thin shell launcher (`qs-bar.sh`/`qs-notif.sh` shape,
here `hotkeyd.sh` and `hotkeyd-panic.sh`) as the front end instead. Moving
hotkeyd's implementation language from Python to Go does not change the
panic-recovery latency argument that produced that refusal — the daemon
still exists to survive an already-broken session, so the ADR that
authorises Go for it must resolve which mandate wins rather than silently
inheriting [[adr0003]]'s wrapper requirement by virtue of the language
switch.

Options surveyed: (a) leave hotkeyd on Python under [[adr0015]] — abandons
the rewrite the PoCs were commissioned to unblock, and does not address the
liability shape [[sp021]] documents (interpreter dependency on every
graphical platform, runtime-only bind validation, version skew across
Arch/Arch ARM/WSL); (b) stretch [[adr0003]]'s condition 2 to cover
per-keystroke dispatch — rejected, it would make the gate meaningless for
future proposals that cite it honestly; (c) a new ADR, standing on the PoC
evidence and shaped like [[adr0008]], that decides Go for this daemon on its
own merits and explicitly resolves the wrapper-mandate conflict rather than
leaving it implied.

## decision
**Go is authorised for `hotkeyd`, the X-session keystroke daemon, standing
on its own merits — not on [[adr0003]]'s three-condition gate.** This ADR
does not invoke that gate and states why: condition 2 requires "websocket/
stream proxying or hot-path latency" — stream proxying or a measured hot
path where GIL-style interpreter serialisation dominates. hotkeyd holds no
listener and proxies no stream; its dispatch rate is one XI2 event per human
keystroke, which is not a hot path by any measurement this repo has taken.
Borrowing that clause anyway would make it unciteable the next time a
proposal needs to pass it honestly. The merits that DO carry the decision,
established by [[poc014]] and [[poc015]]:

- A static Go binary carries **no interpreter dependency on any graphical
  platform** hotkeyd runs on — native Arch/Manjaro `:0`, WSL, and
  proot-Arch-on-aarch64 — closing the exact liability [[adr0015]] itself
  named as load-bearing-negative for Python: "Python's own dependency
  surface (system packages, version skew across Arch / Arch ARM / Termux /
  WSL) now matters on every platform that runs a graphical session."
- **No `python-xlib` version skew** across those platforms, because there is
  no `python-xlib` — [[poc015]]'s client is 1027 stdlib-only code lines
  owning the ~10 X11/XI2 requests the daemon uses.
- **The bind table is validated by the compiler, not at daemon load time.**
  Binds compile into the source (dwm `config.h` model); a malformed entry is
  a `go build` failure instead of a runtime rejection discovered only once
  the daemon starts.

The shape of this decision follows [[adr0008]]: a language is admitted for a
concrete, binding-level reason, under conditions stated in this ADR, without
reopening or widening [[adr0003]]'s general test. [[adr0003]]'s gate keeps
governing every other proposal for a compiled helper exactly as written.

**Resolving the wrapper-mandate conflict — a stated scope carve-out, not an
implication.** [[adr0003]] mandates a `nushell/actions/` wrapper as the
user-facing front end for every compiled helper it authorises. [[adr0015]]
already refuses that specifically for X-session keystroke daemons, because a
nushell hop in front of a keystroke daemon adds startup cost to the panic-
recovery path — a path whose entire job is to survive an already-broken
session. That reasoning is about what fronts a keystroke daemon, not about
what language the daemon is written in, so it survives the Python-to-Go
move unchanged. **X-session keystroke daemons are therefore carved out of
the [[adr0003]] `nushell/actions/` wrapper mandate**; the existing thin
shell launcher — `hotkeyd.sh` (start/stop/status/health/check) and
`hotkeyd-panic.sh` (the panic path, staying in shell per [[ft003]]) — is the
stated front end for `hotkeyd`, unchanged by this rewrite. This carve-out
covers X-session keystroke daemons; it does not touch [[adr0003]]'s wrapper
mandate for any other compiled helper.

**The zero-dependency invariant is part of the decision, not an
implementation detail.** [[poc015]] validated the zero-dep route
specifically because the alternative — vendoring a patched `jezek/xgb` fork
— arrives bundled with ~30 kLOC of third-party code and a patch to
re-apply on every upstream bump, for a fix ([[poc014]]'s 16-line
`readResponses` gap) that is a bug, not a design conflict. `hotkeyd`'s
`go.mod` require block stays **empty** and `go.sum` stays **absent** for the
life of this daemon: this is the citable decision against a future "just
add one library" PR. A dependency need real enough to justify breaking this
invariant is real enough to justify writing a new ADR, not a silent import.

**Scope — this authorises one daemon, nothing wider.** This decision covers
`hotkeyd` only. It does not flip [[adr0015]]'s status: [[adr0015]] remains
**Accepted**, narrowed rather than superseded — it continues to sanction
Python for the repo's other X-ecosystem clients (`qs-keymon.py`,
`qs-region.py`, `qs-focus-border.py`, `i3/test-events.py`, and their pytest
suites), none of which this ADR touches. No sweep of the repo's Python X
clients is authorised by this decision, and none should be inferred from
it.

## consequences
**Positive.** hotkeyd gets a static binary with zero interpreter dependency
on every graphical platform it runs on, closing [[adr0015]]'s own named
liability for this specific daemon. The bind table's 42 validation rules
move from runtime to compile time. [[poc015]]'s client cross-compiles clean
to arm64/arm from one machine, covering proot-Arch-on-aarch64 without a
cross-toolchain. The `getattr`-based seams ([[sp021]] problem item 4) become
real Go interfaces, so a test double missing a method is a compile error
instead of a silent no-op in production. The wrapper-mandate conflict is
resolved explicitly here rather than left for a future reviewer to guess
at, and [[adr0015]] stays intact for the daemons it still correctly governs.

**Negative, and load-bearing.** A Go toolchain becomes a build-time
dependency on every host that builds `hotkeyd` (`hotkeyd/dot.yaml` needs a
`command -v go` guard). `SIGHUP` live table reload is lost — [[ft011]]'s
promise to re-register only changed grabs without ever dropping one
mid-gesture cannot survive binds-in-source, so reload becomes rebuild +
`hotkeyd.sh restart`, and [[ft011]] must be amended to say so rather than
state something false. The zero-dependency invariant is a standing tax:
every future capability that would normally come from a well-known library
must instead be hand-rolled or vendored-and-justified through a new ADR,
and [[poc015]]'s 1027 lines of hand-owned X11/XI2 wire-protocol code are now
this repo's maintenance surface, not upstream's — mitigated, not erased, by
the fact that [[poc015]] validated that code against the real `:0` and
`:10` sessions rather than a synthetic rig. The repo now carries two
sanctioned languages for X-session daemons under two different ADRs
([[adr0015]] for Python, this one for Go); a future contributor must check
which ADR governs a given binary rather than finding one uniform rule, and
that bookkeeping cost is accepted deliberately rather than resolved by
forcing every X client onto one language.
