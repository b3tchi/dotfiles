# ADR [[cat002]] [[cat001]] [[product]]

## title
self-respawning reader loops fail fast and are rate-bounded when their
runtime dir vanishes

## context
The notification daemon ([[im008]], [[ft010]]) owns a command FIFO
under `$XDG_RUNTIME_DIR` and reads it with a shell loop —
`while :; do mkfifo …; timeout 2 cat "$FIFO"; done` — respawned by the
hosting QML `Process` whenever the shell exits ([[adr0012]]). During
[[sp019]] execution this shape turned into a fork bomb the moment the
FIFO's parent directory vanished (XDG runtime dir torn down under a
live session): `mkfifo` failed silently, `cat` returned instantly on
ENOENT, and the loop burned two forks per iteration unbounded —
measured at 2814 forks/sec and 77.5% sys CPU before the fix landed
(commit d069180).

The hazard is not specific to this FIFO. Any daemon-side reader that
re-establishes itself against a runtime path that can disappear
(FIFO readers, `tail -F` state-file followers — `Bar.qml` already
wraps its feeds in restart timers) has the same failure mode: the
loop's precondition is gone, every iteration fails instantly, and an
unbounded retry becomes a CPU/fork storm instead of a quiet outage.

## decision
Every self-respawning reader loop is bounded by three layered guards,
none of which may be dropped:

1. **Fail fast on unrecoverable setup** — the setup step exits the
   loop instead of being retried inline (`mkfifo … || exit 1`). A
   loop cannot re-establish its own vanished precondition from the
   inside; it must die and let the layer above decide.
2. **A sleep floor on every iteration** (`sleep 0.2` here) so that no
   present or future fast-fail path inside the loop can pin a core,
   whatever the failure is.
3. **Respawn bounded by a timer outside the loop** — the hosting
   process's exit handler restarts through a fixed-interval timer
   (`onExited → 500 ms Timer`), never immediately. The timer is both
   the rate limit and the retry path: the runtime dir may come back,
   and when it does the next respawn's setup succeeds.

## consequences
A vanished runtime dir now costs roughly two respawns per second of
negligible work instead of thousands of forks; recovery is automatic
when the directory returns, with no operator action. Worst-case
command latency after a FIFO recreate is bounded by the `timeout 2`
read plus the sleep floor — accepted, commands are human-initiated
dismissals.

This is the house pattern for any new reader loop in the session
stack: an unbounded `while :; do spawn; done` around a fallible setup
step is a defect, not a style choice. Reviewers may reject such a
loop by citing this ADR. Dropping any of the three guards (e.g.
"the dir can't vanish here") reopens this decision.
