# ADR [[cat001]] [[product]]

## title
tmux hosts and displays agent workers; it never carries their messages

## context
[[ft014]] runs Pi workers as named windows in a linked tmux project group so an
operator can watch them work. Once tmux is already in the picture, it offers
several things that look like a message channel and cost nothing to reach for:

- `send-keys` delivers a string to a pane;
- `wait-for` blocks until a named channel is signalled;
- pane and window options (`@name`) store arbitrary values per target;
- `display-message` shows text.

Each of these genuinely works in a demo. [[poc022]] used `wait-for` to detect
worker completion and it functioned correctly.

None of them survives contact with the properties this pipeline needs. They
cannot be versioned, so a protocol change is undetectable. They cannot be
sequenced, so ordering is whatever arrives. They cannot be replayed, so an
orchestrator that dies between reading and acting has lost the message. And
they are addressed by tmux target, which is the sharpest edge: window and pane
ids are RECYCLED. A worker's window closes, a new window takes the slot, and a
`send-keys` aimed at the old target now types its text into whatever occupies
it — a shell, an editor, another agent's session.

## decision
tmux is the display and process host for workers and nothing else. The only
tmux operations permitted are window and process lifecycle: `new-window`,
`list-windows`, `kill-window`, `list-panes`, and reading a pane for inspection.

No `send-keys`, no `wait-for`, no `display-message`, and no pane or window
option used as storage. Display options that change how tmux itself presents a
window (`remain-on-exit`, which keeps a crashed worker's error on screen) are
allowed; user options (`@name`) are not, because their only purpose is holding
values.

Messages travel exclusively as versioned, sequenced JSON envelopes in a
run-scoped runtime directory. Workers are addressed by stable UID and window
NAME, never by `@window-id` or `%pane-id`.

## consequences
The bus has to exist and be maintained — atomic writes, sequence claiming,
delivery acknowledgement — where `wait-for` would have been one line. That
weight buys replay after a crash, at-least-once delivery, cross-run isolation,
and a protocol that can be versioned.

Liveness still comes from tmux, because that is a display question. A missing
window means "not found", which per [[adr0017]] is an observation and never a
licence to clean up.

This decision is enforced, not merely documented: static checks fail the build
if a forbidden verb appears as executable code rather than as a prohibition, and
a live test puts a shell in a reclaimed window slot, completes a worker, and
asserts the pane is byte-identical afterwards.

If a future adapter needs a message channel tmux appears to offer, that is a
reason to supersede this ADR deliberately — with an argument about replay,
sequencing and stale targets — rather than to add one call and see if anything
breaks.
