# ADR [[cat001]] [[cat002]] [[product]]

## title
Go for clipd, the cross-host clipboard agent

## context
[[sp039]] replaces the xrdp-chansrv clipboard channel and
`clip-win-bridge.sh` with [[ft018]]: one `clipd` binary per host that
watches the native clipboard, writes each copy as an age-encrypted file
into a LAN-only Syncthing folder, and decrypts a remote entry only when
the user picks it from the `$mod+v` picker. It must run on the Linux X
sessions (`:40` kwi3, `:10` i3) and natively on the Windows host, and the
same source should later serve Termux.

[[adr0003]] is the standing rule for a compiled Go helper, a strict
three-condition AND. clipd meets only condition 3 (a clipboard event loop
is not a pipeline that completes and exits). Condition 1 is a long-running
daemon *holding open network listeners*: clipd runs long, but holds **no
listener** — Syncthing owns the transport. Condition 2 is stream proxying
or a hot path where interpreter cost dominates: clipd proxies no stream,
and its event rate is one clipboard change per human copy. Stretching
either condition to cover it would make the gate uncitable for the next
daemon that honestly needs it. [[adr0021]] (hotkeyd) and [[adr0030]]
(agent-monitor) set the precedent for this shape: admit Go on stated,
binding-level merits without widening [[adr0003]].

The merits are concrete; the Win32 one was measured in [[poc024]]:

- **Win32 clipboard from one cgo-free binary.** [[poc024]] built a
  `GOOS=windows CGO_ENABLED=0` Go program on raw `syscall.NewLazyDLL`
  calls: `AddClipboardFormatListener` on a message-only window, the
  `ExcludeClipboardContentFromMonitorProcessing` check, and writes carrying
  `CanIncludeInClipboardHistory=0` / `CanUploadToCloudClipboard=0` all
  worked. Nushell cannot own a window message loop; pwsh can, but
  only as a second implementation of the whole agent.
- **age in-process.** `filippo.io/age` is the reference implementation, in
  Go. Encrypting and decrypting in-process means plaintext never crosses a
  pipe to an `age` child, and no `age` binary is needed on Windows.
- **One source, three targets.** The same module builds for `linux/amd64`,
  `windows/amd64` and, later, `linux/arm64` (Termux). The arm64 target is
  not yet proven for clipd; [[poc015]] showed a cgo-free Go module
  cross-compiling clean to arm64 for hotkeyd. A shell agent on Linux plus
  a pwsh agent on Windows would be two implementations of the entry
  format, TTL and never-send rules — the security-critical part — drifting
  independently.

Options surveyed: (a) nushell/sh agent on Linux plus pwsh on Windows —
two implementations of the secret-handling path, plaintext piped through
`age` children, rejected; (b) stretch [[adr0003]] condition 2 — rejected,
same reasoning as [[adr0021]]; (c) a new ADR, on the [[poc024]] evidence,
that decides Go for clipd and states its wrapper surface explicitly.

## decision
**Go is authorised for `clipd` ([[ft018]]), standing on its own merits —
not on [[adr0003]]'s three-condition gate.** Conditions 1 and 2 do not
hold (no listener, no stream, human-rate events) and this ADR does not
borrow them. The decision rests on the three merits above: Win32 clipboard
access from one cgo-free binary, age encryption in-process, and one source
built for Linux, Windows and Termux. The only direct dependency is
`filippo.io/age` (Win32 via stdlib `syscall`); any other direct import
needs a new ADR.

**Wrapper surface — [[adr0003]]'s nushell-wrapper rule, discharged per
platform:**

- **Linux:** `nushell/actions/clipd.nu` is the user-facing front end
  (`setup | peer add | peer rm | status | start | stop`). Users and
  scripts manage clipd through it.
- **Windows:** no nushell is required on the host. The front end is a
  logon scheduled task that runs `clipd.exe agent windows`, set up by
  `clipd/windows/setup.ps1`, plus the `clipd.exe` CLI itself
  (`list | pick <id> | pick --latest | status`) until the Quickshell
  picker reaches Windows through kwi3.
- **Machine callers on the hot or boot path may invoke the binary
  directly:** the session launchers (i3 `exec_always`, the kwi3 session
  script) start `clipd agent x <display>`, and `quickshell/qs-clip.sh`
  calls `clipd list` / `clipd pick`. Same reasoning as [[adr0015]] and
  [[adr0021]]: a nushell hop on the `$mod+v` path or in session start adds
  startup cost where the user is waiting and nothing is gained. This
  carve-out covers these three callers only.

**Scope — this authorises one binary, nothing wider.** It does not touch
[[adr0003]]'s gate or wrapper mandate for any other helper, does not
authorise rewriting the existing `i3/scripts/clip-*` sh daemons in Go
(they are replaced by [[sp039]] or stay as they are), and adds no network
listener: if clipd ever needs one, that is a new decision.

## consequences
**Positive.** One implementation of the entry format, TTL, never-send
rules and age handling runs on every host, so the secret-handling path
cannot drift between platforms. Plaintext never reaches an `age` child
or a temp file; on Linux it passes only through `xclip`'s stdin/stdout.
The Windows agent is a single static `clipd.exe` with no interpreter or
cgo at run time. Termux becomes a new build target, not a port.

**Negative, and load-bearing.** A Go toolchain is a build-time dependency
on every host that builds clipd, Windows included: on Linux
`clipd/dot.yaml` needs the `command -v go` guard and the
build-to-temp-then-move pattern from hotkeyd; on Windows `rotz install
clipd` installs Go via scoop and builds `clipd.exe` natively.
`filippo.io/age` and its transitive `golang.org/x/crypto` are third-party
code in the trust path of every clipboard secret; version bumps need the
same review as code changes. The Linux front end is split between
`clipd.nu` (management) and direct calls from three machine callers, so a
reviewer must check this ADR to know which callers are allowed to skip the
wrapper. The repo now has three Go-on-its-own-merits ADRs ([[adr0021]],
[[adr0030]], this one) beside [[adr0003]]; that bookkeeping is accepted
rather than folded into a wider gate.
