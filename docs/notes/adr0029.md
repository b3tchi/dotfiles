# ADR [[cat001]] [[product]]

## title
agent-census --fast reads accounts' internal state files, opt-in and parity-guarded

## context
[[adr0025]] decided [[ft012]]'s census reads only `claude agents --all
--json` from the claude installation; `~/.claude-*/sessions/<pid>.json` and
`~/.claude-*/jobs/<id>/state.json` were surveyed and explicitly ruled
out-of-bounds. Its own consequences section named the exact reversal
condition: reading those files "REVERSES this decision, which is why it
needs a superseding ADR rather than a quiet patch" -- and separately, "If the
stale-`busy` inaccuracy starts mattering to a real consumer, supersede this
ADR rather than editing it."

`dotfiles-ah7q` shipped exactly that reversal without the ADR: `agent-census
--fast` reads `sessions/<pid>.json` and `jobs/<id>/state.json` directly, and
`--if-changed <stamp>` gates repeat runs on whether those files moved. Both
flags ship today, wired into production (quickshell's `Common/Census.qml`
polls `agent-census --fast --if-changed <stamp> --json` on a 1s timer for
every bar), with no ADR ever recording the decision. This ADR is that
missing record, written after the fact for code already running -- not a
proposal.

The reason: `claude agents --all --json` costs ~0.65 CPU-s per account,
almost entirely Node startup -- ~1.55 CPU-s for the two-account census this
box runs today. Reading the same facts off the two file trees directly costs
~0.025 CPU-s, a ~60x difference. [[us023]]'s ticker constraint is a consumer
polling every 1-2s; at 1.55 CPU-s a run that consumer alone would burn a
fifth of a core continuously. `--if-changed` layers on top and drops the
common no-op case further (measured ~0.045 CPU-s), but only the file-read
path makes the *rare* case -- something actually changed -- affordable at
all.

What is read, concretely: `sessions/<pid>.json` (one per session process:
pid, procStart, kind, cwd, sessionId, name, status -- rewritten on every
status change) and `jobs/<id>/state.json` (the durable job record: state,
name, cwd, sessionId -- survives the process). Both are internal and
undocumented; nothing upstream promises their shape survives a claude
upgrade. That is the whole risk this ADR has to price, not remove.

## decision
`agent-census --fast` (and its `--if-changed` gate) is authorised to read
`sessions/<pid>.json` and `jobs/<id>/state.json` directly, joining a
background session to its job record the same way the CLI-backed path
joins them, and shaping the result into the identical row schema so nothing
downstream can tell which probe produced a row. This narrowly reverses
[[adr0025]] for exactly this one opt-in path.

[[adr0025]]'s underlying principle survives everywhere else, unchanged:
`agent-census` run without `--fast` -- what a human gets by default, and
what any consumer gets that never asks for the flag -- still reads only the
supported `claude agents --all --json`. `tmux`, `ps`, and the `ft001`
registry are still read directly and nothing else. This ADR carves out one
flag; it does not reopen the general rule.

Admission is conditioned on two things holding together, not on the CPU
numbers alone:

1. **Opt-in only, never default.** `--fast` must be passed explicitly. A
   human running `agent-census` bare, and any future consumer that does not
   ask for it, keeps getting the supported command and none of this ADR's
   risk.
2. **A standing, live parity guard.** `tests/agent-census/probe-cases.nu`
   runs BOTH probes against the real, live machine and asserts their output
   is identical as a set (`sessionId`, `kind`, `state`, `status`, `cwd`) --
   case `"probe/fast agrees with the CLI on this machine"`. Verified during
   this ADR by two methods: (a) a synthetic control -- identical rows pass,
   one field flipped in a scratch copy fails -- confirming the case actually
   compares rather than merely invoking both probes; (b) it is failing RIGHT
   NOW on this machine against real data (see consequences). A reshaped or
   drifted internal layout must surface as this case going red, never as a
   consumer that has quietly gone wrong. On a machine with no claude account
   the case must skip loudly (a `PENDING` line in the suite tally), never
   pass by vacuously agreeing that two empty answers match -- a comparison
   that never ran is not evidence the guard works.

Scope: this authorises exactly the `--fast`/`--if-changed` pair in
`nushell/actions/agent-census`. It does not authorise any other tool or
consumer to read claude's `jobs/`/`sessions/` trees directly, and does not
touch the `tmux`, `ps`, or registry reads [[adr0025]] already sanctioned.

## consequences
**Positive.** A 1s-cadence consumer becomes affordable at all: ~1.55 CPU-s
per two-account census drops to ~0.025-0.1 CPU-s via `--fast`, and further
to ~0.045 CPU-s in the common unchanged case via `--if-changed`. This is
what lets [[sp030]] widen the census (Task 6) and build a polling roster
(Task 8) without paying a CLI round trip on every refresh tick.

**Negative, and load-bearing.** The fast path depends on a layout nothing
upstream promises. `shape-fast-agents` reads fields with `get -o` (optional)
throughout, so a claude upgrade that renames or drops a field does not raise
-- it silently drops or nulls a row. The failure mode is therefore the
parity case going red in a test run, not a runtime error in a consumer:
`Common/Census.qml`'s `Process` block has no fallback logic of its own, so a
reshape between releases would render subtly wrong badges on the bar,
quietly, until a maintainer runs the suite (or otherwise notices) and fixes
the mapping. There is no automatic runtime fallback to the supported probe.
The mitigation, until the mapping is fixed, is manual: drop `--fast` from
time-sensitive consumers (edit `Common/Census.qml`'s command list, or point
`QS_CENSUS_CMD` at a wrapper that omits it) so they fall back to the
supported command while the parity failure is triaged.

The stale-`busy` inaccuracy [[adr0025]] accepted (`dotfiles-ubc4.9`) is
**not resolved by this decision -- it stays open.** The fast probe reads
whatever `status` was last WRITTEN to `sessions/<pid>.json`; it never reads
`updatedAt`/`statusUpdatedAt` for freshness, so an abandoned session
reporting stale `busy` is exactly as miscounted via `--fast` as via the CLI
this ADR now runs alongside. Verifying this ADR surfaced the mirror case
live, not hypothetically: sessionId `ea4fa227-...` (kwi3) had
`sessions/2602084.json` on disk reading `status: "shell"` while
`claude agents --all --json` reported `busy` for the identical session at
the same moment -- the persisted value lagging the CLI's own live
determination in the other direction from ubc4.9's original report. Filed
as `dotfiles-v1in` rather than absorbed silently into this ADR's scope.

The parity guard itself currently falls short of its own "skip loudly"
condition: `probe-cases.nu` takes an early `return` in its no-account /
CLI-empty branches, and nushell's `return` inside a closure run via `do`
exits the enclosing `run-case`, which still reports `{status: "pass"}` --
indistinguishable in `run-tests.nu`'s tally from a real comparison, even
though the harness ships a `pending()` helper built for exactly this case.
Filed as `dotfiles-jpmj`; until it lands, a clean run on an account-less
clone reads as an ordinary pass rather than a marked skip.
