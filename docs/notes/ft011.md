# Feature [[cat002]] [[product]]

## providing
One Python-owned global keybinding layer for X11 sessions (native `:0`,
xrdp `:10`): it grabs chords on the root window itself and dispatches to
i3 over a persistent IPC connection, becoming the single source of truth
for global binds instead of the `bindsym` / `bindcode` tables scattered
across i3 entry points and modes. Consumed by [[ft003]] (i3-config
layering), whose base config keeps one hardcoded panic bind that returns the
keyboard to i3 — stopping the daemon, linking a real fallback bind table, and
reloading — and by [[ft009]] (mode-bar control), whose host reads
layer state off the daemon's channel instead of parsing i3 binding
events. Recovery means "give the keyboard back to i3", not "restart the
daemon": a restart helps only when the daemon is dead, and not at all when it
is alive and wrong. It buys what i3 cannot express: layers with timeouts, key
sequences, repeat counts (`3j`), per-window conditional binds, and TRUE
held-modifier state — the nav mode's move/resize indicator today needs
`nop` marker binds precisely because i3 cannot report a held modifier.
Migration is per-group cutover, never duplication: a chord lives in
EITHER i3 or the daemon, because a chord bound in both double-fires. A
migration group is a **grab-ownership closure**, not a concept — two X clients
cannot hold a passive grab on one chord, so a grab-based daemon can never
shadow an i3 global the way an i3 binding *mode* can. The group is therefore
every chord that would be owned twice on *any* display, resolved per display
(`$mod` is `Mod4` on `:0`, `Mod1` on `:10`), expanded until closed. Scoping a
group conceptually is what reverted the first nav cutover ([[sp020]]).
Out of scope: sway (no active session), and app-internal keys (nvim,
tmux, quickshell pickers) — those are not global binds and no global
layer can own them.

## api_surface
Daemon, one process per display:

    hotkeyd.py [--display :0] [--binds hotkeyd/binds.py] [--check]

`--check` loads and validates the table, prints conflicts, exits without
grabbing (the i3 `-C` equivalent once binds leave i3). `check --ownership`
emits, per display, chord → resolved modifier → owner (`i3` / `daemon` /
`neither` / `BOTH`), generated by parsing i3's live bind table and `binds.py`,
and exits non-zero on any `BOTH` row. It is the gate on every cutover commit;
hand-auditing a table across two `$mod` values is what failed the first time.

Mechanism is a per-chord passive grab on the root window — the same thing i3
and sxhkd do — never `XGrabKeyboard` / `XIGrabDevice`: an exclusive grab means
a hung daemon locks the session, while per-key grabs degrade to "that one key
stops working".

Grabs go through **XI2 (`XIGrabKeycode` against `XIAllMasterDevices`)** rather
than core `XGrabKey`, because a core `KeyPress` carries no device identity and
the daemon must be able to tell one keyboard from another — and a real
keystroke from an injected one. `XIDeviceEvent.sourceid` is the only channel
that does so, since injection and real input share a display. `python-xlib`
ships no XI2 event parser; the struct is unpacked by hand, as
`quickshell/qs-keymon.py` already does. Measured inventory: `:0` has
`AT Translated Set 2 keyboard` (12), `BlueZ` (13), `Acer WMI hotkeys` (14);
`:10` has `xrdpKeyboard` (7); both have `XTEST` (5). Binds may scope to a
device, and XTEST-sourced events may be dropped:

    Bind("h", "focus left", device="AT Translated Set 2 keyboard")
    IGNORE_DEVICES = ["Virtual core XTEST keyboard"]

XI2 grabbing does NOT relieve the ownership constraint — an XI2 passive grab
contends with i3's core passive grab identically. Device identity and grab
ownership are orthogonal axes.

Bind table is a Python module (composition beats a parser: workspace
`1..8` loops, per-layer tables, shared command builders), exporting two
names:

    BINDS = [
        Bind("$mod+Shift+q", "kill"),
        Bind("$mod+o", enter_layer("nav")),
        Bind("$mod+Shift+d", run("~/.dotfiles/quickshell/qs-start.sh"),
             on_release=True),
    ]

Per-screen handling lives in the event layer: the daemon knows which display it
owns and resolves the screen-specific values itself — the modifier `$mod` binds
to, the `qsenv` prefix, the terminal command. One table, screen-aware; never a
second table or a per-display copy kept in sync by hand.

While i3 still owns binds in a group, the daemon's `$mod` MUST equal i3's, so
both read the same source: the `i3wm.mod` X resource
(`set_from_resource $mod i3wm.mod Mod4`, [[ft003]]), with the xrdp session
merging `i3wm.mod: Mod1`. Agreement by construction, because a hardcoded
modifier is wrong on one display — and worse, FREE there, so the daemon would
own a chord i3 does not. Once a group is fully migrated the daemon is its sole
grabber and simply defines the value; do not take that shortcut earlier.

    LAYERS = {
        "nav": Layer(
            binds=[Bind("h", "focus left"), ...],
            mods={"move":   Mod("Ctrl", [Bind("h", "move left"), ...]),
                  "resize": Mod("Mod1", [Bind("h", "resize shrink width "
                                              "5 px or 5 ppt"), ...])},
            exit_keys=["q", "Escape", "Return"],
        ),
    }

An action is an i3 command string, a `run(...)` spawn, a layer verb
(`enter_layer` / `exit_layer`), or any Python callable taking the event.
The loader rejects a duplicate chord within a layer, a reference to a
layer that does not exist, and an empty command — that validation is what
replaces i3's own duplicate-binding detection. It runs on EVERY load path,
not only under `--check`: startup, `SIGHUP` reload, and the escape-hatch
restart all refuse an invalid table, and a refused reload keeps the running
one rather than taking the daemon down with it.

State channel: a unix socket at
`$XDG_RUNTIME_DIR/hotkeyd-<display>.sock`, one JSON object per line on
every layer or held-modifier change. A connecting client is replayed the
current state first, so a bar that starts late is never blank:

    {"layer": "nav", "mod": "move"}
    {"layer": "nav", "mod": null}
    {"layer": "default", "mod": null}

Reload is `SIGHUP` (re-read the table, re-register only the grabs that
changed; never drop grabs mid-gesture).

Front-end is a thin shell launcher in the `qs-bar.sh` / `qs-notif.sh` shape,
per [[adr0015]] — not a `nushell/actions/` wrapper, which would add nushell
startup cost to the restart path:

    hotkeyd.sh start | stop | restart | status | check [--ownership]
    hotkeyd-panic.sh panic | resume

Every consumer goes through the launcher: the session entry points call
`start`, and `check` is the pre-commit / post-edit validation path.

`hotkeyd-panic.sh` is the recovery path and the one thing i3 keeps bound
(`$mod+Shift+F12`). `panic` stops the daemon on this display — grabs die with
the client, so X drops them — links `i3/config.d/zz-fallback-binds.conf` into
`~/.i3/config.d/`, and runs `i3-msg reload`, after which i3 holds passive grabs
on every chord the fallback names. `resume` reverses it. There is no
contested-chord window: grabs die before i3 re-establishes its own. The
fallback file is the REAL bind table, kept in the repo and checked by `i3 -C`
in the suite — a stub that rots is discovered during the outage it exists for —
and the `zz-` prefix keeps it last in the `config.d/*.conf` glob so it
overrides anything an overlay set earlier. The panic chord is RESERVED: the
validator refuses any table that binds it, so a future edit cannot quietly take
the one key that recovers the session. `status` exits non-zero when no daemon
is running for the display. It identifies the daemon by its own `--display`
argv rather than by a pidfile or the lock: a pidfile goes stale after a
`SIGKILL` and then lies about a daemon that is not there — which is precisely
the state the escape hatch exists to recover from.

## data_model
No persistence. In-memory state is the layer stack plus the held-modifier
set, published on the socket and owned by the daemon alone. Runtime
files, both per display so native `:0` and xrdp `:10` never collide (the
`qs-session.sh` scoping pattern): the socket above, plus an `flock`
single-instance lock at `$XDG_RUNTIME_DIR/hotkeyd-<display>.lock` (same
guard as `quickshell/qs-focus-border.py`). Grabs live in the X server and
die with the process — which is why the escape hatch stays in i3.

## sample
Cutover shape for one group — the bind leaves i3 in the same commit it
appears in the table:

    # i3/config.common — REMOVED (moved into hotkeyd/binds.py)
    # bindsym $mod+o mode "nav"
    # mode "nav" { bindsym h focus left ... }

    # i3/config.common — KEPT: panic bind, never migrated
    bindsym $mod+Shift+F12 exec --no-startup-id \
        ~/.dotfiles/hotkeyd/hotkeyd-panic.sh panic

Bar host reading the channel (replaces `subscribe ["mode"]` parsing):

    Process {
        command: ["socat", "-u",
                  "UNIX-CONNECT:" + root.runtimeDir
                      + "/hotkeyd-" + root.display + ".sock", "-"]
        stdout: SplitParser {
            onRead: data => {
                const s = JSON.parse(data)
                root.currentMode = s.layer
                root.activeMod   = s.mod        // null when none held
            }
        }
    }

xrdp caveat carried over from the i3 implementation: the session
synthesises Shift around every character it sends, so a held Shift is not
observable there — the daemon sees the same churn i3 did. Modifier layers
use Ctrl / Alt, and the 120 ms release fall-back guard stays. That guard is
conditional on an unanswered question: if the synthesised Shift arrives as
XTEST (5) while real keys arrive as `xrdpKeyboard` (7), source filtering
removes the ambiguity and the guard goes. It cannot be settled by injection —
XTEST is what a harness injects with — so it needs a human at a real RDP
client ([[sp020]] Task 15).

## components
Shipped through T5 of epic `dotfiles-hwds`. The first nav cutover (T6) shipped
and was reverted (`fd9e9f2`) for scoping the group conceptually rather than by
grab ownership; the directional-group cutover ([[sp020]] Task 14) is what flips
this Feature from `proposed` to load-bearing:

- [hotkeyd/hotkeyd.py](../../hotkeyd/hotkeyd.py) — `GrabManager` (per-chord
  grabs incl. lock-bit variants, keysym-first resolution, compare-then-regrab
  on `MappingNotify`), `I3Client` (one persistent IPC connection),
  `SingleInstance` (flock per display), `Daemon` (grab -> dispatch -> publish).
  Grabs move from core `XGrabKey` to `XIGrabKeycode` at [[sp020]] Task 11
- [hotkeyd/hotkeyd-panic.sh](../../hotkeyd/hotkeyd-panic.sh) — panic / resume;
  the recovery path i3 keeps bound
- [i3/config.d/zz-fallback-binds.conf](../../i3/config.d/zz-fallback-binds.conf)
  — the real fallback bind table, `i3 -C`-checked in the suite
- [hotkeyd/binds.py](../../hotkeyd/binds.py) — declarative bind table + the
  validator that replaces i3's duplicate-binding detection
- [hotkeyd/layers.py](../../hotkeyd/layers.py) — layer engine + state
  channel publisher
- [hotkeyd/hotkeyd.sh](../../hotkeyd/hotkeyd.sh) — launcher
  (start/stop/restart/status/check), the only entry point consumers call
- [hotkeyd/dot.yaml](../../hotkeyd/dot.yaml) — `python-xlib` install; NO links
  (the tree runs in place, so only one bind table ever exists on disk)
- [hotkeyd/test-hotkeyd.sh](../../hotkeyd/test-hotkeyd.sh) — runtime suite
  entry point (unit suites, `--check` contract, live X under Xvfb + real i3)
- [hotkeyd/test-launcher.sh](../../hotkeyd/test-launcher.sh) — lifecycle suite
  (two displays at once, escape-hatch path, degraded environments)
- [hotkeyd/live_check.py](../../hotkeyd/live_check.py) — live-X assertions
  driving the real `Daemon`
- [i3/config.common](../../i3/config.common) — binds move OUT per group;
  keeps the `$mod+Shift+F12` panic bind, permanently un-migrated
- [i3/config.d/native.conf](../../i3/config.d/native.conf),
  [i3/config.d/wsl.conf](../../i3/config.d/wsl.conf) — `exec_always` autostart,
  one daemon per display
- [i3/test-nav-mode.sh](../../i3/test-nav-mode.sh) — existing nav suite,
  re-pointed at the daemon (asserts real focus/move/resize effects)
- [quickshell/qs-keymon.py](../../quickshell/qs-keymon.py) — prior art:
  the XI2 raw-event listener this layer's grab loop supersedes for
  global-bind purposes
