# Feature [[cat002]] [[product]]

## providing
One Python-owned global keybinding layer for X11 sessions (native `:0`,
xrdp `:10`): it grabs chords on the root window itself and dispatches to
i3 over a persistent IPC connection, becoming the single source of truth
for global binds instead of the `bindsym` / `bindcode` tables scattered
across i3 entry points and modes. Consumed by [[ft003]] (i3-config
layering), whose base config keeps one hardcoded panic bind that returns the
keyboard to i3 — stopping the daemon, linking a real fallback bind table, and
reloading — and by [[ft009]] (mode-bar control), whose host reads
layer state off the daemon's channel instead of parsing i3 binding
events. Recovery means "give the keyboard back to i3", not "restart the
daemon": a restart helps only when the daemon is dead, and not at all when it
is alive and wrong. It buys what i3 cannot express: layers with timeouts, key
sequences, repeat counts (`3j`), and TRUE
held-modifier state — the nav move/resize indicator needed twelve `nop`
marker binds precisely because i3 cannot report a held modifier, and that
whole mechanism is deleted now the daemon simply states which modifier is
down ([[sp020]] Task 7).
Migration is per-group cutover, never duplication: a chord lives in
EITHER i3 or the daemon, because a chord bound in both double-fires. A
migration group is a **grab-ownership closure**, not a concept — two X clients
cannot hold a passive grab on one chord, so a grab-based daemon can never
shadow an i3 global the way an i3 binding *mode* can. The group is therefore
every chord that would be owned twice on *any* display, resolved per display
(`$mod` is `Mod4` on `:0`, `Mod1` on `:10`), expanded until closed. Scoping a
group conceptually is what reverted the first nav cutover ([[sp020]]).
Out of scope: sway (no active session), and app-internal keys (nvim,
tmux, quickshell pickers) — those are not global binds and no global
layer can own them.

**Scope note, added 2026-07-28.** This list previously also claimed
"per-window conditional binds" and "layers with timeouts". Neither appears in
[[us019]], which asks for *sticky layers, held-modifier sub-layers, key
sequences, repeat counts* — four things. Both were added downstream as
justification rather than requirements, and repeating them back made the
delivery gap look larger than it is. Removed. Add them again only if someone
actually asks.

## api_surface
Daemon, one process per display:

    hotkeyd.py [--display :0] [--binds hotkeyd/binds.py] [--check]

`--check` loads and validates the table, prints conflicts, exits without
grabbing (the i3 `-C` equivalent once binds leave i3). `check --ownership`
emits, per display, chord → resolved modifier → owner (`i3` / `daemon` /
`neither` / `BOTH`), generated by parsing i3's live bind table and `binds.py`,
and exits non-zero on any `BOTH` row. It is the gate on every cutover commit;
hand-auditing a table across two `$mod` values is what failed the first time.

Mechanism is a per-chord passive grab on the root window — the same thing i3
and sxhkd do — never `XGrabKeyboard` / `XIGrabDevice`: an exclusive grab means
a hung daemon locks the session, while per-key grabs degrade to "that one key
stops working".

Grabs go through **XI2 (`XIGrabKeycode` against `XIAllMasterDevices`)** rather
than core `XGrabKey`, because a core `KeyPress` carries no device identity and
the daemon must be able to tell one keyboard from another — and a real
keystroke from an injected one. `XIDeviceEvent.sourceid` is the only channel
that does so, since injection and real input share a display. `python-xlib`
0.33 supports this path directly: `Xlib.ext.xinput` exposes `grab_keycode` /
`XIPassiveGrabDevice` and registers a parsed `DeviceEventData` carrying
`deviceid`, `sourceid`, `detail` and `mods`. Hand-unpacking (what the deleted
`quickshell/qs-keymon.py` did) is needed only for XI2 *raw* events, which have
no registered parser. Attribution reads `sourceid` (the physical slave), never
the `deviceid` in the event header (the master) — reading the header would
report every keyboard on a display as `Virtual core keyboard`. Measured
inventory: `:0` has `AT Translated Set 2 keyboard` (12), `BlueZ` (13),
`Acer WMI hotkeys` (14); `:10` has `xrdpKeyboard` (7); both have `XTEST` (5).
Binds may scope to a device, and a source may be dropped outright:

    Bind("h", "focus left", device="AT Translated Set 2 keyboard")
    IGNORE_DEVICES = ["Virtual core XTEST keyboard"]

Two binds on one chord scoped to different devices are NOT duplicates — the
source disambiguates them at dispatch — while two on one chord with the same
scope still are. `IGNORE_DEVICES` ships **empty**: XTEST is what `xdotool` and
every harness here inject with, and whether xrdp's synthesised Shift is
XTEST-sourced is unmeasured, so nothing is dropped until [[sp020]] Task 15
settles it.

A display without XI2 is fatal and named (`XI2 unavailable …`, exit 5), never a
silent fall back to core grabs: falling back would leave the daemon running
with no device attribution at all and nothing reporting it.

Auto-repeat is read off the event rather than reconstructed. Core delivery
synthesised a RELEASE+PRESS pair per repeat, which the daemon had to coalesce by
timestamp; XI2 sends no synthetic release and sets `XIKeyRepeat` on the press
(measured: a 1.2 s hold delivers 15 presses, 14 flagged, 1 release).

XI2 grabbing does NOT relieve the ownership constraint, but not for the reason
first assumed. **Measured (2026-07-27):** the X server keeps core and XI2
passive grabs in *separate* conflict domains — `GrabMatchesSecond` compares
grabtype — so an XI2 grab over i3's live core grab on the same chord is NOT
refused, and the later grabber wins delivery outright. What still reports
`BadAccess` is a colliding *XI2* grabber, i.e. a second hotkeyd. The practical
consequence is that a chord owned by both i3 and `binds.py` no longer no-ops on
the daemon's side: the daemon starts after i3 and takes it. So ownership
auditing cannot lean on `BadAccess` at all — it belongs to `check --ownership`
— and device identity remains orthogonal to grab ownership.

Bind table is a Python module (composition beats a parser: workspace
`1..8` loops, per-layer tables, shared command builders), exporting two
names:

    BINDS = [
        Bind("$mod+Shift+q", "kill"),
        Bind("$mod+o", enter_layer("nav")),
        Bind("$mod+Shift+d", run("~/.dotfiles/quickshell/qs-start.sh"),
             on_release=True),
    ]

Per-screen handling lives in the event layer: the daemon knows which display it
owns and resolves the screen-specific values itself — the modifier `$mod` binds
to, the `qsenv` prefix, the terminal command. One table, screen-aware; never a
second table or a per-display copy kept in sync by hand.

While i3 still owns binds in a group, the daemon's `$mod` MUST equal i3's, so
both read the same source: the `i3wm.mod` X resource
(`set_from_resource $mod i3wm.mod Mod4`, [[ft003]]), with the xrdp session
merging `i3wm.mod: Mod1`. Agreement by construction, because a hardcoded
modifier is wrong on one display — and worse, FREE there, so the daemon would
own a chord i3 does not. Once a group is fully migrated the daemon is its sole
grabber and simply defines the value; do not take that shortcut earlier.

    LAYERS = {
        "nav": Layer(
            binds=[Bind("h", "focus left"), ...],
            mods={"move":   Mod("Ctrl", [Bind("h", "move left"), ...]),
                  "resize": Mod("Mod1", [Bind("h", "resize shrink width "
                                              "5 px or 5 ppt"), ...])},
            exit_keys=["q", "Escape", "Return"],
        ),
    }

An action is an i3 command string, a `run(...)` spawn, a layer verb
(`enter_layer` / `exit_layer`), or any Python callable taking the event.
The loader rejects a duplicate chord within a layer, a reference to a
layer that does not exist, and an empty command — that validation is what
replaces i3's own duplicate-binding detection. It runs on EVERY load path,
not only under `--check`: startup, `SIGHUP` reload, and the escape-hatch
restart all refuse an invalid table, and a refused reload keeps the running
one rather than taking the daemon down with it.

State channel: a unix socket at
`$XDG_RUNTIME_DIR/hotkeyd-<display>.sock`, one JSON object per line on
every layer or held-modifier change. A connecting client is replayed the
current state first, so a bar that starts late is never blank:

    {"layer": "nav", "mod": "move"}
    {"layer": "nav", "mod": null}
    {"layer": "default", "mod": null}

Reload is `SIGHUP` (re-read the table, re-register only the grabs that
changed; never drop grabs mid-gesture).

Front-end is a thin shell launcher in the `qs-bar.sh` / `qs-notif.sh` shape,
per [[adr0015]] — not a `nushell/actions/` wrapper, which would add nushell
startup cost to the restart path:

    hotkeyd.sh start | stop | restart | status | check [--ownership]
    hotkeyd-panic.sh panic | resume

Every consumer goes through the launcher: the session entry points call
`start`, and `check` is the pre-commit / post-edit validation path.

`hotkeyd-panic.sh` is the recovery path and the one thing i3 keeps bound
(`$mod+Shift+F12`). `panic` stops the daemon — grabs die with the client, so X
drops them — links `i3/config.d/zz-fallback-binds.conf` into `~/.i3/config.d/`,
and runs `i3-msg reload`, after which i3 holds passive grabs on every chord the
fallback names. `resume` reverses it. There is no contested-chord window: grabs
die before i3 re-establishes its own.

**Panic is machine-wide, not per-display.** `~/.i3/config.d/` is one directory
reached by both sessions through the single shared `i3/config` entry point, so
the link cannot be scoped to a display and i3's `include` takes no
conditionals. A panic on `:10` is therefore a file `:0`'s i3 will parse on its
next reload — so `panic` stops the daemon on EVERY display, and `hotkeyd.sh
start` refuses while the link is present (exit 4). Otherwise an `exec_always`
on reload, or an xrdp reconnect, would rearm one display behind the fallback
and recreate the contested state. `resume` is the only way back, which is what
survives a reboot: the link is on disk, the daemon's absence is not.

The fallback file is the REAL bind table, kept in the repo and checked by
`i3 -C` in the suite — a stub that rots is discovered during the outage it
exists for. Its content is the i3 equivalent of what `binds.py` owns MINUS what
i3 still owns, which is not the same as "the binds i3 has today": i3 still owns
its own table, and a duplicate keybinding is a config ERROR to i3, not
last-wins. There is consequently no override story — `zz-` settles the
`config.d/*.conf` glob ORDER and nothing else. The panic chord is RESERVED
(`binds.RESERVED_CHORDS`): the validator refuses any table that binds it under
every spelling — the `$mod` token, `Mod4+Shift+F12` and `Mod1+Shift+F12`,
alias-folded — because the validator is display-agnostic while `$mod` is not,
so a token-only check would leave the chord stealable on one display.
`status` exits non-zero when no daemon
is running for the display. It identifies the daemon by its own `--display`
argv rather than by a pidfile or the lock: a pidfile goes stale after a
`SIGKILL` and then lies about a daemon that is not there — which is precisely
the state the escape hatch exists to recover from.

## data_model
No persistence. In-memory state is the layer stack plus the held-modifier
set, published on the socket and owned by the daemon alone. Runtime
files, both per display so native `:0` and xrdp `:10` never collide (the
`qs-session.sh` scoping pattern): the socket above, plus an `flock`
single-instance lock at `$XDG_RUNTIME_DIR/hotkeyd-<display>.lock` (same
guard as `quickshell/qs-focus-border.py`). Grabs live in the X server and
die with the process — which is why the escape hatch stays in i3.

## sample
Cutover shape for one group — the bind leaves i3 in the same commit it
appears in the table:

    # i3/config.common — REMOVED (moved into hotkeyd/binds.py)
    # bindsym $mod+o mode "nav"
    # mode "nav" { bindsym h focus left ... }

    # i3/config.common — KEPT: panic bind, never migrated
    bindsym $mod+Shift+F12 exec --no-startup-id \
        ~/.dotfiles/hotkeyd/hotkeyd-panic.sh panic

Bar host reading the channel (replaces the `nop nav-` binding-event
reconstruction; the `mode` subscription survives only for the modes i3 still
owns — `resize`, `screenshot`, `$mode_system`):

    Process {
        id: layerFeed
        command: ["python3", root.layerFeedCmd]
        stdout: SplitParser {
            onRead: data => {
                try {
                    const s = JSON.parse(data)
                    root.daemonLayer = s.layer ? String(s.layer) : "default"
                    root.daemonMod   = s.mod   ? String(s.mod)   : ""
                } catch (err) {}      // a malformed line is SKIPPED, not fatal
            }
        }
        onExited: {                   // no daemon: plain bar, never a stale layer
            root.daemonLayer = "default"
            root.daemonMod = ""
            layerFeedRetry.restart()
        }
    }
    Timer { id: layerFeedRetry; interval: 1000
            onTriggered: layerFeed.running = true }

The reader is `hotkeyd/state-tail.py`, not `socat`: socat is absent on this
host, and a QML `Process` can read a child's stdout but cannot open a unix
socket itself. It connects, prints the daemon's lines verbatim, and **exits**
the moment the socket is missing or closes — it never retries internally. That
split is [[adr0014]]: a reader cannot re-establish its own vanished
precondition, so it dies and the host's respawn Timer above is the single,
bounded retry. Measured under a permanently-absent socket directory: 5 reader
spawns over 5 s with the Timer, 64 without it.

A consumer that starts while the daemon is already in a layer is never blank —
the publisher replays the current state to each client at accept time, so the
FIRST line a reader prints is the truth as of now, not the next change.

xrdp caveat carried over from the i3 implementation: the session
synthesises Shift around every character it sends, so the daemon sees the same
churn i3 did. Modifier layers use Ctrl / Alt, and the 120 ms release fall-back
guard stays — **permanently, as of a live-client measurement (2026-07-28)**.
An earlier draft made it conditional on source filtering. A passive XI2 probe
on the live `:10` session with a human typing settled it: every event, real
keystroke and synthetic Shift alike, carries `sourceid 7 (xrdpKeyboard)`.
xrdp injects at the device level, so there is nothing to filter on and
`IGNORE_DEVICES` cannot help here. Measured rather than injected, because
XTEST is what a harness injects with.

Narrower than the old claim: a *bare* held Shift IS observable on `:10`
(balanced press/release over 246 ms and 623 ms holds). What corrupts it is a
character delivered mid-hold — xrdp drops Shift to send the character, so one
physical press yields two releases and the hold looks ended ~900 ms early. The XI2 port supplies the *channel* for that answer
and nothing more: it does not remove the guard, and `IGNORE_DEVICES` stays
empty until the measurement lands.

## components
Shipped through T5 of epic `dotfiles-hwds`. The first nav cutover (T6) shipped
and was reverted (`fd9e9f2`) for scoping the group conceptually rather than by
grab ownership; the directional-group cutover ([[sp020]] Task 14) is what flips
this Feature from `proposed` to load-bearing:

- [hotkeyd/hotkeyd.py](../../hotkeyd/hotkeyd.py) — `GrabManager` (per-chord
  grabs incl. lock-bit variants, keysym-first resolution, compare-then-regrab
  on `MappingNotify`), `XAdapter` + `require_xi2` (the XI2 grab mechanism and
  its fail-fast probe), `key_event` (`XIDeviceEvent` -> the daemon's own record),
  `DeviceRegistry` (`sourceid` -> name, invalidated on hierarchy change),
  `I3Client` (one persistent IPC connection), `SingleInstance` (flock per
  display), `Daemon` (grab -> dispatch -> publish). Grabs moved from core
  `XGrabKey` to `XIGrabKeycode` at [[sp020]] Task 11
- [hotkeyd/hotkeyd-panic.sh](../../hotkeyd/hotkeyd-panic.sh) — panic / resume;
  the recovery path i3 keeps bound
- [i3/config.d/zz-fallback-binds.conf](../../i3/config.d/zz-fallback-binds.conf)
  — the real fallback bind table, `i3 -C`-checked in the suite
- [hotkeyd/binds.py](../../hotkeyd/binds.py) — declarative bind table + the
  validator that replaces i3's duplicate-binding detection
- [hotkeyd/layers.py](../../hotkeyd/layers.py) — layer engine + state
  channel publisher (`StatePublisher`, incl. replay-on-connect)
- [hotkeyd/state-tail.py](../../hotkeyd/state-tail.py) — the reader every
  consumer spawns: connect, print lines verbatim, exit when the socket goes
  ([[adr0014]]; the host owns the retry)
- [hotkeyd/hotkeyd.sh](../../hotkeyd/hotkeyd.sh) — launcher
  (start/stop/restart/status/check), the only entry point consumers call
- [hotkeyd/dot.yaml](../../hotkeyd/dot.yaml) — `python-xlib` install; NO links
  (the tree runs in place, so only one bind table ever exists on disk)
- [hotkeyd/test-hotkeyd.sh](../../hotkeyd/test-hotkeyd.sh) — runtime suite
  entry point (unit suites, `--check` contract, live X under Xvfb + real i3)
- [hotkeyd/test-launcher.sh](../../hotkeyd/test-launcher.sh) — lifecycle suite
  (two displays at once, escape-hatch path, degraded environments)
- [hotkeyd/test-panic.sh](../../hotkeyd/test-panic.sh) — panic / resume suite;
  asserts ownership TRANSFER as a real WM effect (who answers the chord before
  and after), reading i3's loaded table from `get_config`
- [hotkeyd/live_check.py](../../hotkeyd/live_check.py) — live-X assertions
  driving the real `Daemon`
- [i3/config.common](../../i3/config.common) — binds move OUT per group;
  keeps the `$mod+Shift+F12` panic bind, permanently un-migrated
- [i3/config.d/native.conf](../../i3/config.d/native.conf),
  [i3/config.d/wsl.conf](../../i3/config.d/wsl.conf) — `exec_always` autostart,
  one daemon per display
- [i3/test-nav-mode.sh](../../i3/test-nav-mode.sh) — existing nav suite,
  re-pointed at the daemon (asserts real focus/move/resize effects)

Channel CONSUMERS — both were reconstructing nav state from i3 binding events
and went silent when the layer left i3; both now read this socket:

- [quickshell/config/Bar.qml](../../quickshell/config/Bar.qml) — the mode pill

- `quickshell/qs-keymon.py` — DELETED by [[sp020]] (dotfiles-hwds.40). The XI2
