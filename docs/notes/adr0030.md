# ADR [[cat001]] [[product]]

## title
worker windows are addressed by their recorded tmux window id, with the name
as fallback

## context
[[adr0028]] decided that tmux hosts and displays workers and never carries
their messages. That decision is sound and still holds. But it also closed with
a sentence about addressing: "Workers are addressed by stable UID and window
NAME, never by `@window-id` or `%pane-id`." The reasoning was recycling — tmux
window and pane ids are reused, so a stale `@N` eventually points at whatever
now occupies the slot.

The code went the other way the day after adr0028 was written. Commit
`3a1a7145` (2026-09-06, "address worker windows by tmux window_id, not by
name") introduced `window-target`, which prefers a recorded `window_id` and
falls back to the window name only when no id was recorded. `spawn` captures
the id at creation (`new-window -P -F "#{window_id}"`) and stores it in the
identity envelope; `liveness` matches an `@N` exactly and a name loosely.

Nothing recorded that reversal, so an Accepted ADR has been contradicted by
shipped code for four days, discovered while retrospecting [[sp029]].

What changed the calculus is that a window NAME is not stable either. Names are
`<role>-<subject>@<project>`, which collide the moment two runs share a role
and a subject — and before `dotfiles-bg65` that was the DEFAULT for any
dispatcher spawning more than one worker of the same role, because every
ordinary spawn minted `<role>-1`. A name lookup then matches whichever window
sorts first, silently. The recycling hazard adr0028 named is real but bounded:
an id is recycled only after its window closes, and the id is captured at
creation and read back from a durable identity record, so a mismatch surfaces
as "not found" rather than as an action against the wrong target. A name
collision, by contrast, resolves to a WRONG LIVE WINDOW and looks successful.

## decision
A worker's window is addressed by the `window_id` recorded in its identity
envelope when one is present, and by its window name otherwise. This is what
`window-target` implements and what every caller uses instead of reaching for
`identity.window` directly, so an older identity written before ids were
recorded keeps working while a newer one is never addressed ambiguously.

This NARROWS [[adr0028]]'s addressing sentence and leaves the rest of that
decision fully in force: tmux remains display and process host only, no
`send-keys` / `wait-for` / `display-message` as transport, no user options as
storage, and messages continue to travel exclusively as versioned JSON
envelopes on the file bus.

The prohibition adr0028 was reaching for survives in the part that matters:
addressing is never derived from a LIVE tmux query at use time. It comes from
the durable identity record, so the id is as stable as the record that holds
it.

## consequences
A window whose id has been recycled is addressed as "not found" rather than
acted upon, because liveness matches the id exactly and a reaped window does
not answer. Per [[adr0017]] that is an observation and never a licence to stop,
accept or delete — which is the same protection adr0028 wanted, reached by a
different route.

Identity records written before `3a1a7145` carry no `window_id` and stay on the
name path forever. That is intentional and untested-by-design: the fallback
exists so old records keep working, not so new ones can omit the id.

adr0028 is NOT marked superseded. Its transport decision is unaffected and
still statically enforced; only its addressing clause is narrowed here, and
retiring the whole ADR to correct one sentence would discard a live constraint.
A reader of adr0028's addressing sentence must read this ADR with it.

The name is still what an operator scans a window list for, and
`dotfiles-bg65` made that reliable by moving uid uniqueness to project scope —
so `<role>-<subject>@<project>` no longer collides for ordinary spawns even
though nothing addresses by it.
