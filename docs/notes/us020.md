# Story [[cat002]] [[product]]

## role
Someone using the same dotfiles from a laptop console and over RDP.

## want
To bind a chord on one display without binding it on the other.

## because
`$mod` resolves to a different physical key per display — Super on the native
`:0`, Alt on the xrdp `:10`, because Super does not survive an RDP client. One
table therefore means one chord with two different meanings, and there is no
way to say "only where `$mod` is Super".

This has now cost the same thing twice, which is what makes it a story rather
than an annoyance:

- `$mod+w` opened the alt-tab switcher. Harmless on `:0` as Super+w; on `:10`
  it is ALT+W, which emacs and readline use for copy, so ordinary typing opened
  the switcher and it was dropped outright (dotfiles-hwds.50) — losing it on
  the display where it was fine.
- Alt+Tab on `:0` was lost the same way at the switcher cutover: the pre-daemon
  i3 config grabbed both Super+Tab and Alt+Tab, and a static table cannot say
  "Mod1 as well, unless Mod1 is already what `$mod` means" — on `:10` that
  second form is a duplicate chord and the validator correctly refuses the
  table (dotfiles-y2ju).

Both times the resolution was to delete a working bind from one session to keep
the other usable.

## acceptance_criteria
- A bind can be declared for one `$mod` resolution and is not grabbed on a
  display where `$mod` resolves differently.
- The declaration is checkable without a display, so `--check` still runs
  headless and in a hook.
- `check --ownership` reports per-display ownership for such a bind without
  reporting a false `BOTH`.
- Restoring `$mod+w` on `:0` only, and Alt+Tab on `:0` only, are both
  expressible — those are the two cases that produced this story.
- A bind with no display qualifier behaves exactly as today.
