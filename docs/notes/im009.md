# Implementation [[cat002]] [[cat001]] [[product]]

## solves
[[us019|programmable-global-keybinds]]

## approach
Move ownership of global chords from i3's bind table into a per-display
Python daemon that grabs each chord itself on the root window
and dispatches over one persistent i3 IPC connection — the shape
[[ft011]] specifies, with per-key grabs chosen over an exclusive grab so a
hung daemon costs single keys instead of the whole session. Grabs go through
XI2 (`XIGrabKeycode`) rather than core `XGrabKey`, because a core `KeyPress`
carries no device identity and the daemon must distinguish one keyboard from
another — and a real keystroke from an injected one. Layer state
(current layer + held modifier) is published on a per-display unix socket
that bars consume read-only, the [[adr0012]] daemon-owns-state shape
applied to input, which is what lets [[ft009]] drop its reconstruction of
layer state from `nop` marker binds. Language is Python under [[adr0015]]
condition 1 (`python-xlib`, already installed for the quickshell layer),
fronted by a thin shell launcher rather than a nushell action. The key
trade-off: the daemon reimplements the duplicate-bind validation i3 gave
for free, paid back by expressiveness i3 cannot offer at all
(release-triggered binds, real held-modifier state, sequences, counts) —
and migration is per-group cutover, since a chord bound in both engines
double-fires. A group is a **grab-ownership closure**, not a concept: two X
clients cannot hold a passive grab on one chord, so the daemon can never shadow
an i3 global the way an i3 binding mode can. Scoping the first nav cutover
conceptually is what reverted it (`fd9e9f2`).

SHIPPED SHAPE, where execution differed from the sketch above. The migration
completed: 70 global chords and 63 layer-only chords are the daemon's, and
FOUR stay in i3 permanently — kill, reload, the hammer and panic. That is a
rule, not a remainder: grabs die with the daemon, so a key whose job is to deal
with an already-broken session cannot live in the thing that may be what is
broken. Two chords were deleted rather than migrated (`$mod+Ctrl+x` xkill,
`$mod+Ctrl+t` picom) and two dropped after shipping (`$mod+Shift+o` rename,
`$mod+w` — which on `:10` is ALT+W and ate a chord emacs and readline use).

The hold-layer gesture does not end on a key event; it ends on a server poll
([[adr0016]]), which then required `on_exit` so no other exit route strands the
overlay the gesture owns.

Half the delivered work is diagnostics rather than binds, and that was not
foreseen: four separate reports of a tool answering a weaker question than the
operator asked ([[adr0017]]) — a daemon serving nothing while `status` said
running, and then a heartbeat that called every pre-upgrade daemon wedged.

## data_model
No persistence. Per-display runtime state owned by the daemon, all under
`$XDG_RUNTIME_DIR` and keyed on the display with the screen suffix stripped so
`:10.0` and `:10` are one session:

- `hotkeyd-<n>.sock` — the state feed (one JSON line per layer / held-modifier
  change), current state replayed on connect
- `hotkeyd-<n>.lock` — `flock` single instance. Line 1 is the pid; line 2 is
  the literal `heartbeat=1`, and its ABSENCE means the daemon predates the
  heartbeat rather than that the heartbeat went stale ([[adr0017]]). The file's
  MTIME is the heartbeat itself, rewritten at most once a second from the top
  of the run loop
- `hotkeyd-<n>.grabs` — the grab report, `{pid, wanted, active, missing[]}`,
  rewritten atomically on every grab-set computation. A SIDECAR rather than the
  lock, because writing it would beat the heart and make a wedged daemon that
  still receives `MappingNotify` look alive. Stamped with the writer's pid, and
  a report whose pid does not match the lock's is ignored — a report is
  evidence only about the daemon that wrote it

In-memory: the current layer, the held-modifier set, and the WANTED chord list
beside the ACTIVE one. Keeping both is what lets a chord return after a keymap
that hid it settles; deriving the next grab set from the active one made it
monotonic and lost half the table (dotfiles-hwds.41).

Grabs live in the X server and die with the process — the reason [[ft003]]
keeps a restart bind and a fallback table.

Bar-side readers of the socket follow [[adr0014]] (fail fast, sleep floor,
timer-bounded respawn).

## api_surface
Nothing user-facing beyond [[ft011]]'s published surface. What shipped BEYOND
the proposed card is diagnostic, and it is the larger half of the work:

`hotkeyd.py --health --display <d>` answers "is this daemon SERVING", with a
distinct exit code per verdict because the codes license different actions
([[adr0017]]): 0 serving; 6 the run loop stopped (the only reapable verdict);
7 the display did not answer the CALLER; 8 another client holds an exclusive
keyboard grab, which no restart can fix; 9 DEGRADED — alive, but chords the
table asks for are not grabbed, and a restart IS the cure; 10 UNDETERMINED —
the daemon predates the heartbeat, so the question is unanswerable.

The launcher (`start` / `stop` / `restart` / `status` / `check`) relays those
codes rather than flattening them, and suppresses the "run start" advice for
the two verdicts a restart cannot help.

The i3 side gains exactly two permanent lines, not one: a hardcoded panic bind
calling `hotkeyd-panic.sh panic`, and the hammer (`$mod+Shift+r`) that reloads
i3, restarts the bar and cycles the daemon. Recovery returns the keyboard to i3
rather than restarting the daemon: a restart helps only when the daemon is
dead, not when it is alive and wrong.

Bind-table surface added during execution: layers may declare `hold` +
`on_hold_release` (the alt-tab gesture, ended by a poll per [[adr0016]]) and
`on_exit`, dispatched on every INVOLUNTARY exit — an explicit exit action, i3
taking a mode, daemon shutdown, SIGHUP reload — so a layer that owns an overlay
cannot strand it. Exit keys are deliberately excluded from that rule: they are
the user handing the keyboard back.

## components
- [hotkeyd/hotkeyd.py](../../hotkeyd/hotkeyd.py) — grab + dispatch loop,
  `MappingNotify` re-grab, persistent i3 IPC, the health probes and the
  grab-report publisher
- [hotkeyd/binds.py](../../hotkeyd/binds.py) — declarative bind table:
  70 global chords, 4 layers (nav, resize, system, switcher), validation
- [hotkeyd/layers.py](../../hotkeyd/layers.py) — layer engine, hold layers,
  `on_exit`, socket publisher
- [hotkeyd/hotkeyd.sh](../../hotkeyd/hotkeyd.sh) — launcher, `qs-bar.sh` shape
- [hotkeyd/hotkeyd-panic.sh](../../hotkeyd/hotkeyd-panic.sh) — panic / resume
- [hotkeyd/live_check.py](../../hotkeyd/live_check.py) — the checks that need a
  real X server; claims are gated on preconditions read off the same run
- [hotkeyd/test-hotkeyd.sh](../../hotkeyd/test-hotkeyd.sh) — runtime suite,
  17 stages
- [hotkeyd/test-launcher.sh](../../hotkeyd/test-launcher.sh),
  [hotkeyd/test-panic.sh](../../hotkeyd/test-panic.sh) — lifecycle suites
- [hotkeyd/dot.yaml](../../hotkeyd/dot.yaml) — links + `python-xlib`
- [i3/config.common](../../i3/config.common) — every migrated group removed;
  4 recovery chords kept by argument (kill / reload / hammer / panic)
- [i3/config.d/zz-fallback-binds.conf](../../i3/config.d/zz-fallback-binds.conf)
  — the panic-time i3 spelling of everything the daemon owns
- [i3/config-xrdp](../../i3/config-xrdp) — the proot entry point, which starts
  no daemon and therefore keeps its own binds
- [i3/test-nav-mode.sh](../../i3/test-nav-mode.sh) — re-pointed at the daemon
- [quickshell/config/Bar.qml](../../quickshell/config/Bar.qml) — reads the
  state socket; the `nop`-marker reconstruction is gone
- [quickshell/config/Common/ModeBarTheme.qml](../../quickshell/config/Common/ModeBarTheme.qml)
  — layer → pill/hints registry, plus `silentModes` for layers the bar must not
  paint
- [quickshell/qs-focus-border.py](../../quickshell/qs-focus-border.py) — rings
  the focused window per layer; `SILENT_LAYERS` mirrors the bar's set
