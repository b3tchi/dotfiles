# Story [[keyboard]] [[display-platform]] [[product]]

## role
[[pn001|developer]]

## want
bind my own keyboard interactions — sticky layers, held-modifier
sub-layers, key sequences, repeat counts — without the window manager's
bind table deciding what is expressible

## because
every interaction I have added so far has been shaped by what i3's
`bindsym` table can say rather than by what I wanted: the nav mode's
move/resize indicator only exists via marker binds the bar has to
reverse-engineer, and the task switcher needed a second event listener
because i3 binds cannot fire on key release

## acceptance_criteria
- a keyboard interaction that depends on a modifier being *held* can be
  built without publishing that fact through side effects of unrelated
  binds, and the status bar shows the held state from a state feed rather
  than by inferring it from bind side effects
- a bind can act on key release as well as key press, so a
  press-to-preview / release-to-confirm interaction needs no second
  event listener alongside the bind
- the same bind definitions drive both the native `:0` session and the
  xrdp `:10` session, with no per-session duplicate of the bind table
- the bind set is validated before it is loaded: a chord defined twice in
  one layer, or pointing at a layer that does not exist, is reported by
  name and refused rather than silently ignored
- if the process owning the binds stops, the session remains usable —
  keys reach the focused window, and one documented bind restarts it
- migrating a group of binds does not change what the keys do: the
  existing nav-mode runtime suite passes against the new mechanism while
  still asserting real focus, move, and resize effects
