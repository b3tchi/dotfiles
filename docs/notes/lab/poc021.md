# PoC [[cat001]] [[board]]

## hypothesis
The agent-asks case needs no hook at all — an instruction to use the [[poc020]]
inbox is sufficient, provided the instruction is delivered ambiently rather than
pasted into each task. Separately: interaction with a running agent can be
**switched** between direct (TUI prompts,
operator attached) and mail (everything routes to the [[poc020]] inbox, operator
answers async in a folder) — with the agent knowing nothing about either, and the
switch flippable mid-session rather than fixed at spawn.

## method
Isolated: `tmux -L pocmode`, scratch dir, scratch `--settings`. Real
`~/.claude/settings.json`, the `default` tmux server, and the live `preview-d`
(:4200) / `akm-graph-d` (:4810) daemons untouched. Workers on `--model haiku`,
`--permission-mode auto`, Claude Code 2.1.220.

The [[poc020]] CLI was reinstated from the reference artifact
(`poc020-agent-inbox.py`) and smoke-tested — which also settled that the
reconstructed artifact actually runs, not just parses.

Probe task: write a file to `/tmp/poc-mode-outside/probe.txt`, deliberately
outside the session's project scope so auto mode escalates it. A hook posted the
pending permission to the inbox, blocked, and mapped the operator's reply to a
decision. The mode switch was a flag file (`MAIL_MODE`) the hook re-read on every
invocation.

Two hook events were tried as the gate: `PermissionRequest` first, then
`PreToolUse`. Both allow and deny paths were exercised, with the artifact's
existence on disk as the objective signal.

Round 2 ran separately on `tmux -L pocamb`, its own scratch dir, and **no hooks
at all**. Four workers got an identical ambiguous task with no mention of the
inbox, differing only in how (and whether) the mode instruction reached them:
nothing / `CLAUDE.md` / `--append-system-prompt` / `--append-system-prompt` with a
hardened instruction. Compliance was measured behaviourally — did a request file
appear, or did an artifact appear without one — and the instruction's *arrival*
was then checked independently by asking each agent to state what `agent-inbox`
is. Answers deliberately named a format (`TOML`) no run had produced by default.

## result

### `defer` is abstain, not async
Read from the implementation rather than measured:
`if (p.permissionBehavior === "defer") { c = p.hookSource || ...; continue }` —
it declines to decide and falls through to the next decider. In the managed-hooks
gate it is grouped with deny. There is no built-in "answer later" posture; the
name is misleading. This is what makes the mode switch cheap, though: `defer` is
exactly the right return for direct-interaction mode.

### `PermissionRequest` does NOT gate — it only notifies
The hook fires (~immediately, carrying `session_id` and `transcript_path`) and can
post to the inbox, but its `permissionDecision` is ignored: with mail mode on, the
TUI prompt appeared **anyway**, the operator's `ALLOW` was captured and returned by
the hook at 16:01:09, and the write still did not happen. The prompt sat waiting
for a human regardless.

This is consistent with [[poc019]] round 6, which only ever used
`PermissionRequest` to write an escalation line and never claimed it could decide.
The `allow|deny|ask|defer` enum being present in the binary for this event does not
mean the harness honours it here.

### `PreToolUse` DOES gate — the mode works on this event
Same hook body, same inbox, event swapped:
- **No TUI prompt ever appeared.** The hook holds the tool call itself.
- Operator answered `ALLOW` in the folder → hook returned allow → `probe.txt`
  contained `PROBE`, agent reported `Done.`
- Operator answered `DENY` → write blocked, and the agent surfaced the reason
  verbatim: `Error: operator denied: DENY`, then correctly explained the failure.

Both directions verified by artifact-on-disk, not by transcript wording.

### The switch works and is live
`MAIL_MODE` absent → hook logs `mail mode OFF -> defer to normal prompt`, returns
`defer`, and the normal TUI dialog appears unchanged. Present → request lands in
the folder, no dialog. Because the flag is stat-ed per invocation, the transport
can be flipped mid-session: walk away, switch to mail, come back, switch off.

### Hook block duration
The gate held ~45–50s per exchange against a `timeout: 600` entry in settings, well
inside the configured window. No evidence yet of the 60s default biting when the
setting is raised — but nothing waited long enough to probe the real ceiling.

### The unsolved problem: scoping
`PreToolUse` fires for **every** matching tool call, not only ones that would have
prompted. This PoC dodged it by hardcoding a predicate (`Write` whose path contains
`poc-mode-outside`); everything else passed through untouched. A real mail mode
needs a way to intercept exactly the set auto mode would escalate — and the hook has
no access to the classifier's verdict. Left unsolved here; it is the main design
risk, not a detail.

### Round 2 — no hooks needed for the questions case, but soft instruction is inert
The hook work above targets *harness-initiated* permission prompts. The
originally-wanted case — the agent choosing to ask — needs no hook at all: the
"mode" can simply be an instruction to use `agent-inbox`. That was tested
separately, with the ambiguous task ("create a config with retries=3 and
timeout=30", format unstated) and **no mention of the inbox in the task itself**.

| variant | instruction delivered via | outcome |
|---|---|---|
| control | nothing | guessed `appconfig.json` |
| md | `CLAUDE.md` | guessed `appconfig.yaml` |
| sys | `--append-system-prompt` | guessed `appconfig.json` |
| hard | `--append-system-prompt`, enumerated + prohibition | **asked**, then wrote `appconfig.toml` |

**The soft ambient variants behaved exactly like the control.** Crucially this is
NOT a delivery failure: asked directly, both could recite the instruction — the
`md` agent named CLAUDE.md as its source, the `sys` agent reproduced the exact
command including `--timeout 1800`. They knew, and guessed anyway. The model does
not classify "which file format?" as a decision belonging to someone else;
picking a sensible default feels correct to it.

What flipped it was an instruction shaped as an explicit prohibition with the
decision classes enumerated — format/extension/schema/library/"anything the task
did not state" — plus the framing *"you are running detached, the operator is not
watching, absence of a stated preference is NOT permission to pick a default."*
That agent asked, parked in the background, and on `use TOML` produced real TOML
(`retries = 3`). TOML appeared in no other run, so the answer demonstrably steered
rather than coinciding with a default.

### Custom auto mode: rules load, but REPLACE the shipped list
Checked because custom `autoMode` rules looked like a possible route to shaping
what escalates. They are not a route to this feature at all — auto mode governs
whether a *permission* is granted, not whether an agent *asks a question* — but
the check surfaced a footgun worth recording.

Custom rules do load (they appear in `claude auto-mode config`). They **replace**
the shipped list for their key rather than appending to it:

| key | shipped default | with ONE custom rule |
|---|---|---|
| `hard_deny` | 1 (Data Exfiltration) | 1 — the custom one; shipped rule gone |
| `allow` | 17 | 1 — the custom one; 16 shipped rules gone |

So adding a single `hard_deny` silently removes the only shipped hard_deny, the
Data-Exfiltration rule.

**Correction (settings schema, read after the fact):** replacement is the
default, but it is not the only option — each `autoMode` list accepts the literal
string `"$defaults"`, which expands to the built-in rules *at that position*:

```json
{ "autoMode": { "hard_deny": ["$defaults", "My extra rule ..."] } }
```

The measurement above stands (one custom rule → shipped list gone), but the
earlier conclusion that you must hand-copy the defaults from
`claude auto-mode defaults` was wrong. Use `$defaults`. The footgun is real only
for someone who omits it, which is the natural thing to write.

Runtime enforcement of a custom rule was **not** demonstrated: a custom
`hard_deny` on a marker filename produced the same TUI prompt as a no-rules
control, so that test could not separate enforcement from baseline behaviour.
Establishing it needs an action default auto mode reliably auto-*allows*, then
denying it by rule. Unresolved.

### Field evidence (first real unattended use, not a PoC round)
An agent doing actual work (copying xrdp dotfiles off a phone) ran unattended for
~9 hours against the shipped implementation. Four things it settled that no
scratch test had:

- **Background parks survive at least 60 minutes.** Its own log records waits of
  30m, 30m, 60m, 60m, 60m before each timeout. That answers the duration-ceiling
  question left open above and in [[sp025]] far better than the ~9-minute scratch
  maximum. Nothing was lost across eight expiries — the durable files held.
- **Timeouts were far too short.** 1800s turned one question into eight re-asks
  overnight. The mode now specifies 43200s (12h): the operator may be asleep, and
  an ask that expires in half an hour answers nothing while filling the inbox.
- **Permission prompts still go to the TUI, confirming the boundary.** A
  permission dialog surfaced in the agent's tmux session, not the inbox, exactly
  as round 2 predicts — an instruction can only redirect questions the *agent*
  raises, never ones the *harness* raises. This promotes the `PreToolUse` gate
  from "deferred, not a dependency" to a real gap in unattended use: an agent
  that hits a permission prompt while nobody is attached is stuck regardless of
  how good the inbox is.
- **Re-asks are reminders, not duplicates, and need their own handling.** Each
  ping restated the question differently, so the exact-text idempotency check
  missed and minted a new request — eight pending files for one decision. The
  behaviour is right (a parked ask *should* be able to nudge); the storage model
  is wrong. A reminder should update its existing request in place.

### Smaller findings
- **The variadic-flag trap generalises.** `--allowedTools <tools...>` swallowed the
  prompt exactly as `--add-dir` did in [[poc020]], producing a worker that starts
  with no task and looks merely slow. Any variadic flag placed immediately before
  the positional prompt eats it.
- After a denial, unsubmitted text (`! echo PROBE > /tmp/...`) was observed sitting
  in the worker's input box. Origin not established; noted rather than explained.
  [[poc019]] round 1 saw input-box accumulation from a different cause.
- Losing a foreground command to a kill also took down the detached `pocmode` tmux
  server mid-run, voiding one result and forcing a re-run. Long foreground waits
  around live workers are worth avoiding.

## recommendation
**Mail mode is a prompt fragment, not a hook.** Round 2 settles the scope: the
agent-asks case — the one actually wanted — needs no hook, no `PreToolUse` gate,
and therefore none of the scoping problem below. Ship the CLI plus an instruction.

- **The instruction must be hard, enumerated, and prohibition-shaped.** Soft
  guidance ("ask when genuinely ambiguous") is *inert* — it delivers fine and the
  agent ignores it, indistinguishably from having no instruction at all. List the
  decision classes, state that absence of a preference is not permission to choose,
  and say the operator is not watching. This is a load-bearing finding, not
  prompt-polish: the difference between the soft and hard variants is the
  difference between a feature that works and one that silently never fires.
- **Verify compliance behaviourally, never by asking the agent.** Both failing
  variants could recite the rule perfectly while violating it. Any future check
  must measure whether it *asked*, not whether it *knows*.
- **`--append-system-prompt` and `CLAUDE.md` are equivalent carriers** — both
  delivered; neither rescued a weak instruction. Pick on ergonomics.
- Only if harness-initiated *permission* prompts also need routing does the hook
  work below apply. That is a separate capability, not a dependency, and it carries
  the unsolved scoping problem — so do not take it on for the questions case.

If that separate capability is ever built: use **`PreToolUse` + a
re-read-per-invocation toggle**, not `PermissionRequest`.

- **`PreToolUse` is the gate.** It is the only event tested whose decision the
  harness honours, and it suppresses the TUI dialog entirely rather than racing it.
- **`PermissionRequest` remains useful for notification only** — it is the right
  place to nudge ([[ft010]]) that something is waiting, which is what [[poc019]]
  round 6 used it for. Do not route decisions through it.
- **The toggle is a flag the hook stats every call**, not a launch flag. That is
  what makes "switch from direct interaction to mail" work on an agent already
  running, which is the whole point of the feature.
- **Return `defer` when mail mode is off.** Direct interaction then behaves
  identically to no hook at all.
- **Settle scoping before the spec commits.** Intercepting every `PreToolUse` and
  asking the operator about all of it is unusable; intercepting a hardcoded subset
  is what this PoC did and is not shippable. Options worth a further round: mirror
  the `autoMode` allow/soft_deny/hard_deny rules inside the hook, or intercept
  broadly and auto-allow anything matching a local allowlist, reserving the inbox
  for the residue.
- **Fail closed.** The PoC defaulted to `deny` on no reply and on an unparseable
  one; a permission gate that fails open on operator silence would be worse than no
  gate.

Not settled here: the real hook-block ceiling under a raised `timeout`; whether a
denial can be distinguished from a timeout by the agent; and the scoping predicate
above, which is the blocking unknown for a shippable mail mode.

Scratch dir, `/tmp/poc-mode-outside`, and the `pocmode` tmux server were removed.
