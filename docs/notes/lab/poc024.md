# PoC [[cat001]] [[cat002]] [[board]]

## informs
[[sp039|networked-clipboard-hub]]

## hypothesis

H1: a cgo-free Go Windows binary using `AddClipboardFormatListener` gets an
event for every copy, distinguishes a password-manager-marked copy
(`ExcludeClipboardContentFromMonitorProcessing`) from a plain one, and can
publish text carrying `CanIncludeInClipboardHistory=0` /
`CanUploadToCloudClipboard=0` that reads back intact.

H2: two LAN-only Syncthing instances (global/local discovery, relays, NAT
off; versioning off; `fsWatcherDelayS=1`), one with the folder on Linux
tmpfs and one on Windows NTFS, propagate a new age-encrypted entry file and
its deletion in ≤3 s p90, both directions.

## method

Scratch dirs only (session scratchpad + `%TEMP%\clipdpoc`), all deleted
afterwards. Host: WSL2 (mirrored networking) + its own Windows side.

H1: ~200-line Go program, raw `user32`/`kernel32` via `syscall.NewLazyDLL`,
message-only window, `GOOS=windows CGO_ENABLED=0`, go1.27.1. Triggers from
PowerShell: `Set-Clipboard` (plain), a WinForms `DataObject` carrying
`ExcludeClipboardContentFromMonitorProcessing` (KeePass-style), a
`DataObject` with a bitmap, a 5-copy burst, and the binary's own `set`
(CF_UNICODETEXT + both exclusion formats, non-ASCII text).

H2: Syncthing v2.1.5 on both sides (Linux: Arch package; Windows: official
release zip, sha256 verified). Configured via REST: static peer address on
127.0.0.1, folder `clipd`, rescan 3600 s. Each entry `age -r` encrypted,
written as `.tmp` then renamed to `<random>.age`; the receiver was polled every
50 ms for the file to appear, then for it to vanish after deletion. 10 runs in
each direction.

## result

**H1 validated.** Every copy raised `WM_CLIPBOARDUPDATE`. The marked copy
showed `exclude=true` and every plain copy `exclude=false`. The published
pick enumerated `CanIncludeInClipboardHistory` and
`CanUploadToCloudClipboard`, and the non-ASCII text read back correctly
through the Win32 API. Bitmap copies expose CF_DIB/CF_DIBV5 (#8/#17). Two
quirks: one copy fires 2-3 events, and the first can carry only `DataObject` /
`Ole Private Data` with empty text (the app renders the data late). Starting
the exe over WSL interop takes seconds, so a listener started by an
interop-spawned process misses the copies made before it registers. Not
verified: that Win+V history actually honours the exclusion flags (no API
read-back; documented Microsoft behaviour).

**H2 validated.** New entry appeared: tmpfs→NTFS 2.04-2.30 s,
NTFS→tmpfs 2.02-2.26 s (p90 ≈ 2.2 s). Deletion propagated in 2.02-2.13 s
both ways. 20/20 entries decrypted. No `.stversions` and no conflict copies.
The latency floor is about 2 s (watcher delay of 1 s plus scan and exchange).
inotify on tmpfs and ReadDirectoryChangesW on NTFS both fire. Side effect:
the first listen on `0.0.0.0` raised a Windows Defender Firewall prompt,
which created inbound Allow rules (Domain profile) for the binary's path.

## recommendation

Adopt sp039 as written. The Windows agent stays in Go with no cgo. It must
(a) check `ExcludeClipboardContentFromMonitorProcessing` *before* reading any
payload and never read a marked copy, (b) dedupe events by
`GetClipboardSequenceNumber` plus a content hash, and re-read after a short
delay when the formats show delayed rendering, and (c) run as a logon task,
not spawned over interop. Accept about 2 s sync latency (fine for
pick-on-demand). Syncthing deployment must listen on the LAN interface only and
ship an explicit firewall rule (Private profile, scoped to peer IPs) instead
of relying on the interactive prompt. Write entries as temp-then-rename so a
peer never syncs a partial file.
