# PoC [[cat002]] [[board]]

## informs
[[sp043|us027-ultrawide-focus-actuator]]

## hypothesis
The s5kjn1 ultrawide module on the Nothing Phone (1) has a focus actuator
(VCM) on its CCI bus that answers over I2C and, when driven, visibly
sharpens a scene the parked lens renders soft.

## method
Throwaway scratch dir (discarded), kernel 7.2.9, libcamera 0.8.0
(`cam -c1`, 1280x720 XRGB8888), i2c-tools + libgpiod, 2026-11-22, run on
the phone itself in five passes:
- Downstream: nothing-pmos `docs/status.md` names the ultrawide actuator
  `dongwoon,dw9800w @ 0xc` on `cci1_i2c0`. The live DT has no actuator
  node and no `lens-focus`; the s5kjn1 node has only vdda/vddd/vddio.
  The kernel ships `dw9719.ko` (`CONFIG_VIDEO_DW9719=m`) with
  `dongwoon,dw9800k` among its compatibles.
- Live DT: s5kjn1 at `18-002d`, EEPROM `gt24p128e` at `18-0051`. The DT
  already defines `regulator-camu-vaf` (`vreg_camu_vaf_1p8`,
  regulator-fixed, TLMM gpio 71 active high, vin = `bob`), but nothing
  consumes it: 0 users, disabled.
- Powering VAF by hand: unbind `regulator-camu-vaf` from
  `reg-fixed-voltage`, `gpioset -c gpiochip4 71=1`, rebind on exit.
- Per lens position: write DW98xx regs (0x02 = 0x00 power-up, 0x03/0x04 =
  10-bit position), read back, run `cam --capture=25` as the user, keep
  the last frame. One baseline frame with VAF unpowered (today's state).
- `cam` must run as the user: as root libcamera allocates from the
  root-only `default_cma_region` dma-heap, which is exhausted (24 MB CMA,
  24 kB free) -> `dma-heap allocation failure`; the user falls back to
  udmabuf.

## result
- VAF off: every access to `0x0c` NACKs (`No such device or address`),
  streaming or not. This is why no VCM was visible before.
- VAF on: `i2cdetect -r 18` shows `0x0c`; reg 0x00 = `0xf2` (DW98xx IC
  id), reg 0x01 = `0x07`. Power-up ACKs; every position write 0-1023
  reads back exactly and holds across camera restarts.
- The lens moves: on a room scene (~0.5-2 m, dim) pos
  100-250 resolves fabric pattern, a cable and object edges; pos 1023 and
  the VAF-off baseline are heavily blurred. Unpowered, the lens is
  not held anywhere, which explains today's soft stills ([[poc027]]).
- Laplacian variance (400x300 centre crop) is noise-dominated: baseline
  1555, peak 1810 at pos 250, 1603 at pos 1023. The images are the
  evidence; the metric only orders them.
- EEPROM (16 KiB) holds the module serial `F13570042C5XM31021` and a
  flagged, checksummed block at 0x92 with 10-bit values 564/396/408.
  These are plausibly AF calibration codes; the layout is unconfirmed.
- Live view (follow-up, same day): `libcamerasrc ! waylandsink` with the
  lens stepped by hand. The user judged a street view out of the window
  sharpest around pos ~375 ("infinity"); positions below it blur the far
  scene too (focus beyond infinity), positions above it focus nearer.
  The street itself was over-exposed (no AE tuning), so no still of it.
- This overrides the earlier still-based reading that pos 0-250 is far
  focus: those runs restarted `cam` per position, so AE swung between
  frames (luma 70-197), and the subjects (0.3-4 m) sat inside the
  ultrawide's deep depth of field. Treat pos ~375 as infinity.
- Distance calibration by eye in live view (user): 1 m sharp at pos 396,
  0.3 m at 440. Fit: pos = 377 + 18.9 / metres. It predicts infinity at
  377 (matches ~375 by eye) and 0.1 m at 566.
- Macro check (user, live view): 4 cm (the spec's closest focus) sharp
  at pos 840; the fit predicts 849. The fit holds from infinity to 4 cm.
- Optics cross-check against the spec (f/2.2, 14 mm equiv., 1/2.76"
  JN1 -> f ~2.1 mm): infinity-to-0.1 m needs ~46 um of lens travel, i.e.
  ~0.24 um/code and ~250 um over 0-1023, a plausible VCM stroke. The
  aperture is fixed (no iris); a hyperfocal preset (pos 401, ~0.8 m at
  f/2.2) showed no visible change from infinity in live view. That is
  expected for far subjects, so the f-number is consistent but not
  independently confirmed.
- Exposure: the softISP AE over-exposes bright scenes (no AE tuning for
  the s5kjn1). A live tuner (throwaway Python GStreamer app:
  `libcamerasrc` -> `waylandsink`, controls changed at runtime on the
  running source) showed manual exposure works on this pipeline:
  `ae-enable=false` with `exposure-time=<us>` and `analogue-gain=<x>`
  changes the picture live, so a camera app can tune exposure by hand
  without restarting the stream (user-confirmed). `exposure-value` (EV)
  and `brightness` were wired in too but not separately confirmed.
- Live-tuner plumbing: the camera must run as the user (CMA), the VCM
  needs root I2C, so a root wrapper powered VAF, lent `/dev/i2c-18` to
  the user for the session and restored it (`0:0 600`) on exit.
- The EEPROM block at 0x92 lines up: 564 = the 0.1 m (macro) code and
  396 = the 1 m code; 408 is unexplained. Layout still unconfirmed, but
  the module's factory calibration very likely sits there.
- The unpowered lens position is not fixed: some runs showed the near
  subject sharp unpowered, others blurred. A free-hanging VCM lens likely
  rests where gravity puts it, so it depends on the phone's attitude.

## recommendation
A focus actuator exists and works. Draft the follow-up story for the
hardware layer: add an `actuator@c` node under the s5kjn1's CCI bus
(`compatible = "dongwoon,dw9800k"`; dw9800w is the same family, verify
the register map against `dw9719.c`), with `vdd-supply =
<&vreg_camu_vaf_1p8>`, and a `lens-focus` phandle on the s5kjn1 node, via
the nothing-pmos dtb fix. libcamera then sees a lens with LensPosition.
Until AF exists, park the lens at the infinity code at stream start:
~377 (fit), or derived from the EEPROM codes once their layout is
confirmed (per-module, rather than a hardcoded number). Bright
outdoor scenes over-expose; that is AE tuning, a separate problem;
manual exposure (`ae-enable=false` + exposure time / gain) is the
working fallback today. Run `cam` as the user, not root, while CMA stays this small.
