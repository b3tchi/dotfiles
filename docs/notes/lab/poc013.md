# PoC [[cat002]] [[board]]

## informs
[[sp020|python-global-hotkey-layer]]

## hypothesis
A Python daemon holding per-bind `XGrabKey` grabs on the root window and
dispatching over one persistent i3 IPC connection is (a) indistinguishable
from i3's own bind latency at human input rates, (b) able to survive an
xrdp keymap reset, and (c) safe to kill — leaving no latched modifier, no
leaked grab, and a keyboard that still reaches clients.

## method
Throwaway harness ([[adr0015]] condition 2), python-xlib only:
`grabd.py` (grab one chord + persistent IPC + `CLOCK_MONOTONIC` JSONL log),
`i3obs.py` (i3 `binding`-event baseline), `run.py` (XTEST injection +
percentiles), `behave.py` / `behave2.py` (five behaviour probes).

Latency: 200 XTEST-injected `Super+F10` presses through the daemon vs 200
`Super+F9` presses through a temporary `bindsym Mod4+F9 nop spike-i3` bind,
per display, 25 ms apart. Both paths terminate in one IPC hop to a client
(daemon: command reply; i3: `binding` event), so neither is credited a
free hop. A positive control refuses to print percentiles unless BOTH paths
recorded ≥200 events — it fired, see the `:0` row below.

Displays: xrdp `:10` (live session), a clean Xvfb `:77` + minimal i3 (used
because live `:0` turned out to be ungrabbable, below). All temporary state
— the spike bind file and the `:77` server — removed afterwards; both live
i3 instances reloaded clean.

## result
**Latency — the daemon is not measurably slower than i3.**

| display | daemon grab delivery | daemon full dispatch | i3 baseline | delta (p95) |
|---|---|---|---|---|
| `:10` xrdp (live) | 0.44 ms / p95 0.54 | 0.76 ms / p95 2.06 | 1.33 ms / p95 1.90 | **+0.17 ms** |
| `:77` clean Xvfb | 0.33 ms / p95 0.44 | 0.44 ms / p95 0.59 | 0.37 ms / p95 0.48 | **+0.11 ms** |

(medians first, n=200 per cell, positive control PASS on both.) On the
live xrdp session the daemon's *median* dispatch is actually 0.57 ms faster
than i3's binding-event path; the p95 tail is 0.17 ms worse. Both are two
orders of magnitude below anything a hand notices.

**Lock bits are load-bearing, and proved so by negative control.** With all
four variants (`0`, `Lock`, `Mod2`, both) registered, the chord fired 3/3
with NumLock on (event `state=0x50`) and 3/3 with CapsLock on
(`state=0x42`). A grab registered with the **bare mask only** fired 3/3 with
NumLock off and **0/3 with NumLock on**. This is the "daemon randomly stops
working" bug, and it is one line of registration.

**Keysym-first resolution matters more than expected.** `Super_L` is
keycode **133** on `:0`/`:77` but **115** on the xrdp `:10` session — the
same physical key, different keycode per session. Today's
`bindcode 37/105/64/108` in `i3/config.common` is therefore display-specific
by accident; a keysym-resolving daemon is portable by construction.

**Keymap reset is survivable.** `setxkbmap -layout us` (the xrdp-reconnect
proxy) delivered 2 `MappingNotify` events to the daemon and the chord fired
3/3 afterwards. Both events reported `old_code=76 new_code=76` — the keysym
still mapped to the same keycode, so no re-grab was needed. Two spurious
`MappingNotify` events also arrived at every daemon startup, so the handler
must be idempotent (compare-then-regrab), not unconditional.

**SIGKILL mid-hold is clean.** Killed while `Super+F10` was physically held:
modifier mask `0x40` during the hold, `0x0` after kill+release (no latch);
`grab_keyboard` succeeded afterwards (no leaked grab); a freshly started
daemon re-grabbed and fired 2/2. The failure mode is a partial keyboard
outage until restart — exactly what the escape-hatch bind is for — not a
stuck session.

**Double-grab fails loudly, and only for the duplicated chord.** A second
client grabbing the same chord got `BadAccess` (code 10, `major_opcode 33` =
GrabKey) while the first grabber kept firing 3/3. So a botched migration is
detectable at grab time rather than silently double-firing — the daemon
should report per-chord `BadAccess` and keep serving the rest.

**Unexpected finding — an active keyboard grab blackholes both mechanisms
equally.** Live `:0` recorded **zero** events on BOTH paths (daemon *and*
i3's own bind) for 200 injected presses; `grab_keyboard` there returned
`AlreadyGrabbed` on three probes 2 s apart, with X input focus on Firefox
while i3's tree focus was elsewhere — a stuck popup grab. i3's binds were
dead on that display at that moment, with or without a daemon. Conclusion
for [[sp020]]: an exclusive grab held by *any* client is an existing session
hazard, not new exposure introduced by this layer — and it is the reason the
layer must never take such a grab itself. Real `:0` latency numbers remain
unmeasured and stay with the spec's Task 8 manual matrix.

## recommendation
**Validated — proceed with the [[sp020]] plan as written.** No change to the
solution shape. Three things the spike sharpens for the implementation tasks:

1. Register all four lock-bit variants per chord (proved load-bearing) and
   resolve chords keysym-first (`Super_L` is 133 vs 115 across this host's
   own two sessions).
2. `MappingNotify` handling must be compare-then-regrab: spurious events
   arrive at startup and on any keymap touch, and re-grabbing blindly would
   churn grabs for no reason.
3. Report `BadAccess` per chord and keep serving the others — that is the
   signal a migration duplicated a bind, and it is the only warning
   available mid-cutover.

Latency is a non-issue at this scale, so the `--check`/validation work and
the cutover discipline are where the remaining risk lives, not in the
dispatch path.
