# PoC [[cat002]] [[board]]

## informs
[[sp022|preview-qml-native-render-tiers]]

## hypothesis
A Qt Quick (`qml6` `ApplicationWindow`) window survives i3 reparenting on
xorgxrdp `:10` — the split/move/float operations that make a mapped
wry/WebKitGTK window self-close with `CloseRequested` (dotfiles-bfk).
If it does, [[ft005]]'s wrapper can drop the split-before-map + move-the-
terminal docking workaround and dock the preview window directly, and
re-docking a live window becomes possible.

Secondary: what window identity a `qml6`-hosted window presents, since the
wrapper matches windows by WM_CLASS today.

## method
Throwaway scratch dir (no worktree — this proves Qt/X server behaviour,
not repo code). A ~7-line `Probe.qml` `ApplicationWindow` with a fixed
title `preview 1`, launched on live `DISPLAY=:10.0` under the running i3,
on a dedicated `probe9` workspace so no real window was touched. The
window was resolved by `xdotool search --pid $!` and then subjected, in
one shell so the process was never orphaned, to: `split vertical` + `open`
(sibling forces a reparent), `move up`, `move right` + `split horizontal`,
`floating enable` then `floating disable` (two reparents), and
`move container to workspace probe8` + workspace switch. `kill -0` after
each stage; `xdotool search --pid` re-run at the end to confirm the same
window id. Versions: qt6-base/declarative/svg 6.11.1, Qml Runtime 6.11.1,
i3-wm 4.25.1, xorgxrdp virtual Xorg on `:10`, no compositor.

Two earlier runs were INVALID and discarded: the first backgrounded the
probe in one tool call and checked it in another, so the harness reaped it
before any i3 command ran; the second used `setsid`, whose `$!` is the
setsid parent, not `qml6`. Both reported DEAD for reasons unrelated to i3.
Recorded because the failure mode — a probe that dies of its own harness
and reads as a confirmed negative — is the easy way to "prove" the
opposite of the truth here.

## result
CONFIRMED. Every stage ALIVE, same window id (`0x3600...`) throughout,
`probe.log` empty (no Qt warning, no `CloseRequested` analogue):

| stage | result |
|---|---|
| mapped | ALIVE |
| split + sibling open (reparent) | ALIVE |
| `move up` | ALIVE |
| `move right` + split | ALIVE |
| floating enable/disable (reparent x2) | ALIVE |
| cross-workspace move | ALIVE |

Identity: `WM_CLASS(STRING) = "qml6", "Qml Runtime"` — derived from the
runtime, NOT from the `.qml` file, so every `qml6`-hosted app in the repo
shares it (`d2-view` collides). `WM_NAME` is the QML `title` verbatim
("preview 1") and reliable. `_NET_WM_PID` is set, so
`xdotool search --pid` resolves the window exactly.

## recommendation
The wry reparent hazard is a WebKitGTK/wry property, not an xorgxrdp or i3
one — the same operations on the same display with a Qt Quick window are
inert. So [[ft005]]'s docking workaround (`prepare-split`,
`wait-preview-mapped`'s class poll, `finalize-dock`'s move-the-launching-
terminal inversion, `main-show`'s fresh-window-only guard) is specific to
the host being replaced and deletes with it; dock by moving the preview
window, and re-dock live windows freely.

Do NOT match a `qml6` window by class — it is the runtime's identity, not
the app's, and it already collides with `d2-view`. Match by
`_NET_WM_PID` (`xdotool search --pid`, exact, and the wrapper already
holds the pid) and keep the title for any future `for_window` rule. A
per-slot pidfile needle must include the slot number: a bare runtime name
lets one slot's pidfile validate against another slot's live window.

Untested and worth flagging: sway/Wayland (this was X11/i3 only), and
whether a `WebEngineView` *inside* the QML window reintroduces the hazard
through the Chromium compositor — the web tier is where the engine comes
back, so that is the one place the result may not carry.
