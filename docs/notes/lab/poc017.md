# PoC [[cat002]] [[board]]

## informs
[[sp022|preview-qml-native-render-tiers]]

## hypothesis
A `WebEngineView` inside a QML `ApplicationWindow` reintroduces the wry
reparent hazard (dotfiles-bfk) on xorgxrdp `:10`, because the engine
brings its own Chromium compositor and GL surface — the layer [[poc016]]
did NOT exercise, since it probed a bare window with no web engine.

This is [[sp022]]'s load-bearing assumption. The spec's web tier
(`html` / `akm` / `stl`) must live INSIDE the QML process, because the
requirement is that a cursor move across a type boundary swaps content in
one window with no open/close. If the hazard returns, the in-process web
tier is dead and the tier design has to narrow to a delegated peer window.

## method
Throwaway scratch dir, not repo code. `WebProbe.qml` — an
`ApplicationWindow` whose entire content is a `WebEngineView` loading a
local `page.html` via `Qt.resolvedUrl` (no daemon dependency). The page
animates three elements under continuous CSS `transform` with
`will-change: transform`: an idle static page can be composited once and
never touched again, which would be a weaker test than the real preview
case, so the compositor is kept working across every reparent.

Same six-stage i3 sequence as [[poc016]], on live `DISPLAY=:10.0` under
the running i3, on a dedicated `probe9` workspace: `split vertical` +
`open` (sibling forces a reparent), `move up`, `move right` + `split
horizontal`, `floating enable` / `disable` (two reparents), and
`move container to workspace probe8` + workspace switch. `kill -0` after
each stage, all in one shell so the process is never orphaned (the
[[poc016]] harness trap), and `xdotool search --pid` at the end to confirm
the window id was not silently recreated.

Run TWICE, because preview-wv's own xrdp guard forces
`WEBKIT_DISABLE_COMPOSITING_MODE=1` there and the QML equivalent would be
a constraint worth knowing about:
1. `QT_QUICK_BACKEND=software` — what the client would set on xorgxrdp per
   [[adr0005]] / [[adr0004]].
2. No `QT_QUICK_BACKEND` at all — the default backend, to learn whether
   the software setting is load-bearing or merely prudent.

Memory read as summed `Pss` from `/proc/<pid>/smaps_rollup` over the qml6
process plus its children and the `QtWebEngineProcess` helpers. Approximate:
the helper match is by name across the box, not by parentage.

Versions: qt6-webengine 6.11.1-4, qt6-base/declarative/svg 6.11.1,
i3-wm 4.25.1, xorgxrdp virtual Xorg on `:10`, no compositor.

## result
INVALIDATED — the hazard does NOT return. Every stage ALIVE in BOTH
backend variants, same window id throughout, empty logs (no GL warning, no
backend complaint, no renderer crash):

| stage | software backend | default backend |
|---|---|---|
| mapped + page loaded | ALIVE | ALIVE |
| split + sibling open (reparent) | ALIVE | ALIVE |
| `move up` | ALIVE | ALIVE |
| `move right` + split | ALIVE | — |
| floating enable/disable (reparent x2) | ALIVE | ALIVE |
| cross-workspace move | ALIVE | ALIVE |

`QT_QUICK_BACKEND=software` is therefore NOT load-bearing for window
survival on xorgxrdp — the default backend survives the same sequence.
It remains prudent under [[adr0005]] for render correctness and cost,
which this PoC did not measure.

Memory — **these figures are WRONG; superseded by [[poc018]]. Use
~240 MiB for the web tier's marginal cost, not ~390 MiB.** Recorded as
originally measured, with the error named, because the mistake is
instructive: this PoC reported 413 MiB PSS settled against 21 MiB for an
engine-less window, a ~390 MiB delta. Its helper summed the parent plus
its children AND a global `pgrep -f QtWebEngineProcess`, so every renderer
helper that was already a child got counted twice — overstating the figure
by ~60%. [[poc018]] re-measured with a deduped recursive descendant walk:
**265 MiB settled, 25 MiB engine-less, ~240 MiB delta.** When measuring a
multi-process Chromium tree, walk the process's own descendants; never
name-match globally.

The engine-less baseline (21 MiB here, 25 MiB in poc018) is a bare window
painting a single `Text` item — a FLOOR for an empty QML window, NOT a
measurement of [[sp022]]'s native tier, which neither PoC exercised (no
image, no svg painted).

## recommendation
[[sp022]]'s in-process web tier stands as specified — proceed to
spec-refinement without revising `## solution`. The wry reparent hazard is
specific to WebKitGTK/wry, not to "a web engine on xorgxrdp": Chromium
under Qt survives the identical sequence that kills wry on the identical
display, with the compositor actively animating.

Do NOT read the 21 MiB baseline as the native tier's cost — it is an empty
window. If the ~155 MiB native figure from [[poc007]]'s recommendation
matters to a downstream decision, it needs its own measurement against
real image / svg / markdown content, which this PoC deliberately did not
do (it was scoped to the survival question).

Untested and still open: sway/Wayland (X11/i3 only here), and whether
repeated delegate swaps between the native and web tiers inside ONE live
window leak or wedge over time — this probed a single load, not the
hot-swap loop [[sp022]] actually ships. The latter is a natural
spec-refinement task, not a blocker.
