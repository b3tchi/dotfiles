# PoC [[cat002]] [[board]]

## informs
[[sp041|libcamera-qml-camera]]

## hypothesis
A minimal C++ Qt6 QML plugin built against libcamera 0.8 can stream the
Nothing Phone's back camera (s5kjn1, `camera@2d`, libcamera `simple`
pipeline with software ISP) into a `QVideoSink` shown by a QML
`VideoOutput`, at >= 15 fps, and the same plugin loads both under `qml6`
and inside quickshell.

## method
Scratch dir (discarded): CMake `qt_add_qml_module(URI LibCamera)`, one
`CameraSource` QML_ELEMENT (~120 lines): CameraManager -> first camera
matching `camera@2d` -> Viewfinder role forced to ABGR8888 1280x720 ->
FrameBufferAllocator -> requests; `requestCompleted` (libcamera thread)
mmaps the dmabuf plane, memcpys rows into a
`QVideoFrame(Format_RGBA8888)`, hands it to the GUI thread via a queued
`invokeMethod` -> `QVideoSink::setVideoFrame`, requeues with
`ReuseBuffers`. Loaded through `QML_IMPORT_PATH`. Versions: libcamera
0.8.0, Qt 6.12 (qt6-qtmultimedia 6.12.0), quickshell on kwi3-phone
(KWin Wayland), 2026-11-22.
Gotcha: libcamera's headers clash with Qt's `signals`/`emit` macros —
build with `QT_NO_KEYWORDS` (Q_SIGNALS / Q_EMIT).

## result
validated.
- qml6 Window: 222 frames in ~7 s (~31 fps); grabbed VideoOutput shows a
  real, correctly coloured image (no green cast — better than the
  gst-launch path), upright with `VideoOutput.orientation: 270`.
- quickshell PanelWindow (`quickshell -p shell.qml`, separate instance):
  190 frames in 6 s (~32 fps), grab shows the live image.
- libcamera's startup V4L2 "Unable to get rectangle" ERROR lines are the
  usual sensor-enumeration noise (also printed by `cam`), harmless.
- ABGR8888 from libcamera is R,G,B,A in memory = Qt `Format_RGBA8888`;
  no conversion needed. One CPU copy per frame at 720p is cheap enough
  for 30 fps.

## recommendation
Adopt [[sp041]]'s approach A as written: libcamera directly ->
QVideoSink, built as a shared QML plugin (`qt_add_qml_module`), works in
qml6 and quickshell unchanged. Build with `QT_NO_KEYWORDS`. Rotation:
libcamera reports 90; the correct display is `orientation: 270`
(counter-clockwise), so the module should expose
`(360 - rotation) % 360` or the sensor's own value with that documented.
The PoC copies frames; a zero-copy dmabuf path is an optimisation, not
needed for v1.
