# PoC [[cat002]] [[board]]

## informs
[[sp022|preview-qml-native-render-tiers]]

## hypothesis
`qml6` will NOT tolerate `import QtWebEngine` arriving at
`Loader`-instantiation time — the module historically wants
`QtWebEngineQuick::initialize()` called before the application object
exists, so a delegate file that carries the import and is loaded lazily
should fail to instantiate.

This is [[sp022]]'s Task 5 risk, flagged at spec-refinement as "the most
likely task to surprise": if the lazy import fails, the client needs a
small C++ entry point, which reopens the language question the
[[adr0015]]-family framing settled.

Secondary: does a top-level `import QtWebEngine` cost RAM before any
`WebEngineView` exists? The fallback shape (eager import, lazily
instantiated view) is only worth having if the cost genuinely sits at view
instantiation.

## method
Throwaway scratch dir, not repo code. `DISPLAY=:10.0`,
`QT_QUICK_BACKEND=software`, `QT_FORCE_STDERR_LOGGING=1` (QML swallows
`console.log` without it — the `d2-view` header notes the same).

Variant A — lazy import: `LazyMain.qml` carries NO `QtWebEngine` import
anywhere; a `Loader` with an empty `source` flips to `WebTier.qml` on a
2.5 s timer, and `WebTier.qml` is the only file importing the module.
Success is observable, not assumed: `Loader.status`, a
`Component.onCompleted` marker, and `WebEngineView.onLoadingChanged`
status codes are all logged.

Variant B — eager import, late view: `EagerMain.qml` imports
`QtWebEngine` at the top level but holds the `WebEngineView` inside an
uninstantiated `Component`, assigned to the `Loader` on the same timer.

Memory read as summed `Pss` from `/proc/<pid>/smaps_rollup` over the qml6
process and ALL descendants, deduped, sampled at 2 s (pre-swap) and 10 s
(settled). Recursive descendant walk, deliberately NOT a global
`pgrep -f QtWebEngineProcess` — see `## result` for why that distinction
matters.

Versions: qt6-webengine 6.11.1-4, qt6-base/declarative 6.11.1,
xorgxrdp virtual Xorg on `:10`, no compositor.

## result
INVALIDATED — the lazy import works. `qml6` loaded `WebTier.qml` with the
`QtWebEngine` import arriving at `Loader` time, with no top-level import
and no explicit initialize call:

```
qml: SWAP -> WebTier.qml
qml: WEBTIER WebEngineView constructed
qml: LOADER status=1            (Loader.Ready, not Loader.Error)
qml: WEBTIER loadStatus=2       (LoadSucceededStatus)
```

Memory, `:10`, settled, animated page:

| variant | before swap | settled | delta |
|---|---|---|---|
| A — lazy import (no top-level) | 25 MiB, 1 proc | 265 MiB, 5 procs | 240 |
| B — eager import, late view | 47 MiB, 1 proc | 264 MiB, 5 procs | 217 |

So a top-level `import QtWebEngine` costs ~22 MiB (25 → 47 MiB) with no
`WebEngineView` in existence — the module's own footprint. The engine
proper (~240 MiB, 4 helper processes) lands at view instantiation in both
variants. Lazy import is therefore not merely viable but marginally
cheaper, and the [[sp022]] fallback is not needed.

**Corrects [[poc017]].** That record reported ~413 MiB settled and a
~390 MiB delta over an engine-less window. Both figures are too high: its
helper summed the parent plus children AND a global
`pgrep -f QtWebEngineProcess`, counting the renderer helpers twice. The
consistent deduped walk here gives **~240 MiB** as the web tier's true
marginal cost. poc017's survival findings are unaffected — only its
memory numbers were wrong. [[sp022]] carried the inflated number and is
corrected alongside this record.

Cosmetic noise worth expecting in the real client on xorgxrdp, neither
fatal nor affecting load: `Failed to create Vulkan instance: -9`,
`Failed to create platform Vulkan instance`, `GPUInfo not initialized on
GpuInfoUpdate`. The page loaded successfully through all three.

## recommendation
[[sp022]] Task 5 keeps the lazy `Loader` shape as specified and should
drop its eager-import fallback edge case — the fallback costs 22 MiB for
nothing. No C++ entry point is needed, so the [[adr0015]]-family framing
holds and the language question stays closed.

Use ~240 MiB, not ~390 MiB, wherever the web tier's cost informs a
decision. And when measuring a multi-process Chromium tree, walk the
process's own descendants — a name-matched `pgrep` double-counts helpers
that are already children, which is exactly how [[poc017]] overstated the
figure by 60%.

Untested: whether repeated native↔web swaps in one live window leak
across many cycles (this probed a single swap in each direction's start
state), and sway/Wayland. Both remain [[sp022]] Task 9 material.
