# PoC [[cat002]] [[board]]

## informs
[[sp021|hotkeyd-go-zero-dep-rewrite]]

## hypothesis
A pure-Go X11 client (no cgo) can passively grab a key chord via XInput2,
receive `XI_KeyPress` as a GenericEvent carrying the correct SLAVE `sourceid`,
ungrab it, and sustain 1000 events with no connection stream desync — the
binding question blocking a Go rewrite of [[ft011]]'s `hotkeyd.py`.

## method
Scratch dir `/tmp/.../scratchpad/poc-go-xi2` (throwaway, discarded; nothing
written to the repo). `Xvfb :97`, injection via `xdotool`, chord `Mod4+a`
(keycode 38 resolved at runtime via `GetKeyboardMapping`).

Candidate A — vendor `github.com/jezek/xgb` v1.3.1 via a `replace` directive,
patch `readResponses`, hand-write the XI2 wire subset over the exported
`Conn.NewRequest` / `NewCookie`. Candidate B (cgo + `libXi`) held in reserve
and never needed.

Two prior walls confirmed rather than assumed. `xgb` v1.3.1 ships no `xinput`
package, and its generator cannot make one:

    $ go run ./xgbgen --proto-path /usr/share/xcb /usr/share/xcb/xinput.xml
    Unrecognized tag 'case' in expression context.

That only blocks generating the WHOLE extension, which was never needed — five
requests and one event parser is the entire daemon surface.

The second wall is the real one. `readResponses` reads a fixed 32 bytes per
response and the event branch never reads a GenericEvent's extra `length*4`
payload. Measured event size here: **120 bytes**. The patch is 16 added lines,
one hunk, zero deletions, mirroring the reply branch 40 lines above it verbatim:

    if evNum == 35 {
        extra := Get32(buf[4:])
        if extra > 0 {
            biggerBuf := make([]byte, 32+extra*4)
            copy(biggerBuf[:32], buf)
            io.ReadFull(c.conn, biggerBuf[32:])
            buf = biggerBuf
        }
    }

Hand-written wire code `xi2.go` — **256 lines**: constants + `DeviceInfo` /
`DeviceEvent` types (~75), `XIQueryVersion` (16), `XIQueryDevice` incl. the
variable-length device-info walk (40), `XIPassiveGrabDevice` (42),
`XIPassiveUngrabDevice` (22), `ParseDeviceEvent` + `fp1616` (30),
`NewEventFuncs` glue (14). `XISelectEvents` (opcode 46, hierarchy events) not
implemented; ~15 more of the same shape.

Versions — behavior here is version-sensitive: go 1.26.5, xgb v1.3.1,
xorg-server-xvfb 21.1.24-1, xdotool 4.20260303.1-1, XI2 protocol 2.3
negotiated, `CGO_ENABLED` irrelevant (static pure-Go build).

## result
**Validated**, Candidate A, deterministic across 4 consecutive runs with
identical counts. All five criteria passed:

1. `XIPassiveGrabDevice` clean — reply's failed-modifier list empty.
2. GenericEvent `ext=131 evtype=2`, `raw[120]B` — 32-byte header plus 88 bytes
   stock xgb discards.
3. `deviceid=3 ("Virtual core keyboard", MasterKeyboard)` vs
   `sourceid=5 ("Virtual core XTEST keyboard", SlaveKeyboard)` — distinct, and
   both resolved against a live `XIQueryDevice` table rather than eyeballed.
   This is the attribution split the daemon exists on.
4. `XIPassiveUngrabDevice` clean; 0 events from 3 further injected chords.
5. 600 injected chords → **1800 events** received (600 press + 1200 release,
   exactly the predicted arithmetic), **0** malformed, **0** unknown response
   codes, **0** spurious errors. Three round-trip shapes after the flood
   (`XIQueryVersion`, `GetInputFocus`, `XIQueryDevice`) all returned coherent
   replies.

The counterfactual is what makes criterion 5 meaningful. Same binary, same rig,
`readResponses` reverted to stock:

    received total=1950  XI_KeyPress=0  XI_KeyRelease=0
    malformed/short generic events=450
    non-generic=map[xproto.LeaveNotifyEvent:450 xproto.SelectionNotifyEvent:450 ...]
    XGB: BUG: Could not find event construct function for event with number 64.
    exit=124 elapsed=45s

XI2 payload bytes get reinterpreted as fresh 32-byte responses — phantom
`SelectionNotify` / `LeaveNotify` events nobody sent, "errors" with impossible
codes. Then the post-flood round-trip **never returns**: the reply is eaten as
event garbage and the cookie blocks forever. Exit 124 is `timeout` killing it.
For a hotkey daemon that is the worst available failure mode — not a crash, a
silent permanent hang.

Gotchas a real implementation must handle: `GrabType.Keycode` is **1, not 0**
(trust the XML, not prose — 0 is Button, so the wrong constant grabs *button
38*); `XIDeviceInfo` needs `<pad align="4"/>` after the name, then each
`DeviceClass` skipped by its own `len` at offset +2, or every device past the
first silently corrupts; `mask_len` counts 4-byte units, not bytes; FP1616 is
**signed** (`float64(int32(v))/65536.0` — casting through `uint32` gives
garbage for negative coords on a left/above monitor); event size is variable
(`buttons_len`/`valuators_len`), so never assume 120; GenericEvent sequence
numbers are meaningless for correlation (all three events reported `seq=5`);
register `NewEventFuncs[35]` before connecting; use a checked cookie for
`XIPassiveGrabDevice` so a competing grabber's `BadAccess` surfaces
synchronously.

Lock-bit variants were dodged — the PoC grabbed `modifiers=[0x40]` only. Real
sessions need `0x40`, `|Lock(0x02)`, `|Mod2(0x10)`, `|both`, which is ONE
request (the modifier list is a parameter), but the reply reports failures
*per modifier*, so a partial success must not read as total success.

## recommendation
**Adopt Candidate A: vendored `jezek/xgb` fork + 16-line `readResponses` patch
+ ~270 lines of hand-written XI2 wire code. No cgo.** The patch is a
bug-shaped hole, not a design conflict — it copies the adjacent reply branch
verbatim, rebases cleanly, and is worth upstreaming, so the fork may not even
be permanent. The prize is `CGO_ENABLED=0`: `hotkeyd` targets native
Arch/Manjaro, WSL, and proot-Arch-on-aarch64, and a static pure-Go binary
cross-compiles to all of them from one machine with no `pkg-config`, no
`libXi` headers, no per-platform toolchain. Candidate B would trade that away
to avoid ~270 lines of XML-verified struct packing, and would additionally
hand over `libXi`'s `XGetEventData`/`XFreeEventData` cookie lifecycle as a
fresh leak source. Bad trade — do not revisit cgo unless the fork proves
unmaintainable.

One caveat to budget for before committing the port: this ran against the
XTEST slave (id 5) only, because grabbing a chord on the live `:0`/`:10`
session would have taken the keyboard from the user. The wire format and the
master/slave split are proven; the full device-attribution matrix is not.
Re-run criteria 2 and 3 against a real display with physical keyboards
attached — `hotkeyd.py` discriminates on exactly that, and [[ft011]]'s
measured `:0` inventory (`AT Translated Set 2` 12, `BlueZ` 13, `Acer WMI` 14)
is what the Go side must reproduce.
