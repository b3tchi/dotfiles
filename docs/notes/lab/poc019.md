# PoC [[cat001]] [[board]]

## hypothesis
Claude Code agents can be dispatched as tmux sessions instead of Agent-tool
subagents, and coordinate through an addressable message channel — giving them
what Agent-tool subagents lack: an address, a return path for questions, and the
ability to spawn further agents.

Running record. Each round below states what it tested and what it settled.
Status stays `open` until every requirement in `## requirements` is met.

## requirements
- [x] R1 spawn — a detached tmux session runs a working `claude`
- [x] R2 dispatch — a task reaches a freshly spawned agent
- [x] R3 report — a child can deliver a message to its parent
- [x] R4 non-destructive delivery — a message never truncates in-flight work
- [x] R5 event loop — an agent wakes on an event without polling turns
- [x] R6 nesting — a spawned agent can spawn a further agent
- [x] R7 unattended spawn — no interactive prompt can stall a worker
- [x] R8 concurrency — parallel agents can share the bd/Dolt store safely
- [x] R9 build-vs-use — `claude --bg` / `claude agents` ruled in or out
- [~] R10 containerized workers — plumbing proven; auth + registry unresolved
- [x] R11 human-in-the-loop — worker asks, parks, resumes on a user reply

## method
All rounds ran in scratch dirs on isolated tmux servers (`tmux -L pocagent`,
`-L pochook`, `-L pocnest`) so the live `default` server was never touched.
tmux 3.7b, Claude Code 2.1.220, workers on `--model haiku`. Hook rounds used a
scratch `--settings` file; the real `~/.claude/settings.json` was never modified.

**Round 1 — send-keys channel.** Idle injection probe; injection during an
active multi-tool-call task with file-count growth as an objective busy signal;
an uninjected control of the same shape; and a full parent/child loop with the
child spawned under `-e AGENT_PARENT=parent`.

**Round 2 — hook channel.** Hook contract confirmed against
code.claude.com/docs/en/hooks first. Round 1's truncation test repeated with
delivery moved to a `Stop` hook draining a queue file. Then the hook rewritten
to block up to 20s waiting for an event, with timestamps logged.

**Round 3 — spawn path.** Real `git worktree add`, child spawned into it, child
instructed to spawn a grandchild whose task was passed as an argv positional.
Nesting measured by the grandchild's proof file plus `tmux list-sessions`.

**Round 4 — bd/Dolt concurrency.** Tested with parallel shells rather than
agents: the question is process-level contention, which shells measure more
precisely and at no token cost. An isolated scratch bd workspace (`bd init
--prefix poct` in a throwaway git repo — never the real store, verified by issue
count) took 6 concurrent `bd create`, then 6 concurrent `bd update --claim` on
one issue, then 6 concurrent `bd update` on six distinct issues.

**Round 5 — built-in background agents.** `claude agents --help` and
`claude agents --json` inspected against the live machine to decide whether the
built-in background-agent facility supersedes any of this.

**Round 6 — permission posture (R7).** Two of the three postures were put under
test. Posture 3 (stall detection): a scratch `--settings` file registering a
`PermissionRequest` hook that appends an escalation line, with a worker spawned
under a deliberately narrow `--allowedTools 'Bash(echo hello)'` and then asked to
run a command outside it. Posture 1 (pre-seeded trust): attempted under an
isolated `CLAUDE_CONFIG_DIR`, abandoned — see result.

**Round 7 — containers (R10).** The `claude` install is a single ELF binary, so
it was bind-mounted into a stock `python:3.12` container rather than baking an
image. Tested: binary portability across distros, the host-tmux ->
`docker exec -it` -> TUI chain, and whether the round-5 session registry survives
the container boundary.

**Round 8 — orchestrator/window dispatch + human-in-the-loop inbox (R11).**
An orchestrator session was created with its own window 0, then spawned a worker
as a *second window* (`new-window -a -t orch:0 -n worker`) with the task passed as
argv. The task deliberately required a decision only the user can make (config
format JSON vs YAML), with instructions to write the question to `inbox/q1.ask`
and end the turn. A `Stop` hook scanned `inbox/` for a `.ask` lacking a matching
`.reply`, parked up to 45s, and on reply emitted it via
`hookSpecificOutput.additionalContext`. The reply had to *steer* the artifact, so
the resulting file's syntax is the proof it was received.

## result

### Round 1 — send-keys works, but preempts (R1, R2, R3 met; R4 failed)
- Spawn works. `new-session -d -c <dir>` running `claude` initializes its TUI
  with no client ever attached. Pass `-x 200 -y 50` — the 80x24 default wraps
  the TUI badly.
- Idle injection is clean: `send-keys -l` + 300ms + separate `Enter` produced
  `> Reply with exactly the word PONG` -> `* PONG`.
- The loop closes. Child wrote its file, ran both send-keys calls, parent showed
  `> DONE-FROM-CHILD child-done.txt written` -> `* Acknowledged.` The parent's
  tmux session name passed as `AGENT_PARENT` is a sufficient address — no
  directory service needed.
- **Mid-task injection PREEMPTS and truncates in-flight work.** Injecting during
  a 15-file task left **4 of 15** files written; the uninjected control of the
  same shape completed **10 of 10**. Controlled comparison, not inference. The
  message is neither lost nor garbled — it steals the turn.
- Unsubmitted text accumulates in the input box and a later nudge concatenates
  onto it, submitting garbage. Observed accidentally. Motivates a `send-keys
  C-u` clear-line before every nudge.
- Busy is detectable by scraping the pane (`\([0-9]+s · .*tokens` while working,
  past-tense `* Verbed for 16s` when idle) — TUI-shaped and fragile.
  **SUPERSEDED by round 5:** `claude agents --json` exposes a real `status`
  field. Do not scrape the pane.

### Round 2 — the hook channel fixes R4, and gives R5
- **8 of 8 files completed AND the mail was processed**, against 4 of 15 for
  send-keys on the same shape. Pane sequence: all 8 writes, then `Ran 2 stop
  hooks` -> `Stop hook error: INCOMING MAIL: ...` -> `HOOKMAIL-SEEN`. Hook
  delivery is non-destructive by construction — it fires after the turn ends, so
  there is no in-flight work to preempt. Terminated cleanly on the next Stop with
  an empty queue.
- **Event loop works.** A `Stop` hook blocking on a queue file logged
  `hook-got-mail` within **0.5s** of the append; the agent responded ~1s later. A
  second park with no event hit its timeout and went cleanly idle. No tokens burn
  while parked — a blocked hook runs no inference. While parked the pane shows the
  past-tense completion marker with an available input box, so parking does NOT
  render as busy.
- The `reason` field surfaces to the agent as **`Stop hook error:`** — mail
  arrives labeled an error. `hookSpecificOutput.additionalContext` is the
  documented non-error channel and is the right field.
- **A parked hook cannot keep an agent alive indefinitely.** Hook execution is
  capped by the harness hook timeout (60s default), and once the hook allows the
  stop the agent is idle — no further Stop hooks fire, nothing left to block.
  Staying alive requires always returning `block`, costing one real turn per cycle.
- A first run here was a harness bug, not a finding: a file-count detector never
  fired, so mail was queued after the turn had already ended. Recorded so the next
  reader does not trust a first-run null.

### Round 3 — nesting confirmed, spawn path simplified (R6 met; R7 open)
- **Depth 2 works.** `gc-proof.txt` containing `GRANDCHILD-RAN` was written by a
  grandchild agent, with both sessions live. A tmux-spawned claude is a top-level
  process and can spawn further agents — the capability the Agent tool lacks and
  that deprecated `infinifu:scrum-master`.
- **Dispatch works via argv — no send-keys at spawn.** A grandchild started as
  `claude ... "<task>"` showed the task as a submitted turn immediately. send-keys
  is only needed for *subsequent* messages to a running agent, removing the
  fragile injection step from the spawn path.
- **A fresh git worktree DOES raise the trust prompt** and blocks until an Enter
  arrives — the real-path answer round 1 could not give, having only tested a
  subdir of an already-trusted dir. The grandchild's cwd, nested under the
  already-trusted worktree, raised no prompt: trust inherits from a trusted
  ancestor, and worktrees do not.
- **A narrow allowlist hangs the agent.** The child stalled on `Contains
  command_substitution / Do you want to proceed?` — a bash shape its
  `Bash(tmux:*)` allowlist did not cover — waiting indefinitely for a human who
  was not watching. Allowlists match command shape, not intent.
- **Not tested (blocked):** whether `--permission-mode bypassPermissions`
  suppresses the trust prompt. Refused by this session's auto-mode permission
  classifier, correctly — it spawns an agent with all permission checks disabled.
  Deliberately not worked around; it is an operator posture decision.

### Round 4 — bd is already the dispatch lock (R8 met)
- **6 concurrent `bd create` all succeeded** with unique ids and no lock errors.
- **`bd update --claim` is genuinely atomic under contention.** Six agents raced
  for one issue; exactly one won (`Assignee: agent5`). This means bd itself
  provides the dispatch lock — the separate dispatch-lock machinery gastown
  carries (`sling_dispatch_lock`, `sling_idempotency`) is not needed here.
- **Losers fail in two different ways, and callers must treat both as "someone
  else got it".** Some returned the semantic `Error claiming poct-10h: issue
  already claimed by agent5`; others returned a raw
  `dolt commit: Error 1213 (40001): serialization failure: this transaction
  conflicts with a committed transaction from another client, try restarting
  transaction`. A caller that reads only the first form will misclassify the
  second as a hard failure.
- **Serialization failures come from row contention, not from parallelism.** Six
  agents updating six *distinct* issues gave `ok=6, serialization_failures=0`.
  So a fleet working disjoint tasks needs no retry wrapper; only contended writes
  (claims, and any shared-row update) need retry-on-1213 with backoff.

### Round 5 — the built-in facility solves a different half (R9 met)
- `claude agents --json` returns **every active session, interactive and
  background**, with `pid`, `cwd`, `sessionId`, `name`, and `status`. On the live
  machine it reported 3 `busy` and 6 `idle` across nine sessions, including one
  pre-existing `"kind": "background"` agent.
- **This retires the round-1 pane-scraping entirely.** `status` is a first-class
  busy/idle signal, so the "send-keys only to an idle agent" rule from round 2
  becomes cheap and robust to enforce instead of resting on a TUI regex.
- **But there is no messaging verb.** Nothing in `claude agents` sends input to a
  running background agent; `--resume <session-id>` starts a *new* process
  against an old conversation rather than talking to the live one. Background
  agents are fire-and-forget, with no address and no return path — the exact gap
  that motivated this PoC.
- Verdict: the built-in facility does **not** supersede tmux dispatch, but it
  does supersede the hand-rolled registry and busy-detection. Use it for both.

### Round 6 — stalls are detectable two ways; prevention untested (R7 partial)
- **`PermissionRequest` hook fires on the stall.** Within ~4s of the worker
  blocking on `This command requires approval / Do you want to proceed?`, the
  hook had written an escalation line. Its stdin payload carries `session_id`
  and `transcript_path`. Note `CLAUDE_SESSION_ID` was **empty** in the hook
  environment — read the id from the JSON payload, not the env var.
- **`claude agents --json` reports a third status: `waiting`.** The stalled
  session showed `status: waiting`, distinct from `busy` and `idle`, alongside 3
  busy and 6 idle sessions elsewhere on the machine.
- **This corrects an earlier claim in this record.** Round 3 asserted a stalled
  agent "looks identical to one doing slow work". That was true only under the
  pane-scraping assumption. It is false: there are two independent detectors, one
  push (hook, immediate) and one poll (registry status).
- `cwd` is the practical join key between the registry and a tmux session, since
  each worker gets its own worktree. `sessionId` links the hook escalation to the
  registry row.
- **Posture 1 (pre-seeded trust) — NOT tested, blocked twice.** The mechanism is
  confirmed by Claude Code's own error text: *"set
  `projects[<path>].hasTrustDialogAccepted: true` in `<config>/.claude.json`"*,
  and `~/.claude.json` does carry `projects.<path>.hasTrustDialogAccepted`
  alongside a per-project `allowedTools`. `CLAUDE_CONFIG_DIR` does isolate the
  config, but an isolated dir is not logged in, and symlinking the real
  `~/.claude/.credentials.json` into it was refused by the permission classifier
  — correctly, and not worked around. Editing the real `~/.claude.json` was
  declined on separate grounds: 9 live sessions were writing that file
  concurrently, so a hand-edit risks both clobbering and a false result.
  Verification needs one operator-run command.

### Round 6b — posture 1 confirmed by operator run (R7 met)
Run by the operator, since it writes the real `~/.claude.json` (9 live sessions
were concurrently writing that file, making an agent-side edit unsafe).

Seeding `projects["<fresh worktree>"].hasTrustDialogAccepted = true` and spawning
a worker there produced **no trust prompt**, and the worker **ran to completion
unattended** — `probe-ok.txt` containing `TRUST-BYPASSED`. Notably this used only
`--permission-mode acceptEdits`: **`bypassPermissions` was not needed**. Posture 1
plus posture 3 is therefore a complete answer to R7, and posture 2 can stay
unused.

Leftover state to revert on the operator's machine: `projects` entries for
`/tmp/poc-agent-probe/wt1` and `/tmp/poc-agent-probe/main`, plus a backup at
`~/.claude.json.trustprobe-backup`.

### Round 7 — containers work, but cost the registry (R10 partial)
- **The binary is portable.** The Arch-built `claude` ELF ran unmodified inside a
  stock `python:3.12` (debian) container via a read-only bind mount of
  `~/.local/share/claude/versions`. No image build, no npm install.
- **The TTY chain works.** A host tmux session running `docker exec -it <ctr>
  claude` rendered the full TUI. This means containerizing swaps only the
  *process*: everything proven in rounds 1-6 (argv dispatch, hook delivery,
  send-keys to idle, nesting) applies unchanged, with the host tmux session name
  still the address.
- **Containers run as root**, which matters because
  `--dangerously-skip-permissions` is known to refuse running as root in some
  versions. Untested — see below.
- **The host registry does NOT see containerized sessions.** A claude was
  confirmed running inside the container (it created its own `/root/.claude` and
  `/root/.claude.json`), yet `claude agents --json` on the host reported 0 of
  them against its own 9. **This regresses round 5**: the `busy`/`idle`/`waiting`
  status signal, recommended there as the replacement for pane-scraping, does not
  cross the container boundary. Any containerized design must either mount a
  shared config dir or aggregate per-container registries.
- **Inconclusive:** querying the *in-container* registry
  (`docker exec <ctr> claude agents --json`) returned `[]`. The in-container
  session never passed first-run onboarding (no credentials), so this cannot
  distinguish "per-container registry works" from "no session to list". Needs an
  authenticated container to settle.
- **Not tested (blocked):** `--dangerously-skip-permissions` inside the
  container, including the root question. Refused by the permission classifier,
  which blocks that flag regardless of the sandbox context. Not worked around.
  Given round 6b, it may simply be unnecessary.

### Round 8 — the full ask/reply loop closes (R11 met)
- **Window addressing works.** `orch:0` = orchestrator, `orch:worker` = worker;
  `send-keys -t orch:worker` and `-t orch:0` both land. Gotcha: a bare
  `new-window -t orch` fails with `create window failed: index 0 in use` — pass
  `-a` (append after current) or an explicit free index.
- **argv dispatch works into a window** exactly as it does into a session
  (round 3), so nothing about the spawn path changes.
- **The human-in-the-loop loop closes end to end.** Worker wrote
  `inbox/q1.ask` = "Format for appconfig file - JSON or YAML?", ended its turn,
  the hook logged `pending question q1.ask - parking`, the reply file was picked up
  **in the same second it appeared**, and the worker resumed and produced
  `retries: 3` — YAML syntax, not `{"retries": 3}`. The reply genuinely steered the
  outcome; `q1.ask` was moved to `q1.answered`.
- **`additionalContext` is confirmed as the right channel.** The worker's pane
  showed `Stop hook feedback: USER REPLY to your question: use YAML please` —
  **feedback, not `Stop hook error:`** as `reason` produced in round 2. It also
  continued the conversation *without* `decision: block`, so the round-2
  refinement is now verified rather than merely recommended.
- **HAZARD: a login shell may not stay in the `-c <dir>` you gave it.** Window 0
  was created with `-c <scratch>`, but its nushell auto-cd'd to
  `/home/jan/.dotfiles` (the project-registry auto-cd in `export-env`). A command
  sent to that window therefore executed in the *real repo* and left a stray file
  there. **Every path in the inbox protocol must be absolute**; never rely on an
  agent's or a window's cwd.
- Park duration is bounded by the harness hook timeout (60s default), so a slow
  human still hits the round-2 park-then-idle path: the hook times out, the agent
  goes idle, and a nudge revives it. The `.ask`/`.reply`/`.answered` files are the
  durable state across that gap — the protocol survives the agent going idle.

## recommendation
Interim, pending R10.

Adopt tmux-session dispatch over Agent-tool subagents: it removes the harness
ceiling on nesting and gives every agent an address.

- **Spawn via argv**, not send-keys: `tmux new-session -d -c <worktree> -x 200
  -y 50 "claude <flags> '<primed task>'"`.
- **Deliver to a live agent over the `Stop` hook** using
  `hookSpecificOutput.additionalContext`. Zero preemption risk, proven against
  the round-1 truncation case.
- **Use send-keys only to wake a provably-idle agent** — safe precisely because
  it is idle, the one state round 1 found clean. Clear the line (`send-keys
  C-u`) first.
- **Do not build an always-block keep-alive loop.** It costs a turn per cycle for
  an agent doing nothing. Prefer park-then-idle: the hook waits out one window,
  the agent goes idle, a nudge revives it.
- **No pane-scraping anywhere.** The queue is still required, but the hook drains
  it. Where busy/idle state is genuinely needed, read `claude agents --json`
  (`status`, `sessionId`, `cwd`) — it is also the session registry, so no
  hand-rolled agent directory is needed either.
- **Let bd be the dispatch lock.** `bd update --claim` is atomic under
  contention, so no separate locking layer is needed. Treat both
  `already claimed` and `Error 1213 serialization failure` as "another agent won";
  retry-with-backoff only on contended writes, since disjoint writes never
  conflict.
- **Keep the built-in background agents in view but not on the critical path.**
  They have no messaging verb and no return path, so they cannot carry the
  child-reports-to-parent requirement — but they cost nothing to read from.

- **Always wire stall detection**, whatever posture is chosen. Register a
  `PermissionRequest` hook that emits an escalation (round 6) and read
  `status: waiting` from the registry as the reconciling poll. Route the
  escalation over the round-2 hook channel. This is cheap, proven, and it means
  a stalled worker surfaces in seconds rather than silently holding a task.

- **Permission posture: seed trust, keep checks on.** Posture 1 + posture 3 is
  sufficient (round 6b): pre-seed `hasTrustDialogAccepted` for each worktree at
  sling time, run workers on `acceptEdits`, and escalate on `PermissionRequest`.
  `bypassPermissions` is not required, so do not grant it.

Containers are optional and can come later. They are attractive because
`--dangerously-skip-permissions` is documented as "recommended only for sandboxes
with no internet access" — but round 6b removed the need for that flag, so the
main argument for containerizing weakens to plain isolation. If adopted, budget
for the registry regression (round 7): host-side `claude agents --json` goes
blind, so either mount a shared config dir into every worker or aggregate
per-container registries. Settle the in-container registry question first — it is
one authenticated container away.

PoC code discarded after each round; scratch dirs and all three tmux servers
removed.
