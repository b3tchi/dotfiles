# PoC [[cat002]] [[board]]

## informs
[[sp021|hotkeyd-go-zero-dep-rewrite]]

## hypothesis
A Go program with ZERO external dependencies (stdlib only, `CGO_ENABLED=0`) can
connect to an X display, authenticate, complete the setup handshake, passively
grab a chord via XInput2, receive `XI_KeyPress` with correct slave `sourceid`,
and sustain 1000 events with no stream desync — removing the vendored-fork
dependency [[poc014]] settled for, for a Go rewrite of [[ft011]]'s `hotkeyd.py`.

## method
Round 2 of [[poc014]], same scratch-dir discipline (`poc-go-xi2-nodep`,
discarded; zero repo writes). [[poc014]] proved the XI2 request encodings and
the `DeviceEvent` parse over xgb's connection; this round replaces everything
BENEATH that layer with owned code, so the unproven surface was: `$DISPLAY`
parse + socket dial, `~/.Xauthority` `MIT-MAGIC-COOKIE-1` extraction, the setup
handshake and its variable-length screen-list walk, sequence tracking with
reply/error correlation, the read loop, and the four core requests the daemon
needs (`QueryExtension`, `GetKeyboardMapping`,
`GetProperty(RESOURCE_MANAGER)`, `QueryPointer`).

Rigs, deliberately three: `Xvfb :96` bare, `Xvfb :95 -auth` (so the cookie path
is exercised at all — see gotcha 3), and read-only probes of the REAL `:0`
(native i3) and `:10` (i3 over xrdp) sessions. No grabs on the live sessions.
Injection via `xdotool`. Versions: go 1.26.5, xorg-server-xvfb 21.1.24-1,
xdotool 4.20260303.1-1, XI2 2.3.

Measured line counts, gofmt-clean, `code` = non-blank non-comment:

| Area | total | code |
|---|---|---|
| Xauthority parse + family/address matching | 154 | 120 |
| DISPLAY parse + socket dial | 82 | 68 |

The read loop — the entire reason [[poc014]] needed a fork — is **61 code
lines**.

## result
**Validated.** All 8 criteria. `go.mod` require block empty, `go list -m all`
returns only `poc-nodep`, no `go.sum`, no `vendor/`. Static 3.8 MiB binary,
`not a dynamic executable`, cross-compiles clean to `linux/arm64` and
`linux/arm` (the proot/Termux targets).

Grab clean (`failed_modifier_count=0`). `GE raw=120B ext=131 evtype=2
deviceid=3 sourceid=5`. 600 chords -> 1800 events, identical across 4 runs; a
2000-chord run gave 6000/6000, `malformed_generic=0 unknown_responses=0
async_errors=0`, five round-trip shapes coherent afterwards including a
variable-length `GetKeyboardMapping` (1736 keysyms). Ungrab clean, 0 events
after. Same numbers over the authenticated `:95` connection.

Error correlation proven unprompted: three consecutive deliberate errors
(`BadWindow` seq 8, `BadWindow` seq 9, `BadValue` seq 10) each found their
waiter with `major=38`/`20`/`131 minor=47` correctly attributing
QueryPointer / GetProperty / XIQueryVersion, `bad_value=3735928559` echoing
`0xdeadbeef` back, and the stream surviving.

Two live-session results close [[poc014]]'s stated limitation:

- `:0` enumerates PHYSICAL slave keyboards `id=12 "AT Translated Set 2
  keyboard"`, `id=13 "BlueZ 5.86 (MCS)"`, `id=14 "Acer WMI hotkeys"`, distinct
  from XTEST `id=5` — matching [[ft011]]'s measured inventory exactly. So
  `sourceid` discriminates hardware from synthetic input, not merely master
  from XTEST.
- `:10` returned `xrdb line: "i3wm.mod:\tMod1"` from hand-written
  `GetProperty`. `:0` has **no `i3wm.mod` line at all** — so the daemon's Mod4
  is a default-on-absence (i3's `set_from_resource` fallback), not a value read
  off the server. Worth knowing before porting that resolution path.

Auth proven both directions. Cookie present: `family=Local
address="jan-swiftsf31441" number="95" name="MIT-MAGIC-COOKIE-1"`. Cookie
withheld: `setup FAILED ... Authorization required, but no authorization
protocol specified` — so the cookie is load-bearing and the `status==0` Failed
path decodes the reason rather than hanging.

Handshake/auth gotchas — the genuinely new findings, several invisible on a
naive rig:

1. Every real entry used `FamilyLocal` (256) keyed on **hostname**. A hostname
   change silently invalidates every cookie in a perfectly readable auth file.
   Needs an explicit diagnostic; matcher does exact -> Wild -> relaxed passes so
   drift degrades to a warning.
2. The display number in Xauthority is stored as **ASCII text**, not an int.
   Comparing against an `int` fails silently.
3. **Xvfb without `-auth` accepts unauthenticated local connections; real Xorg
   does not.** Testing only on bare Xvfb leaves the whole cookie path
   unexercised and *looks* like a pass.
4. The screen walk must be verified **by arrival** — assert `off == len(b)`
   after walking. A wrong `<pad align>` yields a plausible-but-wrong root
   window and every later grab silently targets nothing. Only real `:0`
   exercises it properly (7 depths / 272 visuals / 7 formats vs Xvfb's 6).
5. The vendor string is padded to 4 bytes before the format list
   (`off += pad4(vendorLen)`). `"The X.Org Foundation"` is 20 chars — exactly
   divisible by 4 — so this bug is **invisible** on both Xvfb and this Xorg and
   would corrupt every screen on any other vendor string. Latent-landmine class.
6. `GetProperty`'s value length is in **format units, not bytes**
   (`units * format/8`). With `format=8` they coincide, hiding it until a
   32-bit property.
7. `RESOURCE_MANAGER` can exceed one reply; loop on `BytesAfter` with
   `long_offset` advancing in **4-byte units**. 132 bytes here never iterated;
   a real xrdb database will.
8. `keysyms_per_keycode` varies 7 (Xvfb) / 10 (`:0`) / 15 (`:10`). No fixed
   stride. Count comes off the reply-length field.
9. Sequence allocation and the socket write must be under **one** lock — the
   server numbers by arrival, so incrementing outside the write lock lets two
   goroutines swap identities.
10. 16-bit sequence wrap is UNHANDLED in the PoC and the error scan is linear,
    so past ~65k requests a stale seq could false-positive. A real daemon needs
    a windowed / generation-tagged map. Sibling fact: GE sequence numbers are
    useless for correlation (all three burst events reported `seq=9`).
11. Abstract-namespace socket fallback (`"\x00"+path`) — unneeded here, but some
    containers and WSL bind only the abstract socket.

## recommendation
**Take the zero-dep route; do not fork xgb.** The delta over [[poc014]] is
+755 lines, but 193 of those carry over unchanged, so the genuinely new work is
~834 lines — and the two riskiest chunks (screen walk 185, read loop 61) are
the smallest. 1027 lines is about half of `hotkeyd.py`'s current 1941, so this
is not a large codebase by the standard of the thing it replaces.

The decisive evidence is not the line count, it is the shape of the liability.
The fork route's 272 lines arrive bundled with ~30 kLOC of vendored
third-party code and a patch to re-apply on every upstream bump, for a fix that
belongs upstream but cannot be waited on. The zero-dep route's 1027 lines are
all load-bearing and all owned: no `go.sum`, no GPL question (the surveyed
alternative `linuxdeepin/go-x11-client` is GPL-3.0-or-later AND declares
`module go-x11-client`, so it cannot be imported from its github path at all),
no upstream to track, and `CGO_ENABLED=0` cross-compiles to arm64/arm from one
machine. It is also the ideological match for a suckless-style rewrite with
binds compiled in: own the seven requests you use and nothing else.

Budget three follow-ups honestly, none hard, all load-bearing for a daemon
trusted with the keyboard: a windowed sequence-correlation map before it runs
for weeks; `MappingNotify` triggering a regrab; and the passive grab
registering all four lock-bit variants (`0x40`, `|Lock`, `|Mod2`, `|both`) in
one `XIPassiveGrabDevice` call with the per-modifier failure list actually
inspected rather than read as all-or-nothing.
