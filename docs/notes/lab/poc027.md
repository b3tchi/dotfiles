# PoC [[cat002]] [[board]]

## informs
[[sp042|us026-full-resolution-still]]

## hypothesis
Re-run of [[poc026]] on a lit scene (poc026's phone lay lens-down): the
single-stream still reconfigure gives a clean, correctly exposed image at
4080x3072 with 4 settle frames.

## method
Scratch C++ program (discarded), libcamera 0.8.0, Qt 6.12, phone pointed at
a lit room, 2026-11-22: viewfinder 1280x720 -> stop -> StillCapture at a
given size -> settle N -> grab -> viewfinder; mean luma of viewfinder vs
still; thumbnails and 300x300 centre crops at 100%;
LIBCAMERA_SOFTISP_MODE=cpu vs default (GPU eGL debayer). Debug log of the
sensor mode picked (SimplePipeline).

## result
- 4080x3072 is BROKEN: GPU debayer shows a grid of magenta/cyan/yellow
  blocks over the whole image plus a fine cross-hatch; CPU debayer has no
  blocks but the same cross-hatch and comes out dark. Both the viewfinder and
  every still use the SAME sensor mode (4080x3072 SGRBG10); the defects
  appear only when the software ISP outputs at (near) 1:1, scaled outputs
  average them away.
- 2040x1536, 2560x1920, 3264x2448 and 3840x2880 (GPU): clean at 100% crop,
  no blocks, no cross-hatch; ~0.95-1.1 s capture -> back to viewfinder.
- exposure: still gain follows the viewfinder's; luma equal at 3840x2880
  (exposure 33 ms both), ~1.45x brighter at 4080x3072 (47.7 ms). One early
  run caught AE mid-swing (dark still at settle 8); repeated runs at settle
  4 and 8 were consistent. 4 settle frames suffice.
- images soft (lens parked near close focus, [[us027]]) and yellow-tinted
  (no AWB/colour tuning for s5kjn1) — both pre-existing.

## recommendation
Use 3840x2880 (11 MP) as the still size, not 4080x3072: the largest size
measured clean, ~1.1 s. Pick it in code as the largest still size strictly
below the sensor mode's own size (1:1 output is what breaks), so other
sensors are not hard-coded. 4 settle frames, no exposure carry-over. The
4080x3072 software-ISP defect is a libcamera issue worth reporting upstream
separately.
