# Story [[cat002]] [[product]]

## role
Someone running the WSL Sway environment (`meta-wsl-sway`), where the
session is Wayland rather than X11.

## want
`preview show` and `preview window` to dock the preview window beside the
launching frame, the same way they do under i3.

## because
[[adr0018]]'s client spawns, renders every tier, and follows the editor
across workspaces under sway — but dock-beside-frame never runs there.
Both docking entry points gate on `xdotool getactivewindow`, which is
X11-only, so the branch that would issue `swaymsg [pid=…] move container to
mark` is unreachable from `show`/`window` even though the placement helper
itself supports the sway criterion (bd `dotfiles-8ryw`).

The result is a silent capability gap rather than an error: the window
appears wherever the compositor puts it, and the user has no signal that
docking was skipped. Since the platform model lists sway as a first-class
environment, "renders but never docks" is a per-platform regression against
the i3 experience.

## acceptance_criteria
- Under sway, `preview window [N]` docks the window beside the launching
  frame, and `preview show` re-docks a live window by shape, matching the
  i3 behaviour — verified on a real sway session, same window and same pid
  before and after.
- The active-window probe is abstracted so the docking path selects an
  X11 or Wayland implementation, instead of every caller depending on
  `xdotool`.
- Headless (no WM, no compositor) still degrades to spawn-only with no
  error — the Termux stance is preserved.
- `wm-bin` and the placement helper agree on which compositor is in use on
  a host where both `i3-msg` and `swaymsg` exist.
- `preview/README.md`'s docking section stops saying docking is X11-only.
