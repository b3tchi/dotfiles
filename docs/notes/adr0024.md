# ADR [[cat001]] [[product]]

## title
running agent definition

## title
A running agent is a live process whose job has not finished

## context
[[sp026]] named `claude agents --all --json` as the census source and said
nothing about which of its records count. That turned out to be the whole
question.

The command returns HISTORICAL job records alongside running ones. On the
machine this shipped on it returned 13 records for 6 running agents; the seven
extras were job records aged 25 to 101 days whose processes were long gone.
Counting them answered "how many agent records exist" rather than [[us022]]'s
"how many agents are running".

Filtering on a live pid was not enough either. A background job that has
FINISHED stays resident under `claude bg-pty-host`, so it passes a liveness
test while having no tmux window and nothing left to do — three agents were
reported in a project holding two claude windows.

The output carries two independent fields, which the first implementation
conflated:

  state   the JOB's lifecycle — working / blocked / done / failed. Durable,
          survives the process. Background records only.
  status  the PROCESS's activity — busy / idle. Emitted ONLY while a process
          exists. Both kinds carry it.

## decision
An agent counts as **running** when both hold:

1. **A process exists** — proven by the presence of `status`. Observed
   invariant, 13/13 live and 13/13 in fixtures: `has(status) <=> has(pid)`,
   and every such pid was alive. This is preferred over looking the pid up in
   a process table: same signal, from the supported command, with no window
   between two probes for the process to exit in.
2. **The job is not finished** — `state` is not `done` or `failed`.

Records that fail either test are reachable through `--all` and excluded by
default.

Two corollaries that are part of the decision, not incidental:

- **Presence of `status` is trustworthy; its VALUE is not.** An abandoned
  session sits at `status: busy` indefinitely — one was observed at `busy` for
  six hours with zero CPU. `busy` proves something is there, not that it is
  working. Anything needing real activity must find another signal.
- **Having no tmux window never excludes an agent.** [[us022]] exists because
  background agents that are BLOCKED are invisible until you walk the sessions
  by hand. A window-less blocked agent is precisely what the census is for;
  only terminal ones drop out. Matching the visible window count was tempting
  and would have gutted the feature.

When both fields are present, the JOB axis decides the bucket. `status=idle` +
`state=blocked` is alive and waiting on you; reporting it as idle from the
process axis would bury the row the feature exists to surface.

## consequences
The default count matches what an operator sees plus any window-less agent
genuinely working — 5 tmux windows plus one background worker, on the machine
this shipped on.

`done` is now a bucket that only fills under `--all`. [[us022]]'s acceptance
criteria list it among the four default buckets, so the story text is now
narrower than reality; it was written before the distinction was understood.

A future engineer could reasonably choose differently — count every record, or
count only attachable sessions — which is why this is recorded rather than left
implicit in a `where` clause.

Stale `status` values remain undetectable from the supported surface. See
[[adr0025]].
