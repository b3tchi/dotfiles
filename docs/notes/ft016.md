# Feature [[cat001]] [[cat002]] [[product]]

## providing

One interactive terminal view of every agent this machine is running and every
message they have exchanged. Two panes: a roster — one row per agent across
both runtimes, carrying its state, its own reported activity, and its age — and
a message log in time order, `from` → `to` with a derived subject line. It
renders and does not join: the roster comes from [[ft012]]'s published census
rows and the log from [[ft014]]'s project message read, and this Feature
computes neither. Proposed by [[sp030]], which also widens both sources.

The question it answers is the one [[ft012]] deliberately left to its
consumers ("it observes only; rendering belongs to its consumers") and the one
[[ft014]] records the data for without ever showing: which agents need me, and
what did they say to each other.

## api_surface

A single Go binary linked to `~/.local/bin/agent-monitor`. It is the user
interface, so nothing wraps it — the `nushell/actions/` front-end that
[[adr0003]] mandates for a compiled *engine* would forward argv and add a
shell start-up to an interactive launch, and [[adr0030]] carves that mandate
out the way [[adr0021]] did for `hotkeyd`.

- `agent-monitor` — full screen, alternate buffer, both panes.
- `agent-monitor --project <name>` — restrict to one project.
- `agent-monitor --once` — render one frame to stdout and exit; no raw mode,
  no alternate screen, so it composes in a pipe and in a tmux status line.

Keys: `q` quit, `r` force a census refresh, `tab` move focus between panes,
`/` filter, arrows / `jk` scroll the focused pane. Read-only in this Feature —
no verb reaches a worker; resume / stop / accept stay with the CLI that owns
them, since those destroy worktrees and branches.

Exit status is 0 on a clean quit, including when zero agents are running.

## data_model

Holds no durable state. Two in-process samples with different clocks, because
they cost different amounts:

| sample | source | cadence |
|---|---|---|
| roster | `agent-census --json --detail` | slow tick + on `r` |
| messages | `pi-worker messages --json` | fast tick |

The roster probe costs ~600 ms dominated by one `claude` call per account
([[ft012]]), which [[us023]] names as fine on demand and wrong on a timer, so
it is sampled slowly and rendered from the last good sample in between. The
message read is local file work and is sampled fast. A sample that fails
leaves the previous one on screen, marked stale by age — never a blank pane
and never an invented value.

Both loops are reader loops over a runtime directory that can vanish, so both
carry [[adr0014]]'s three guards: fail fast on unrecoverable setup rather than
retrying it inline, a sleep floor on every iteration, and a bounded retry
outside the loop.

Displayed state is whatever its source reports. An agent whose runtime
publishes no activity shows an empty activity column rather than a guessed
one, and a presence reading older than its freshness bound renders `unknown` —
which licenses nothing ([[adr0017]]). The subject column is derived
reader-side: first line of `content`, or `status — summary` for a result
envelope. The bus stays opaque about what it carries ([[adr0028]]); no
`subject` field is added to an envelope to make this column exist.

## components

Components land at `spec-refinement`; the Feature is proposed, not built.
Consumes [[ft012]] (roster rows) and [[ft014]] (message read, worker presence),
both widened by [[sp030]]. Reads nothing else — no bus paths, no claude
internals, no tmux.
