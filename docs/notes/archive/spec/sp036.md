# Spec [[cat001]] [[cat002]] [[board]]

## extends
[[ft016]]

## problem
Five changes to the shipped message pane, bundled because three of them touch
the SAME cells: the two defects [[sp034]]'s and [[sp035]]'s audits found, plus
three display corrections the operator asked for after living with the
threaded view. Splitting them would mean three specs editing
`PARTICIPANTS` and the detail header in sequence.

**1. `dotfiles-br55` — label cells bypass the neutraliser.** The most
consequential item here. [[sp034]]'s `## plan` claims "every rendered byte
still goes through `subject.go`'s neutraliser and cell-aware truncation".
True of SUBJECT, false of every LABEL cell, in BOTH the flat grid and the
thread grid. An auditor probe on `base@main` rendered a message whose `From`
was `w\x1b[31ma`: the raw `0x1b` reached the terminal. `msgCellFor`'s
From/To path is `orDash(shortAddress(m.From))` / `toCellShort(m.To)` with no
`neutralize()` anywhere, and the thread grid mirrors it onto `PARTICIPANTS`
and the child rows' indented FROM. This pane renders other agents' bytes, and
a label is registry-resolved from a name the worker CHOSE ([[adr0017]],
[[adr0034]]) — attacker-influenced exactly as content is. Worse, `runeWidth()`
returns 0 for `r < 0x20`, so the escape consumes no width budget while still
reaching the terminal: `pad()` neither strips it nor accounts for it. The
suite cannot see it because the `--once` pipe check uses benign real-bus
labels.

**2. `dotfiles-i1sw` — a second reorder by a different key.** [[sp034]]'s
`## plan` forbids deriving a second order; the code does. `ParseMessages`
sorts ascending by ULID, `orderedMessages` reverses to ID-descending (the
pane's single reorder point), and then `Threads()` applies `isNewer` — which
orders by the `At` STRING — twice, over each thread's messages and over the
threads themselves. Measured under ordinary clock skew between two agents:
flat row 0 is `m2`, threaded row 0 is `m1`. [[sp035]]'s wiring makes it
observable — `t` preserves the selected envelope by identity, so a mode
toggle can move the cursor off row 0 and flip the pane from live to
`+N behind` with nothing having arrived. The issue records three fix options;
(a) making `Threads()` ORDER-PRESERVING — group by key in first-appearance
order, keep each group in input order, sort nothing — is the one that makes
the single-reorder rule hold by construction rather than by documentation.
It requires reworking the `At`-based assertions in `thread_test.go`.

**3. Expand glyph becomes `+` / `-`.** `>` collapsed and `v` expanded become
`+` and `-`. Plain ASCII either way, so nothing about the width budget or the
[[sp034]] drop rules changes. A non-expandable one-message thread keeps the
blank cell [[sp035]] gave it.

**4. `PARTICIPANTS` shows direction, and sheds the recipient when open.**
Today the cell is an address-SORTED pair joined by `<>`, which is honest about
grouping and says nothing about who spoke. Collapsed, it becomes the NEWEST
message's direction — `from > to` — so the row reports who spoke last; the
pair flips as the conversation turns, which is information rather than noise.
EXPANDED, the thread row shows only the newest SENDER: the children below it
already carry each message's own sender, the recipient is recoverable from
that context and from the detail pane, and repeating it above rows that say it
spends width on a constant. The thread KEY and the grouping are untouched —
this is display order within the cell, never the address-sorted composite
[[adr0034]] requires.

**5. Detail addresses inline, one party per line.** [[sp035]] put the
addresses on their own line(s) below the label header, which leaves the
operator matching addresses to labels by position. Inline is unambiguous, but
a single line carrying two labels and two 27-character addresses is far too
long for the pane. So: one PARTY per line, each line pairing that party's
label with its own full address. Full addresses stay full — the detail pane
is the view an operator copies from, and [[sp035]] already pinned that
against `shortAddress` elision.

Constraints:

- Feature-refresh on the accepted [[ft016]], the shape [[sp034]] and
  [[sp035]] both used: no `us###`, no `im###`, no new `ft###`, and the finale
  archives the spec without flipping the Feature.
- Thread keys, address-based grouping and the for-you address comparison are
  untouched ([[adr0034]]).
- Reader-side only: no envelope field ([[adr0028]]), no `content` parsing the
  pane does not already do ([[adr0031]]).
- `--once` stays FLAT and byte-identical except where item 1 legitimately
  neutralises a hostile label — a change no benign bus can observe.
  [[sp030]] T9's pipe contract and the suite's `0x1b` check both still bind.
- Any binding or rendering whose behaviour changes keeps a real `tea.KeyMsg`
  test where a binding is involved ([[adr0036]]).
- Items 1 and 4 touch the same cells, and item 2 rewrites the ordering those
  cells are fed from; the task breakdown has to sequence them so no task
  lands a red tree — the sequencing error [[sp035]] hit, where Task 1 changed
  a contract its consumers' tests pinned.

## solution
A third feature-refresh of [[ft016]], the shape [[sp034]] and [[sp035]] both
used: `## extends [[ft016]]`, no `ft###` minted, no `us###` or `im###`
invented, and the finale archives the spec without flipping the accepted
Feature. Nothing here touches [[ft012]] or [[ft014]] — every change is inside
what this reader DISPLAYS ([[adr0028]], [[adr0031]]).

**`dotfiles-br55` is fixed at the choke point, not cell by cell.** Every grid
cell in all three grids — roster, flat log, thread — is written by ONE
function, `pad` (`roster.go:164`), called from the seven places that build a
row or a header. Neutralising inside `pad`, BEFORE it measures and truncates,
closes the hole by construction for every present and future column instead
of leaving a list of cells someone must remember to wrap. It also fixes the
accounting half of the defect in the same stroke: `runeWidth` returns 0 for
`r < 0x20`, so today an escape reaches the terminal while consuming none of
the width budget; neutralising first means what is measured is what is
emitted. `neutralize` is idempotent on already-clean text, so SUBJECT — which
`DeriveSubject` already neutralises — is unaffected, and every benign cell in
every existing golden test renders byte-identically. The roster's own label
columns get the same protection as a side effect, which is correct: they
carry census-supplied text from the same untrusted side. `detail.go`'s header
already wraps its raw string in `neutralize` and is left alone.

**`dotfiles-i1sw` takes fix option (a): `Threads()` stops sorting.** It groups
by key in FIRST-APPEARANCE order and keeps each group's messages in input
order, so the pane's single reorder point — `orderedMessages`, ID-descending
— is the only ordering in the system and the [[sp034]] `## plan` rule holds by
construction rather than by documentation. Option (b) (move the reorder to
`At`) is rejected because it changes the flat pane's order, which [[sp033]]
T6 pinned; option (c) (document the divergence) is rejected because it keeps
a mode toggle able to flip liveness under clock skew. `isNewer` and the
`At`-based assertions in `thread_test.go` are reworked accordingly — that is
the cost this option names up front.

**The three display changes are local.** The expand glyph becomes `+`
collapsed and `-` expanded, plain ASCII like the `>` / `v` it replaces, so no
width or drop rule moves and [[sp035]]'s blank cell for a non-expandable
one-message thread stays blank. `PARTICIPANTS` shows the NEWEST message's
direction as `from > to` while collapsed, and only the newest SENDER while
expanded, since the children below already name each message's sender and the
recipient is recoverable from them and from the detail pane. This is ordering
WITHIN the rendered cell only — the thread key stays the address-sorted
composite [[adr0034]] requires, and grouping, the for-you comparison and the
count are untouched. The detail pane moves its addresses inline, ONE PARTY
PER LINE, each line pairing a label with its own full address: inline removes
the position-matching the [[sp035]] block required, and one line per party
keeps a two-party envelope from running to roughly seventy cells. Addresses
stay unelided — this is the view an operator copies from.

**Sequencing is part of the solution, not an afterthought.** [[sp035]] landed
a task whose consumers' tests still pinned the old contract, leaving a branch
that could not merge alone; the fix there was a held merge, which worked but
should not have been needed. Here, two changes have consumers: the `pad`
neutralisation touches every grid's golden output, and the ordering and
participants changes touch `thread_test.go` and `log_test.go`. Each task must
therefore leave the whole suite green ON ITS OWN BRANCH, updating the
consumer assertions it invalidates as part of its own work. `spec-refinement`
owns turning that into a dependency order; the constraint is stated here so
the breakdown cannot quietly reproduce the same shape.

**What must not move.** Thread keys, address-based grouping and the for-you
address comparison ([[adr0034]]); no envelope field and no new `content`
parsing ([[adr0028]], [[adr0031]]); `--once` flat and byte-identical except
where a hostile label is now neutralised, which no benign bus can observe,
with [[sp030]] T9's pipe contract and the suite's `0x1b` check both still
binding; `tui.Model` comparable with the expansion set in `cmd/`; Go per
[[adr0030]]. Categories [[cat001]] and [[cat002]] unchanged.

No ADR is minted or overturned. `br55` might look like a policy decision, but
it is a defect against a rule [[sp034]]'s `## plan` already stated and
[[adr0031]] already implies — the code simply did not do what the plan
claimed.

**Confidence.** Nothing is unproven. `pad` is a four-line function with one
call path and `neutralize` already exists and is idempotent; the
order-preserving grouping removes code rather than adding a mechanism; the
three display changes are constants and a cell formatter in renderers that
are already under mutation-tested coverage. No PoC is warranted.

### conventions

- **One choke point for neutralisation.** `pad` (`roster.go:164`) is the only
  function that writes a grid cell — seven call sites across
  `roster.go`, `log.go`'s flat grid and `log.go`'s thread grid. It neutralises
  FIRST, then measures and truncates, so what is measured is what is emitted.
  No caller wraps its own cell.
- **One ordering.** After this spec `orderedMessages` (`cmd/agent-monitor/main.go`)
  is the only place the pane orders anything. `thread.go` sorts nothing.
- **Glyphs stay plain ASCII** — `+` collapsed, `-` expanded, blank when not
  expandable, blank on child rows.
- Detail addresses stay FULL and unelided; `shortAddress` is a log-width
  helper and never reaches that pane.

### anti-patterns

- **Do not neutralise cell-by-cell.** A list of wrapped call sites is a list
  someone extends without wrapping. `pad` is the invariant.
- **Do not neutralise AFTER measuring.** `runeWidth` returns 0 for `r < 0x20`,
  so measuring first reproduces the exact accounting bug `dotfiles-br55`
  describes: an escape that reaches the terminal spending no budget.
- **Do not re-introduce a sort in `thread.go`.** First-appearance grouping is
  what makes the single-reorder rule hold by construction.
- **Do not reorder the thread KEY.** Display order inside the
  `PARTICIPANTS` cell is not the key; the key stays the address-sorted
  composite ([[adr0034]]).
- **Do not land a task whose consumers' tests still pin the old contract.**
  [[sp035]] did and needed a held merge. Every task here greens the whole
  suite on its own branch, updating the assertions it invalidates.
- **Do not elide an address in the detail pane.**

### known limitations

- `PARTICIPANTS` now flips as a conversation turns (`a > b` becomes `b > a`).
  That is the point — the row reports who spoke last — but a reader scanning
  for a fixed string will not find one.
- Neutralising in `pad` silently changes any hostile cell's rendering in the
  ROSTER too. That is a fix, not a regression, and no benign census row
  moves a byte.
- First-appearance grouping means a thread's position follows the order
  `orderedMessages` produced, so thread order is now exactly as stable — or
  unstable — as the flat pane's, by construction.

#### success_criteria
- `pad` neutralises its input BEFORE `displayWidth` / `truncateCells`, so no

  must still pass, now for a stronger reason.

  fixture verbatim; asserts no `0x1b` anywhere in the rendered lines.

  same fixture through the thread grid, asserting BOTH cells.

  asserting byte-identity with the pre-change result.

#### success_criteria
- `Threads` contains no `sort.` call. Threads come out in order of first
  appearance in the input, and each thread's `Messages` stay in input order.
- Given the input `orderedMessages` produces (ID-descending), thread order
  and within-thread order are both ID-descending — so the flat pane and the
  threaded pane agree on which envelope is newest, including when `At`
  disagrees with ULID order.
- The clock-skew fixture from `dotfiles-i1sw` (two envelopes whose `At`
  contradicts their ULID order) yields the SAME row-0 envelope flat and
  threaded, where today it yields `m2` and `m1` respectively.
- `isNewer` is deleted, not left unused; its `At`-primary assertions in
  `thread_test.go` are rewritten to assert input-order preservation.

#### edge_cases
- A single-message thread is unaffected.
- An input already grouped (all of a thread's messages adjacent) produces the
  same output as an interleaved one — grouping is by key, not by adjacency.
- Empty input returns an empty non-nil slice, as today.
- An envelope with empty address fields still keys on `""` and keeps its
  position.
- `Threads` still mutates nothing it is given — the existing
  `InputNotMutated` guard stays green.

- `TestThreads_NoSortCallInSource` — scans `thread.go` for `sort.`; fails if
  a sort is reintroduced. The `## plan` anti-pattern made executable, in the

  produce identical output.
